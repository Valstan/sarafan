# Локальный стенд Сарафана на Windows — замена systemd-юнитов.
#
# На проде каждый юнит — файл в /etc/systemd/system. На Windows того же
# механизма нет, и «просто запустить процесс руками» не годится: машина
# перезагружается, окно закрывается, процесс умирает вместе с сессией.
#
# Здесь три уровня замены, и выбираются они по живучести:
#
#   1. **Планировщик задач Windows** (`schtasks`) — основной способ.
#      Задача «при входе в систему» поднимает процесс и держит его; у задачи
#      есть «перезапускать при сбое» и «не останавливать при закрытии».
#      Это ближайший аналог `Restart=always` + `WantedBy=multi-user.target`.
#   2. **Служба Windows** (`sc.exe create`) — нужен для PostgreSQL и Redis:
#      им нужен собственный аккаунт и автостарт до входа пользователя.
#      Требует прав администратора — на машине владельца это обычно так и есть.
#   3. **Ручной запуск** (`start-*.ps1`) — для отладки и разовых прогонов.
#
# Файлы:
#   common.ps1                 — общая часть (корень, venv, env-файл, логи)
#   start-web.ps1              — веб (замена юнита `setka`)
#   start-worker.ps1           — воркер очереди `celery` (замена `setka-celery-worker`)
#   start-wave-worker.ps1      — воркер очередей `wave,digest` (замена `setka-celery-worker-wave`)
#   start-beat.ps1             — планировщик (замена `setka-celery-beat`)
#   start-vk-bot.ps1           — VK-бот Long Poll (замена `setka-vk-bot`)
#   start-radar-intake.ps1     — приём радара (замена `setka-radar-intake`)
#   register-scheduled-tasks.ps1 — регистрация задач планировщика
#   install-stand.ps1          — развёртывание стенда с нуля
#
#   setup_minimax_area.py      — рабочая область движка MiniMax Code
#                                 (профиль CLI на машине → пул аккаунтов,
#                                 без которого движок отвечает no_accounts)
#   classifier_parity.py       — построчная сверка классификатора:
#                                 локальный движок против боевых вердиктов
#
# Полный план переезда (что чем заменяется и как проверяется) — в
# docs/MIGRATION_TO_WINDOWS.md.
#
# ── Ёмкость движка на стенде ───────────────────────────────────────────────
#
# Вызов MiniMax — это **процесс** CLI, а не HTTP-запрос: на боксе он занимал
# ~315 МБ RSS, и два таких процесса на боксе (1,5 ГБ, swap = 0) не помещались.
# Поэтому движок ограничивает себя ДО запуска процесса (модуль
# `modules/minimax_capacity.py`, PR #1266 — перенесён на стенд без правок):
#
#   * **слот** — в общем Redis (`SET … NX PX`), не больше одного вызова CLI
#     одновременно: `MINIMAX_CLI_MAX_CONCURRENT=1` (дефолт). Ограничение
#     общее для хоста, а не внутри процесса, — иначе два воркера поднимут по
#     CLI каждый (см. письмо в мозг от 25.11).
#   * **память** — «сколько можно выделить, не уходя в подкачку»: на Linux это
#     `MemAvailable` из `/proc/meminfo`, на Windows — `psutil.virtual_memory()
#     .available`. Порог: `MINIMAX_MIN_AVAILABLE_MB=384` (RSS живого вызова +
#     запас). Если места нет — вызов не запускается вовсе, отказ уходит в
#     платную страховку сразу, а не через 167 с, которые машина не переживёт.
#
# ⚠️ **Величина памяти на Windows читается через `psutil`, а не `/proc`** — до
# 26.11 `mem_available_mb()` знал только `/proc/meminfo` и на Windows отдавал
# `None`, то есть **проверка памяти молча выключалась, а слот в Redis работал**
# (защита наполовину). Правка — PR «Windows: проверка памяти движка работает».
#
# ⚠️ **Что на Windows НЕ перенесено:** сбор осиротевших процессов CLI
# (`modules/minimax_cli_reap.py`) — он Linux-only (`/proc` + `PPid = 1`), на
# Windows родитель умершего CLI не становится «единицей». На боксе это стоило
# 26 ядерных убийств за ночь (P240). На стенде замер пока не повторялся —
# см. P250.
#
# Машина владельца занята **его же** областями MiniMax Code (замер 26.11:
# 19 открытых областей, свободно 1.0–1.6 ГБ из 15.8 ГБ). Место под CLI есть,
# но запас небольшой — поэтому порог памяти на стенде стоит оставить включённым,
# а число одновременных вызовов — 1.
