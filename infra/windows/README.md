# Локальный стенд Сарафана на Windows — замена systemd-юнитов.
#
# На проде каждый юнит — файл в /etc/systemd/system. На Windows того же
# механизма нет, и «просто запустить процесс руками» не годится: машина
# перезагружается, окно закрывается, процесс умирает вместе с сессией.
#
# Здесь три уровня замены, и выбираются они по живучести:
#
#   1. **Планировщик задач Windows** (`schtasks`) — основной способ.
#      Задача «при входе в систему» поднимает процесс и держит его; у задачи
#      есть «перезапускать при сбое» и «не останавливать при закрытии».
#      Это ближайший аналог `Restart=always` + `WantedBy=multi-user.target`.
#   2. **Служба Windows** (`sc.exe create`) — для PostgreSQL: ему нужен
#      собственный аккаунт и автостарт до входа пользователя. Требует прав
#      администратора — на машине владельца это обычно так и есть.
#   3. **Ручной запуск** (`start-*.ps1`) — для отладки и разовых прогонов.
#
# ── Автозапуск БЕЗ входа в систему (заказ владельца 2026-11-27) ─────────────
#
# «Сайт должен работать после перезагрузки компьютера без входа в систему».
# Для этого юниту нужен триггер «при старте системы» и вход, не требующий
# интерактивной сессии. Сделано так:
#
#   * **S4U** (`-LogonType S4U`) — задача стартует при загрузке ОС, под
#     владельцем, и БЕЗ сохранения его пароля в задаче (в отличие от
#     «Выполнять независимо от регистрации» с паролем). Право
#     «Log on as a batch job» у группы Users на машине есть.
#   * **Пауза PT1M** после старта системы: сеть и PostgreSQL к этому
#     моменту ещё поднимаются. У каждого такого юнита есть перезапуск,
#     а туннель вдобавок переподключается сам.
#
# Без логина поднимаются: **веб** (`setka`), **туннель** (`setka-public-tunnel`)
# и **Redis** (`setka-redis`) — то есть ровно то, что нужно живому сайту.
# Воркеры, beat и даемоны оставлены на «при входе в систему»: они поднимают
# CLI-движок MiniMax и другие консольные инструменты, которым нужна
# интерактивная сессия. Перевод их на S4U — отдельное решение владельца.
#
# **Почему Redis — задача, а не служба Windows.** Служба идёт под LocalSystem,
# а на каталог с бинарниками Redis доступ есть только у владельца (ACL:
# PC79\valstan) → «Access is denied» при старте. Либо выдавать SYSTEM права
# на папку, либо оставить Redis задачей под владельцем — выбрано второе.
# PostgreSQL — настоящая служба, он поднимается сам.
#
# ⚠️ **Redis нельзя запускать напрямую `redis-server.exe`**: сборка msys2
# форкается (родитель выходит, остаётся сирота), задача теряет управление и
# перезапускается раз в минуту — новый redis падает с «Address already in
# use». Рабочий запуск — через `RedisService.exe run --foreground`.
#
# Файлы:
#   common.ps1                 — общая часть (корень, venv, env-файл, логи)
#   start-web.ps1              — веб (замена юнита `setka`)
#   start-worker.ps1           — воркер очереди `celery` (замена `setka-celery-worker`)
#   start-wave-worker.ps1      — воркер очередей `wave,digest` (замена `setka-celery-worker-wave`)
#   start-beat.ps1             — планировщик (замена `setka-celery-beat`)
#   start-vk-bot.ps1           — VK-бот Long Poll (замена `setka-vk-bot`)
#   start-radar-intake.ps1     — приём радара (замена `setka-radar-intake`)
#   start-tunnel.ps1           — обратный SSH-туннель на VPS (публичная витрина)
#   start-redis.ps1            — Redis (брокер celery и общий кеш)
#   redis-stand.conf           — конфиг Redis для стенда
#   register-scheduled-tasks.ps1 — регистрация задач планировщика
#   stop-unit.ps1               — остановка/перезапуск юнита (снимает и сирот)
#
#   ⚠️ `install-stand.ps1` в развёртывании стенда с нуля **НЕТ** (P251): стенд
#   сейчас собирается только вручную на этой машине (env-файл под gitignore,
#   79 переменных живут здесь). Файл в списке ниже не существует.
#
#   setup_minimax_area.py      — рабочая область движка MiniMax Code
#                                 (профиль CLI на машине → пул аккаунтов,
#                                 без которого движок отвечает no_accounts)
#   classifier_parity.py       — построчная сверка классификатора:
#                                 локальный движок против боевых вердиктов
#
# Полный план переезда (что чем заменяется и как проверяется) — в
# docs/MIGRATION_TO_WINDOWS.md.
#
# ── Остановка и перезапуск юнита ────────────────────────────────────────────
#
# **«Stop-ScheduledTask → Start-ScheduledTask» НЕ перезапускает юнит — он его
# размножает.** Задача поднимает цепочку wscript → cmd → powershell → python,
# и остановка задачи снимает только верхушку: python-потомок переживает
# остановку и остаётся сиротой — держит порт 8000 (веб) или забирает задачи
# из очереди (воркер). Следующий старт поднимает **второй** экземпляр рядом.
#
# Живой замер 26.11: после рестарта в 22:40 на каждую очередь висело по два
# воркера (09:58 и 22:40), работали **старые** — поднятые до смержей PR
# #1297/#1306, — а к вечеру у веба накопилось 11 экземпляров (22 процесса).
#
# Поэтому порядок жёсткий: **снять задачу → снять процессы → поднять задачу**.
#
# ```powershell
# # сухой прогон: показать, что будет снято, ничего не трогая
# powershell -ExecutionPolicy Bypass -File infra\windows\stop-unit.ps1 -TaskName setka -WhatIfOnly
#
# # перезапуск юнита: снять задачу, снять процессы, поднять заново
# powershell -ExecutionPolicy Bypass -File infra\windows\stop-unit.ps1 -TaskName setka-celery-worker -Start
#
# # список юнитов и их сигнатур
# powershell -ExecutionPolicy Bypass -File infra\windows\stop-unit.ps1 -TaskName -List
# ```
#
# Процессы снимаются **по сигнатуре командной строки**, а не по PID: PID
# меняется, сигнатура одна на юнит (`uvicorn main:app`,
# `celery_app worker … --queues=celery`, `… --queues=wave,digest`,
# `celery_app beat`, `vk_bot_daemon.py`, `radar_intake_daemon.py`). После
# остановки скрипт **проверяет**, что процессов не осталось, и падает с
# ненулевым кодом возврата, если они выжили.
#
# ⚠️ Шаг «снять процессы» гасит процессы **боевого** контура: публикация на
# паузе, пока юнит не поднят заново. Отсюда `-WhatIfOnly`.
#
# Сторож: `tests/test_infra/test_stand_unit_stop.py` — не даёт завести новый
# юнит без сигнатуры остановки и не даёт пробе супервизора вернуться к
# 5 секундам (таймаут короче ответа веба на тесной машине и был источником
# шторма из 11 экземпляров — P255).
#
# ⚠️ **Жёсткая остановка оставляет задачи в `unacked`.** Воркер подтверждает
# задачу после выполнения; убитый — не подтверждает, и сообщение пропадает из
# очереди, оставаясь в хеше `unacked`. Компоновщик вернёт его сам, но по
# таймауту видимости и только для доставок своего потребителя: на стенде 58
# задач веера сводки пролежали так больше часа (26.11, P256). Возврат —
# `scripts/restore_unacked.py` (по умолчанию сухой прогон, запись — с
# `--apply`).
#
# ── Пул воркера: `threads`, а не `solo` ─────────────────────────────────────
#
# **Почему не `solo`.** При пуле `solo` ETA-задачу (у нас это веер волны и веер
# сводки — у обеих `countdown=`) исполняет **поток таймера celery**, а обычные
# задачи — главный поток. Оба зовут общий персистентный event-loop
# (`utils/celery_asyncio`), а петля у процесса одна: второй, кто её взял,
# получает отказ, и задача падает целиком. Живой замер 27.11 06:47: держатель
# — поток `Timer-1`, из-за отказа падали лента хаба и **мама волны** (а мама —
# это «волна не пошла вообще»: 26.11 так умерли 5 мам-задач за сутки).
#
# **Что даёт `threads`.** Тела задач исполняют потоки пула (`concurrent.futures`),
# а поток таймера только раздаёт ETA-задачи — коллизии не бывает. Prefork
# (billiard) на Windows не работает вовсе: `PermissionError [WinError 5]`,
# проверено 26.11.
#
# **A/B-проба на стенде (27.11, изолированная очередь `probe`):**
#
# | Пул | Коллизий P253 | Отказов задач | Успешных задач |
# |---|---|---|---|
# | `solo`, старый `run_coro` | **16** | 24 | 230 |
# | `threads`, старый `run_coro` | 0 | 0 | 178 |
# | `solo`, новый `run_coro` (ждёт петлю) | 0 | 0 | 230 |
# | `threads` × 2, новый `run_coro` | 0 | 0 | **282** |
#
# **Два слота у волнового юнита.** На проде очередь `wave` обслуживают оба
# воркера (`--queues=celery,wave,digest` и `--queues=wave,digest`) — ADR-0022.
# На стенде очередь `wave` забирает один юнит, поэтому два места публикации
# берутся concurrency'ем пула (`--concurrency=2`). Замер 27.11: задача региона —
# 24.7 с в среднем, мама волны — 0.2 с, веер сводки — 1–3 мин на регион; с
# одним слотом сводка забирает слот на часы и волны протухают по сроку
# (P233, P234; 26.11 — волны 22:00 / 22:20 / 22:50 утрачены).
#
# Сторож: `tests/test_infra/test_stand_unit_stop.py` — не даёт вернуться к
# пулу `solo` и не даёт снять второй слот публикации.
#
# ── Ёмкость движка на стенде ───────────────────────────────────────────────
#
# Вызов MiniMax — это **процесс** CLI, а не HTTP-запрос: на боксе он занимал
# ~315 МБ RSS, и два таких процесса на боксе (1,5 ГБ, swap = 0) не помещались.
# Поэтому движок ограничивает себя ДО запуска процесса (модуль
# `modules/minimax_capacity.py`, PR #1266 — перенесён на стенд без правок):
#
#   * **слот** — в общем Redis (`SET … NX PX`), не больше одного вызова CLI
#     одновременно: `MINIMAX_CLI_MAX_CONCURRENT=1` (дефолт). Ограничение
#     общее для хоста, а не внутри процесса, — иначе два воркера поднимут по
#     CLI каждый (см. письмо в мозг от 25.11).
#   * **память** — «сколько можно выделить, не уходя в подкачку»: на Linux это
#     `MemAvailable` из `/proc/meminfo`, на Windows — `psutil.virtual_memory()
#     .available`. Порог: `MINIMAX_MIN_AVAILABLE_MB=384` (RSS живого вызова +
#     запас). Если места нет — вызов не запускается вовсе, отказ уходит в
#     платную страховку сразу, а не через 167 с, которые машина не переживёт.
#
# ⚠️ **Величина памяти на Windows читается через `psutil`, а не `/proc`** — до
# 26.11 `mem_available_mb()` знал только `/proc/meminfo` и на Windows отдавал
# `None`, то есть **проверка памяти молча выключалась, а слот в Redis работал**
# (защита наполовину). Правка — PR «Windows: проверка памяти движка работает».
#
# ⚠️ **Что на Windows НЕ перенесено:** сбор осиротевших процессов CLI
# (`modules/minimax_cli_reap.py`) — он Linux-only (`/proc` + `PPid = 1`), на
# Windows родитель умершего CLI не становится «единицей». На боксе это стоило
# 26 ядерных убийств за ночь (P240). На стенде замер пока не повторялся —
# см. P250.
#
# Машина владельца занята **его же** областями MiniMax Code (замер 26.11:
# 19 открытых областей, свободно 1.0–1.6 ГБ из 15.8 ГБ). Место под CLI есть,
# но запас небольшой — поэтому порог памяти на стенде стоит оставить включённым,
# а число одновременных вызовов — 1.
