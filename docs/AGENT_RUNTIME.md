# Агентный runtime: профили, очереди, инструменты, замер параллельности

> Каркас «модель выдаёт задание — инструмент выполняет» на локальной машине:
> кто чем занимается, в какую очередь попадает, какие инструменты видит
> модель и сколько заданий машина держит одновременно.
>
> Решение — [ADR-0024](adr/0024-agentnyy-sloy-zadanie-instrument.md).

---

## 1. Слои

```
задание в очереди Celery
        │
        ▼
tasks.celery_app.run_agent_task          ← вход в конвейер
        │  (профиль → очередь → движок → лимит шагов)
        ▼
gateway_mcp.agent.AgentRunner             ← цикл «модель ↔ инструмент»
        │        │
        │        └── gateway_mcp.tool_registry.ToolRegistry
        │                 ├── шлюз VK:   vk_get_community, vk_get_wall, vk_call
        │                 └── локальная БД: sarafan_list_regions,
        │                                sarafan_find_posts, sarafan_region_stats
        ▼
AgentResult → обратно в конвейер (ок, output, tool_calls, steps)
```

Ключевые модули:

| Модуль | Что в нём |
|---|---|
| `gateway_mcp/tool_registry.py` | `ToolSpec` (имя, описание, JSON Schema, обработчик) и `ToolRegistry` (регистрация, каталог, вызов с валидацией) |
| `gateway_mcp/tools.py` | Три read-инструмента VK-шлюза (схемы — из pydantic-моделей) |
| `gateway_mcp/local_tools.py` | Три read-инструмента по локальной базе Сарафана |
| `gateway_mcp/registry.py` | Сборка реестра: какие инструменты доступны агенту |
| `gateway_mcp/agent.py` | Сам цикл: задание → модель → инструмент → результат |
| `gateway_mcp/model_adapters.py` | Адаптеры движков: DeepSeek, MiniMax, заглушка |
| `gateway_mcp/profiles.py` | Профили агентов: очередь, движок, лимит шагов |
| `gateway_mcp/bench.py` | Замер ёмкости машины |

## 2. Разделение задач по агентам

**Проблема, которую решает.** На проде волна и периодика делят один воркер и
его слоты (ADR-0020, ADR-0022): длинная задача волны съедает слот, мелкая
периодика ждёт и протухает по `expires`. Владелец хочет на локальной машине
«под каждую задачу свой агент».

**Механика.** Разделение идёт **по очереди Celery**: у профиля своя очередь,
у очереди — свой процесс воркера. Один воркер — один слот; блокирует его
только то, что лежит в его очереди.

| Профиль | Очередь | Движок | Шагов | Для чего |
|---|---|---|---|---|
| `generic` | `agent` | DeepSeek API | 4 | Универсальные задания из очереди |
| `wave` | `agent_wave` | MiniMax Code CLI | 6 | Длинные задания: веер регионов, публикационные слоты |
| `discovery` | `agent_discovery` | MiniMax Code CLI | 6 | Подбор сообществ: карточки на входе, вердикт по каждой (ADR-0015) |

Имена очередей агентов **не совпадают** с боевыми (`celery`, `wave`,
`digest`): локальный стенд поднимается рядом с боевой раскладкой, и
одинаковые имена означали бы, что локальный агент заберёт боевую задачу.

**Маршрутизация — явная** (`apply_async(queue=...)`), а не через `task_routes`:
тогда переезд не зависит от правки боевой конфигурации очередей.

```python
from tasks.celery_app import enqueue_agent_task

enqueue_agent_task("Собери сводку по региону mi", profile_name="wave")
```

**Пул аккаунтов MiniMax.** Каждый воркер сам берёт аккаунт из пула
(`modules/karman_minimax` — аренда у Кармана; `modules/minimax_engine` —
собственный пул с ротацией и чек-ином). Отдельный процесс воркера означает
отдельную аренду: агент, съевший лимит аккаунта, не валит остальных.

**Локальные модели.** Профиль — это ещё и выбор движка (`engine`). Если
владелец решит крутить локальные модели вместо внешнего API, меняется поле
движка у профиля, а не код конвейера: очередь, инструменты и лимит шагов
остаются прежними.

## 3. Каталог инструментов

Инструмент — это **имя + JSON Schema аргументов + вызов**. Описание
пишется один раз (в pydantic-модели или в docstring обработчика) и дальше
читается и моделью, и MCP-обёрткой, и документацией.

### 3.1. Шлюз VK (read-only, требует `SARAFAN_GATEWAY_KEY`)

| Инструмент | Что делает | Аргументы |
|---|---|---|
| `vk_get_community` | Инфо о сообществе (`groups.getById`) | `group` (id или screen_name), `fields` (CSV, опц.) |
| `vk_get_wall` | Последние посты со стены (`wall.get`) | `owner_id` (сообщество — с минусом), `count` (1..100), `offset` |
| `vk_call` | Произвольный read-метод VK из allowlist шлюза | `method`, `params` (объект) |

Все три помечены read-only (`readOnlyHint`), шлюз запись запрещает.

### 3.2. Локальная база Сарафана (read-only)

| Инструмент | Что делает | Аргументы |
|---|---|---|
| `sarafan_list_regions` | Список регионов: код, имя, тип, активность | `active_only` (по умолчанию true), `limit` (1..500) |
| `sarafan_find_posts` | Посты региона: текст (усечён), AI-вердикт, дата | `region_code`, `limit` (1..100), `only_unclassified` |
| `sarafan_region_stats` | Счётчики региона: посты всего/с вердиктом, сообщества всего/активные | `region_code` |

Живой каталог печатается так:

```python
from gateway_mcp.registry import build_registry
print(build_registry().catalog())
```

## 4. Замер параллельности на локальной машине

**Машина (26.11.2026):** Windows, Python 3.12.10, 8 ядер, 16 ГБ RAM (на
момент замера свободно ~2,9 ГБ — рядом стояли PostgreSQL, Redis, веб и
воркеры).

**Что измеряется.** Сколько заданий агента машина держит **одновременно** и
сколько **в час** проводит. Модель заменена заглушкой с управляемой
задержкой: боевой движок отвечает по сети, и его латентность мешала бы
измерять ёмкость машины.

### Прогон A — контур без задержки (задержка 0,05 с)

```powershell
.\venv\Scripts\python.exe -m gateway_mcp.bench --concurrency 1,2,4,8,16 --tasks 32 --latency 0.05
```

| Конкурентность | Заданий/час | Секунд на 32 задания | Ошибок |
|---|---|---|---|
| 1 | 28 800 | 4,00 | 0 |
| 2 | 58 065 | 1,98 | 0 |
| 4 | 115 200 | 1,00 | 0 |
| 8 | 237 526 | 0,49 | 0 |
| 16 | 460 800 | 0,25 | 0 |

**Вывод.** Контур **не является узким местом**: до 16 одновременных заданий
рост линейный, ошибок ноль. Ограничитель — движок, не машина.

### Прогон B — с настоящими инструментами по локальной базе (задержка 2 с)

```powershell
.\venv\Scripts\python.exe -m gateway_mcp.bench --real-tools --env-file config\local-stand.env --concurrency 1,4,8,16 --tasks 16 --latency 2
```

| Конкурентность | Заданий/час | Секунд на 16 заданий | Ошибок |
|---|---|---|---|
| 1 | 889 | 64,8 | 0 |
| 4 | 3 579 | 16,1 | 0 |
| 8 | 7 158 | 8,0 | 0 |
| 16 | 14 346 | 4,0 | 0 |

Здесь каждое задание — два обращения к движку (вызов инструмента и финальный
ответ) по 2 с, то есть 4 с на задание. При 16 параллельных заданиях машина
проводит **~14 300 заданий в час** — это потолок, заданный задержкой
движка, а не машиной.

### Что эти числа **не** говорят

* Они не говорят, сколько заданий в час выдержит **боевой** движок с пулом
  аккаунтов: там ограничитель — лимиты API, аккаунтов и VK, а не железо.
* Они не учитывают, что MiniMax Code CLI поднимает **процесс на аккаунт**
  (на проде это и был причиной ядерных убийств — ADR-0021): на этой машине
  16 ГБ RAM позволяют держать несколько таких процессов, но каждый ест
  ~250–330 МБ.
* Число «сколько одновременно» для боевого контура — это решение владельца:
  столько процессов MiniMax, сколько машина тянет без свопа.

**Рекомендация владельцу (стартовое значение):** 4 одновременных агента на
этой машине. Обоснование: 4 ядра из 8 остаются системе и PostgreSQL, 16 ГБ
RAM — это 4 × 330 МБ на CLI плюс запас; при 8 агентах пиковое потребление
растёт до ~2,6 ГБ только на CLI, и Windows начнёт давить подкачкой.

## 5. Ограничения Windows, найденные при подъёме

| Что | Симптом | Решение |
|---|---|---|
| **Пул Celery** | Prefork (`billiard`) на Windows: дочерний процесс падает с `PermissionError: [WinError 5] Отказано в доступе` на общем счётчике пула (`billiard/pool.py::_ensure_messages_consumed`); воркер рапортует `ready` и бесконечно перезапускает детей | `--pool=solo`. На боевом Linux остаётся prefork |
| **Файл расписания beat** | На Windows beat пишет файл расписания в текущий каталог; при перезапуске из планировщика «рабочий каталог» другой — расписание молча терялось бы | `--schedule` и `--pidfile` заданы явно в `start-beat.ps1` |
| **env-файл** | На Linux переменные даёт systemd (`EnvironmentFile=`); на Windows их нет — процесс падал бы на `config.runtime._require("DATABASE_URL")` ещё на импорте | Файл читает сам процесс **до** bootstrap'а: `infra/windows/local_env.py` (`SETKA_ENV_FILES`) |
| **Очистка временных каталогов pytest** | `pytest` падает на финальной уборке `tmp_path_factory` с `PermissionError: [WinError 5]` на каталоге в `%TEMP%` | Обход: `--basetemp=<каталог внутри репозитория>`. Несовместимость **не** в тестах проекта, а в pytest на этой машине |
