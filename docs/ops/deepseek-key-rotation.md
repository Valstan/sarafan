# Ротация ключа DeepSeek на проектный (D-188)

**Зачем.** До 11.11.2026 в комнате `setka` лежал **общий** ключ DeepSeek: на одном
аккаунте жили два проекта, и по счёту шли вызовы `deepseek-v4-pro`, которых нет в
нашем коде (замер мозга, 07.11). Владелец решил 11.11: **свой ключ на проект** —
выпустить отдельный, положить в нашу комнату, общий отозвать.

Документ — **порядок действий**, а не теория: после правки ключа в комнате
счёт должен показать, что платит только наш проект, и ни одна лишняя модель в
корпусе появиться не должна.

## Что где лежит

| Что | Где | Кто трогает |
|---|---|---|
| Ключ DeepSeek | комната `setka`, имя `DEEPSEEK_API_KEY` | владелец (UI комнаты) |
| Как доезжает до процесса | `modules/secrets_bootstrap.py` — тянет из комнаты при старте процесса | — |
| Как читается | `config/deepseek.py::get_api_key()` — **из окружения при каждом вызове**, не при импорте | — |
| Имя модели | `config/deepseek.py::DEFAULT_MODEL` = `deepseek-flash`; на проде `DEEPSEEK_MODEL=deepseek-flash` | — |
| Что в корпусе | `content_classifications.model` — **фактическое** имя модели из ответа, не запрошенное | — |

Ключ читается при каждом вызове, поэтому **ротация не требует правок кода**: новое
значение в комнате + перезапуск процессов.

## Порядок (шаг владельца → наши шаги)

1. **Владелец** выпускает отдельный ключ DeepSeek на проект и кладёт его в
   комнату `setka` под именем `DEEPSEEK_API_KEY` (значение вне git).

   ⚠️ **Ключа нет в `/etc/setka/setka.env`** — он живёт **только в комнате** и
   доезжает до процесса через bootstrap при старте. Проверено на боксе 11.11:
   `grep DEEPSEEK_API_KEY /etc/setka/setka.env` → 0 совпадений. Правка env-файла
   на боксе ничего не меняет.

2. **Мы** переключаем потребителей: перезапуск процессов подхватывает новое
   значение из комнаты при bootstrap'е.

   ```bash
   ssh sarafan 'cd ~/SETKA && sudo -n systemctl restart setka setka-celery-worker setka-celery-beat'
   ```

3. **Проверка, что переключились** — ключ в корпусе лежит по отпечатку, а не сам
   ключ. Значение наружу не выводится, сравниваются только первые 16 символов
   хэша.

   **Проверенная команда** (отпечаток эффективного ключа; запускать **до** и
   **после** перезапуска — значения должны разойтись):

   ```bash
   ssh sarafan "sudo -n bash -c 'set -a; . /etc/setka/setka.env; . /etc/setka/secrets-token.env; set +a; cd /home/valstan/SETKA && ./venv/bin/python -c \"import hashlib,os,sys; sys.path.insert(0,\\\".\\\"); from modules import secrets_bootstrap as sb; sb.bootstrap_secrets(); v=os.environ.get(\\\"DEEPSEEK_API_KEY\\\",\\\"\\\"); print(hashlib.sha256(v.encode()).hexdigest()[:16] if v else \\\"ABSENT\\\")\"'"
   ```

   Ожидаемый вид: `a202b4bc08c82274` (отпечаток текущего общего ключа, 11.11).
   Если после перезапуска отпечаток **тот же** — новое значение не доехало,
   переключения не было.

   ⚠️ **Не искать ключ в `/proc/<pid>/environ`** — bootstrap подставляет его в
   `os.environ` уже после старта процесса, и в `/proc` его видно не будет
   (проверено: 0 совпадений по всем процессам). Отпечаток берётся путём
   приложения — тем же bootstrap'ом.

4. **Отзыв общего ключа** — по правилу ротации: новое значение → смена у
   потребителей → отзыв старого. Отзыв делает владелец (доступ к аккаунту
   DeepSeek) **после** того, как мы подтвердили переключение.

   ⚠️ **Проверка отзыва — не через `sudo`-команду.** Отозванное значение
   попадает в `/var/log/auth.log` (G566). Значит проверять надо **по логу** и по
   факту «старый ключ больше не работает», а не командой с ключом в аргументах.

5. **Контроль после отзыва** — корпус должен остаться чистым:

   ```sql
   -- 1) в корпусе нет моделей кроме нашей
   select model, count(*) from content_classifications
    where created_at > now() - interval '1 day' group by 1 order by 2 desc;

   -- 2) v4-pro не появляется вообще
   select count(*) from content_classifications where model like '%v4-pro%';
   ```

   Ожидаемо: `deepseek-flash` (платный движок) + модели локального движка
   (`deepseek-v4.1-flash-free`, `glm-5.3-flash-free` — free-тир на нашем боксе,
   к счёту DeepSeek отношения не имеют).

## Что уже держится в коде (проверено 11.11)

- **«Только flash» — наше правило целиком** (п.3 мандата D-188):
  - `config/deepseek.py` — явное имя `deepseek-flash`, а не алиас
    `deepseek-chat` (маршрутизацию алиаса провайдер меняет молча);
  - `thinking` выключен (`thinking: {"type": "disabled"}`) — раздумья съедали
    бюджет ответа, вердикта не было (замер 07.11: 82 вердикта вместо 200);
  - **сверка имени из ответа**: `modules/deepseek_client.py:326-333` — если
    ответ пришёл от другой модели, это попадает в лог отдельной строкой, а в БД
    ложится **фактическое** имя модели, а не запрошенное.
- **Замер по корпусу за 14 дней (11.11):** `deepseek-flash` — 21 712 вердиктов,
  `deepseek-v4-pro` — **0 за всё время**. Алиас `deepseek-chat` встречался
  568 раз, но только 06.11 — до перехода на явное имя; с 07.11 в корпусе
  только `deepseek-flash`.

## Чего делать нельзя

- **Не выводить значение ключа** в лог, в чат, в PR, в письмо. Только отпечаток
  (хэш первых 16 символов) — он годится для сравнения «до/после» и ничего не
  раскрывает.
- **Не отзывать общий ключ до переключения.** Пока старая пара работает, отзыв
  убьёт и соседний проект на том же счёте.
- **Не проверять отозванный ключ командой с ключом в аргументах** — значение
  попадёт в `/var/log/auth.log` (G566).
- **Не путать локальный движок с облачным.** `deepseek-v4.1-flash-free` и
  `glm-5.3-flash-free` в корпусе — это free-тир на нашем боксе (`opencode`),
  к счёту DeepSeek отношения не имеют. Ротация их не касается.
