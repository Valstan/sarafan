# Путь заливки фото на стену сообщества: кому каким токеном

> Замер 09.11.2026, живые пробы на полигоне `137760500` и ещё семи группах сети.
> Матрица снята **пробой, а не чтением доки** — так же, как
> [`group-setup-probe.md`](group-setup-probe.md). Здесь та же ловушка: интуиция
> «community-ключ умеет всё со своей стеной» неверна.
>
> Дополнение 10.11.2026: [троттлинг upload-сервера — три лица одного отказа](#троттлинг-upload-сервера-три-лица-одного-отказа-замер-1011).

## Матрица «операция × токен»

| Операция | community-токен группы | user **MAMA** (админ) | user **VALSTAN** (владелец) |
|---|---|---|---|
| `photos.getWallUploadServer` + `photos.saveWallPhoto` | ⛔ `[27] method is unavailable with group auth` | ✅ | ✅ |
| прикрепить такое фото к посту **community-токеном** | — | ⛔ **молча**: пост уходит, вложения нет | ✅ и фото становится **собственностью группы** (`owner_id = -group_id`, альбом `-7`) |
| `wall.post` с `attachment=photo<owner>_<id>` (без `access_key`) | ✅ публикует | ✅ публикует | ✅ публикует |

## Что это значит

1. **Заливать в стену сообщества community-токеном нельзя вообще.** Метод
   `photos.getWallUploadServer` — user-only; community-auth отбивается кодом 27.
   Ровно эта ошибка дала **371 неудачную загрузку за вечер 08.11** и ни одной
   картинки в вечернем сборнике.
2. **Залить может не всякий админ.** Фото, залитое администратором (MAMA),
   community-токен в записи **не принимает** — и не ругается: пост уходит
   текстом, вложения нет. Тишина здесь опаснее ошибки: сборник выходит «гладко».
3. **Принимает фото аккаунта-владельца** (того, от кого выпущены наши
   community-ключи) — и переводит его в собственность группы. Личный альбом
   владельца при этом не засоряется.
4. **`access_key` меняет судьбу фото:** с ним фото остаётся личным
   (`owner_id` = пользователь, альбом `-5`), без него — становится фото группы.
   Для сборника нужен второй вариант (фото в стене сообщества).

Правило прикрепления проверено на трёх группах × два аккаунта; картина
одинаковая везде, где community-ключ выпущен от аккаунта владельца.

## Потолок загрузок: HTTP 405 от upload-сервера

`pu.vk.com` после ~19–20 загрузок подряд отдаёт **HTTP 405** (nginx
«405 Not Allowed»). Это антиспум, а не запрет: отказ проходит после паузы
~70 с.

Замер в прод-режиме (50 загрузок, пауза 0.6 с ≈ 0.46/с): **48 успехов и 2
отказа**. Отсюда рабочий темп — **≤0.4/с** (пауза 3 с между загрузками) плюс
ретрай на 405 после паузы 70 с.

405 приходит **не-json'ом** (HTML от nginx), поэтому код ответа смотрится
отдельно от разбора json: иначе «не JSON» выглядит как «сервер не ответил»,
ретрай не случается и фото молча выпадает.

> ⚠️ **Этот замер не воспроизводится (проверено 10.11).** Прогон 50 загрузок
> подряд 10.11 давал троттлинг уже с 5–17-й загрузки. Причина в том, что 405 —
> лишь **одно из трёх лиц** отказа, а сам потолок считает не «загрузок подряд»,
> а что-то другое (окно или дневная квота аккаунта — по счёту не восстановить).
> Что именно лечится паузой — в разделе ниже.

## Троттлинг upload-сервера: три лица одного отказа (замер 10.11)

**Симптом.** За вечер 09.11 сборники вышли **с картинками**, но часть фото
пропала молча: в журнале воркера 100 попыток загрузки, из них 72 отказа
(71 строка «upload вернул пусто», 28 строк про 405).

### Три отказа, которые лечатся одной паузой

| # | Что прислал ВК | Как это выглядело в журнале | Лечится паузой? |
|---|---|---|---|
| 1 | HTTP **405**, тело — HTML от nginx | `upload-сервер отдал 405` | ✅ да |
| 2 | HTTP **5xx**, тело — HTML «The page is temporarily unavailable» | `upload вернул пусто: {}` | ✅ да |
| 3 | HTTP **200**, `{"server": N, "photo": "", "hash": "H"}` — файл залит, фото не создано | `upload вернул пусто: {'server': …, 'photo': '', …}` | ✅ да |

**До 10.11 переповторялся только 405.** Два других отказа уводили фото молча:
файл уходил в ВК, фото не создавалось, код писал «вернул пусто» и уходил дальше.

**Пауза 70 с + повтор — лечит все три.** Замерено 10.11: 5 из 5 отказов после
паузы вернули полноценное фото. Паузы 20 с **не хватает**: окно открывается
примерно через 60 с (проверено: 20 с → 405, 40 с → 405, 60 с → успех).

### Что отказом НЕ является (проверено пробой, чтобы не чинить не то)

- **Не дедуп.** Одна и та же картинка принята трижды подряд, три разных id.
- **Не картинка.** Боевой конвейер (скачать → ресайз → водяной знак → шум) на
  полигоне: 6 из 6 успехов.
- **Не группа.** 14 боевых групп подряд: 13 успехов, один 405.
- **Не токен.** Всё измерено токеном владельца (`VALSTAN`) — тем же, что в бою.

### Что на самом деле потеряно (проверено по постам, а не по журналу)

Журнал воркера показывает **попытки**, а не результат. Перечитывание самих
постов за 09.11 (57 сборников, `scripts/probe_digest_attachments.py`):

- **57 из 57 сборников вышли с фото** — 258 фото, от 1 до 10 на сборник,
  среднее 4,5; ни одного сборника без картинки;
- все фото — **собственность группы**: `owner_id` = −group_id, `album_id` = −7.

То есть «фото не прикрепились нигде» — неверно; потеряна **часть** фото
(≈72 из ≈330 попыток, ~22 %), а не все. Вывод «ничего не прикрепилось» был бы
сделан по журналу — и был бы неверен: **факт о предмете читается по предмету**.

### Свойство фото до и после поста

`photos.saveWallPhoto` кладёт фото в **личный** альбом аккаунта-владельца
(`album_id` −14, `owner_id` = пользователь). Оно становится фото группы
(`album_id` −7, `owner_id` = −group_id) **в момент поста**: community-токен
переносит фото владельца в сообщество. Поэтому «фото осталось личным» без
поста — не дефект, а нормальный промежуточный шаг.

### Приёмка на проде (10.11)

Через **задеплоенный** код (`scripts/probe_photo_fix_live.py`, полигон):

| # | Что показала приёмка |
|---|---|
| загрузок | 12, **12 из 12 загружено** |
| троттлинг сработал | 4 раза: HTTP 500, HTTP 405, HTTP 405, HTTP 405 |
| исход | каждый отказ вылечен паузой 70 с + повтором — в журнале `photo: загрузка отбита троттлингом (HTTP 500 (троттлинг загрузок)), пауза 70 с (попытка 1/3)` |
| время | 315 с на 12 фото (с паузами) — раньше эти же отказы были терминальными, и фото просто терялось |

Цена видно прямо в замере: при ~100 попытках за вечер фото-фаза растянется на
десятки минут. Это осознанный размен — раньше эти фото просто не выходили.

### Как измерять

Обе пробы живут в `scripts/` и ходят по боксу (read-only, кроме загрузок):

```bash
# загрузка: троттлинг, темп, ретрай — на полигоне или по боевым группам
sudo -n bash -c 'set -a; . /etc/setka/setka.env; set +a; cd ~/SETKA \
    && PYTHONPATH=/home/valstan/SETKA ./venv/bin/python scripts/probe_photo_upload.py \
         --count 20 --interval 1.5 --groups polygon --empty-retry-wait 70'

# сколько фото реально ушло в посты (читает посты, ничего не пишет)
sudo -n bash -c 'set -a; . /etc/setka/setka.env; set +a; cd ~/SETKA \
    && PYTHONPATH=/home/valstan/SETKA ./venv/bin/python scripts/probe_digest_attachments.py'
```


## Где это применяется в коде

| Место | Кто заливает | Статус |
|---|---|---|
| `modules/publisher/photo_processing.py::upload_wall_photo` — вечерний сборник (P214) | **аккаунт-владелец** (`VK_PHOTO_UPLOAD_TOKEN_NAMES`, по умолчанию VALSTAN) | ✅ с 09.11; 10.11 — троттлинг (405 / 5xx / пустой `photo`) переповторяется с общей паузой 70 с |
| `modules/publisher/vk_wall_photo_upload.py` — рекламный кабинет, бродкаст | user-токен из `load_vk_routing()` — обычно **MAMA** | ⛔ фото терялось молча (замер 09.11, пост 649 на полигоне) → **починено PR #1038** (выкачено 09.11, приёмка на полигоне: пост 651 — фото прикрепилось и стало собственностью группы): заливает аккаунт-владелец, `access_key` из строки вложения убран |

Аккаунт-владелец выбирается через
`config.runtime.get_photo_upload_token_names()` и берётся **политикой токенов**
(`TokenPolicy.token_for_account`) — БД остаётся единым источником, env не
воскрешает выключенный аккаунт.

## Проверка на живой группе (без мусора)

Загрузить фото → прикрепить community-токеном → перечитать пост:

```python
att = f"photo{owner_id}_{photo_id}"        # без access_key
post = community_client.api_call("wall.post", {"owner_id": -gid, "message": "...", "attachment": att})
items = community_client.api_call("wall.getById", {"posts": f"-{gid}_{post['post_id']}", "fields": "attachments"})
assert items[0]["attachments"]
```

Пустой список `attachments` — значит, заливал не тот аккаунт.
