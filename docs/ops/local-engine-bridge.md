# Мост к локальному движку: как это устроено и как запустить

> Решение владельца 10.11.2026: локальная нейронка на ПК владельца — основной
> движок классификации, DeepSeek по необходимости (локальная недоступна или
> пропустила волну). Основа — мандат мозга от 09.11 («мост по схеме Pull,
> старт в тени; сначала сжать правилник»).

## Что построено (10.11)

| Файл | Где живёт | Что делает |
|---|---|---|
| [`modules/classifier/local_engine.py`](../../modules/classifier/local_engine.py) | бокс | общая логика: выгрузка батча, приём вердиктов, журнал прогонов, статистика для панели |
| [`scripts/local_bridge.py`](../../scripts/local_bridge.py) | бокс | CLI: `export` (батч + промпт) и `submit` (приём вердиктов) |
| [`scripts/local_bridge.sh`](../../scripts/local_bridge.sh) | бокс | обёртка: грузит env приложения и зовёт CLI (env-файл root-only, поэтому `sudo`) |
| [`scripts/local_engine_daemon.py`](../../scripts/local_engine_daemon.py) | **ПК владельца** | демон: тянет батч по SSH → считает локально → отдаёт вердикты; только стандартная библиотека |
| [`web/api/local_engine.py`](../../web/api/local_engine.py) + [`web/templates/local_engine.html`](../../web/templates/local_engine.html) + [`web/static/js/local_engine.js`](../../web/static/js/local_engine.js) | бокс | панель `/local-engine`: движок, качество, обучение |

## Схема Pull

```
ПК владельца                        бокс SETKA
─────────────                        ──────────
демон (по расписанию)
  │  ssh sarafan "sudo -n ~/SETKA/scripts/local_bridge.sh export --limit 20"
  │ ─────────────────────────────────►  отдаёт посты БЕЗ вердикта + тот же промпт,
  │ ◄─────────────────────────────────  какой получает облачный движок
  │
  │  локальная модель (OpenAI-совместимый API)
  │
  │  ssh sarafan "sudo -n ~/SETKA/scripts/local_bridge.sh submit" < verdicts.json
  │ ─────────────────────────────────►  запись вердиктов НАШИМ кодом (идемпотентно по lip)
```

Инициатива всегда на стороне ПК — домашний компьютер не нужно делать видимым из
интернета. Ключ от бокса демону не нужен: только SSH.

**Тождество промпта — условие честного сравнения.** `export` отдаёт ровно тот
system-сообщение (задача + эффективные постулаты) и тот же user-промпт, что
уходит в облако. Локальная модель отвечает на тот же вопрос, что и DeepSeek.

**Почему не HTTP-эндпоинты, а SSH.** HTTP-контракт классификатора
(`/api/classifier/pending`, `/postulates`, `/verdicts`) существует с времён
облачной рутины и подходит. Но env-файл приложения root-only, а ключ ingest
хранится на боксе; демон на ПК забирать его не должен. Через SSH бокс сам
отдаёт батч и сам принимает вердикты — ключ на ПК не появляется, а
инициатива остаётся на стороне ПК.

## Фолбэк: почему DeepSeek сам собой отходит на второй план

Ключ `lip` в `content_classifications` уникален: вердикт на пост ровно один.
Кто первый классифицировал — тот и записал. Поэтому:

* демон ходит чаще, чем часовой прогон бокса → посты забирает локальный движок,
  а облачный headless находит очередь пустой и **не тратит токены**;
* если ПК выключен, демон упал или не успел — посты остаются без вердикта, и их
  забирает облачный headless. **DeepSeek подключается ровно тогда, когда локальный
  движок не справился** — это и было задумано.

Побочный эффект: источник вердикта теперь виден (`source` = `local` / `headless`),
поэтому качество можно сравнивать по движкам, а не «вообще».

## Панель `/local-engine`

* **Движок** — прогоны демона: когда, сколько постов, сколько вердиктов, сколько
  записано, сколько длилось, ошибки (пустой круг тоже пишется — иначе «демон
  молчит» не отличить от «очереди нет»);
* **Качество** — согласие оператора отдельно по облаку и по локальной модели
  (`action` и `theme`) + **недельные окна**: растёт ли качество;
* **Обучение** — коррекции по неделям и судьба выученных правил (предложено /
  утверждено / отклонено / выведено);
* **Вердикты по источникам** по дням за 30 дней.

Панель закрыта входом оператора, как весь SETKA (`middleware/auth_gate.py`):
без сессии — 401 на API и 302 на страницу. Это не обход гейта, а его нормальная
работа: страницу видит только владелец.

## Что нужно от владельца (шаги на ПК)

1. **Модель.** OpenAI-совместимый эндпоинт: `llama-server` или `opencode
   serve`. Контракт тот же, что у облака: `/v1/chat/completions`,
   `response_format: {"type": "json_object"}`, `temperature 0.2`,
   `max_tokens` = 240 на пост.
2. **Железо.** Сжатый правилник — 8,4K токенов системного сообщения; плюс
   посты батча. Локальной модели нужен контекст ≥ 16K. По времени: ~1,2 ч
   вычислений в сутки (мандат мозга) — то есть даже CPU-модель подходит, если
   RAM хватает.
3. **Запуск.** Демон ставится на ПК из репозитория:

   ```bash
   python scripts/local_engine_daemon.py --model-url http://127.0.0.1:8081/v1 \
       --model-name local-model --interval 300
   ```

   Под Windows — Планировщик задач (при загрузке), на Linux — systemd timer.
   Демон сам переживает падение модели: волна уходит в облако (fail-open).
4. **Проверка без модели:** `python scripts/local_engine_daemon.py --dry-run --once`
   — покажет, какой батч он забрал бы.

## Ограничения, о которых надо знать

* **Качество локальной модели неизвестно на наших постах.** Мозг измерил на
  прототипе: совпадение с правками оператора **18,2 %** против 37–45 % у облака.
  Поэтому переключение «как есть» — не приговор: сначала **тень** (оба движка
  на одних и тех же постах, `scripts/classifier_headless_compare.py`), потом
  решение по факту сверки.
* **Склейка между регионами** в смешанном чанке отсекается кодом
  (`parse_chunk_response`), а не только промптом.
* **Отчёт о прогоне** пишется в `logs/local_engine_runs.jsonl` — это
  runtime-файл на боксе, не git.
