# 🔴 Telegram с бокса не отвечает: прокси живой, но приложение его не использует

> Запись `P219` реестра [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md). Индекс грепается, запись читается целиком, реестр целиком не читается никогда ([D-097](../../AGENTS.md)).

`⏱ 2026-11-05 · snooze 0 · fresh · **РЕШЕНО 08.11 (решение владельца): Telegram через наш CF-relay (практика мозга #041/G63) — без ВПН и без новой подписки; выкачено на прод 08.11**`

## Симптом

В логе celery-воркера на боксе:

```
WARNING telegram POST: сеть не ответила за 6 попыток:
ConnectTimeout: HTTPSConnectionPool(host='api.telegram.org', port=443)
WARNING classifier selection: фильтр молчит (uni/admin), режим=algorithmic-fallback
```

Сводки при этом **доходят до VK** (`bulletin_curation_runs.published_post_id` заполнен ✓), но
не доходят до Telegram-каналов районов ✗. Классификатор из-за этого уходит в
алгоритмический фолбэк — фильтр отбора молчит, часть волны проходит без вердиктов.

## Причина (замерено 05.11)

На боксе **жив** прокси-сервис:

```
$ systemctl is-active neural-vpn.service
active
$ ss -lntp | grep 1080
LISTEN 127.0.0.1:10808  users:(("xray",pid=150112))
```

но в `/etc/setka/setka.env` **нет ни одной переменной прокси** (`HTTP_PROXY`,
`HTTPS_PROXY`, `ALL_PROXY` — пусто), и в юните `setka-celery-worker` тоже только
`PATH` и `PROMETHEUS_MULTIPROC_DIR`. Приложение ходит в Telegram напрямую, а из
России api.telegram.org без прокси недоступен → таймаут.

## Почему нельзя просто добавить `ALL_PROXY` в env

Глобальный прокси меняет **выходной IP всех исходящих запросов** приложения,
включая публикацию в VK. Проект держит на своём IP идентичность (механизм ротации
«нейросети», `infra/neural/neural-identity-reset.sh`, квота аккаунта на этом же
выходе) — менять выход для всего — значит ломать идентичность и квоты.

## Что показала проверка 07–08.11

1. **Блок не «полу-потеря SYN», а полный.** Замер по логу воркера: **655 / 634 / 528
   отказов в сутки** (04–06.11), каждый — 6 попыток по 6 с ≈ **40 с** на вызов.
   Итого воркер впустую жёг около **7 часов процессного времени в сутки**.
2. **Бьются оба направления** — `sendMessage` (алерты владельцу, хартбиты,
   репосты в Telegram) и `getUpdates` (приёмник радара). Классификатор от этого
   не страдает: его отбор по «uni/admin» читает разбор тем, а не Telegram.
   Но **алертов и хартбитов нет вообще** — а это ровно тот сигнал, по которому
   владелец узнаёт о проблемах.
3. **Прокси-контур снесён 06.11 вместе с opencode** (`neural-vpn`, `xray`,
   `privoxy`). Восстанавливать его **не нужно и нечем**: подписка NextGenVPN в
   комнате КАРМАНА отдаёт **404, 0 байт** (ссылка протухла) — то есть и ВПН-путь
   сейчас нерабочий. Секрет из комнаты убираем (запись P220-хвост).
4. **Практика мозга уже описана** — #041 «РКН-блок внешнего API с РФ-бокса →
   конфиг-база + relay» и G63 (РКН-блок IP Telegram; лечение — relay вне зоны
   блока + **конфигурируемая база API**; «per-box доступность проверять curl'ом,
   не предполагать»). Наш `tg_relay` (Cloudflare Worker) уже есть и работает —
   он умеет `t.me/s/<channel>` и медиа; не хватало маршрута Bot API.

## Решение владельца (08.11)

**Telegram ходит через наш CF-relay.** Никакой ВПН, никакой новой подписки.

* `modules/telegram_http.py` — единственная дверь к Bot API — получила
  **настраиваемую базу**: `TELEGRAM_API_BASE` (пусто ⇒ прямое соединение, как
  было). При базе-relay адрес `https://api.telegram.org/bot<TOKEN>/<METHOD>`
  переписывается в `<base>/<METHOD>`, а **токен уходит заголовком `X-TG-Token`**
  (не в пути: секрет в URL утекает в лог — G239) и добавляется `X-Relay-Secret`.
  Переписывание живёт в одной двери — остальные модули о relay'е не знают.
* `infra/tg_relay/worker.js` — добавлен маршрут `GET|POST /bot/<method>`:
  проверяет `X-Relay-Secret`, сверяет токен со списком известных ботов
  (`TG_TOKEN_AFONYA`, `TG_TOKEN_VALSTANBOT` — в окружении воркера как
  secret_text), собирает `https://api.telegram.org/bot<token>/<method>` и
  пересылает тело. Прежние маршруты (`/s/<channel>`, `/media`) не тронуты.
* `scripts/deploy_tg_relay.sh` — деплой стал уметь привязывать токены ботов
  (берутся из комнаты КАРМАНА) и печатает готовую строку `TELEGRAM_API_BASE=…`.
* Прод: `TELEGRAM_API_BASE=https://tg-relay.<subdomain>.workers.dev/bot` в
  `/etc/setka/setka.env` + рестарт сервисов.

**Что НЕ делаем:** не поднимаем ВПН и xray обратно (мёртвый контур, мёртвая
подписка); глобальный `ALL_PROXY` по-прежнему не ставим — он менял бы выходной IP
публикаций в VK и ломал бы идентичность проекта.

**Проверка самого relay (с бокса):**

| Проба | Результат |
|---|---|
| наш токен VALSTANBOT | HTTP 200, `ok:true`, бот «Жемчужинка» |

| без `X-Relay-Secret` | HTTP 403 `forbidden` |

**Проверка пути приложения (не изолированный curl, а наш код):**
`modules.telegram_http.post("https://api.telegram.org/bot<TOKEN>/getMe")` →
`HTTP 200 | ok: True | бот: Жемчужинка`. До выката этот же вызов падал
`ConnectTimeout` к `api.telegram.org`.

**Telegram-ошибки в логе воркера:** последняя — `19:00:43`, рестарт воркера —
`19:01:40`, после рестарта — **0** ошибок (проверено по `logs/celery-worker.log`).

**Побочный хвост деплоя (закрыт в том же заходе):** скрипт деплоя оставлял
`/tmp/tg_relay_meta.json` — метаданные воркера с токенами ботов в открытом виде.
Файл затрён (`shred -u`), а сам скрипт теперь затирает его сам (правка в
`scripts/deploy_tg_relay.sh`).

**Регресс, который поймал CI:** первая версия `_prepare()` добавляла ключ
`headers` в kwargs **каждого** вызова, даже когда relay не настроен. Заглушки с
фиксированной сигнатурой (`fake_post(url, json=None, timeout=None)`) такой
аргумент не принимают — общий прогон падал (`tests/test_ad_cabinet/test_telemetry.py`).
Теперь ключ `headers` появляется только если есть что в него положить.
