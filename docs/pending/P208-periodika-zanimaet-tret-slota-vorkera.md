# 🟡 31 % слота воркера — периодика, а не публикации: интейки радара ждут в очереди волн

> Запись `P208` реестра [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md). Индекс грепается, запись читается целиком, реестр целиком не читается никогда ([D-097](../../AGENTS.md)).

`⏱ 2026-10-21 · snooze 0 · fresh`

## Что было измерено (21.10, лог воркера за 26 часов)

До этого вывода `parsing_stats` показывал только волны — 378 минут слота в сутки
(26 %). Полная картина из лога Celery (`Task <name> succeeded in Xs`) другая:

| Задача | Прогонов | Секунд | Доля слота |
|---|---|---|---|
| **все задачи** | 5 056 | 18.6 ч | **72 %** |
| волны `parse_and_publish_theme` | 1 643 × 23.4 с | 10.7 ч | 41 % |
| `poll_radar_vk_intake` | 677 × 9.1 с | 1.7 ч | 6.6 % |
| `poll_radar_bot` | 678 × 8.6 с | 1.6 ч | 6.2 % |
| `classify_pending_posts` | 8 × 589 с | 1.3 ч | 5.0 % |
| `share_neighbor_news` | 73 × 54 с | 1.1 ч | 4.2 % |
| `refresh_post_metrics` | 8 × 312 с | 0.7 ч | 2.7 % |
| остальная периодика (identity, comments, ads, suggested) | ~90 | ~1.5 ч | ~6 % |

**Вывод:** волны — это 41 % слота, а ещё 31 % занимает периодика. При 72 %
занятости очередь в пиках встаёт не из-за числа волн, а потому что слот уже занят
чужим прогоном.

## Главная находка: интейки радара почти всё время ЖДУТ

- `poll_radar_vk_intake` — `a_check` с `wait=10` (Bots Long Poll): 9.1 с из 9.1 —
  ожидание события, которого обычно нет;
- `poll_radar_bot` — `getUpdates` к `api.telegram.org`, который с бокса теряет
  около половины SYN (G307): 8.6 с на тик при `timeout=0`.

Оба крутятся **каждую минуту** в **единственном** слоте воркера. Волна,
пришедшая в этот момент, стоит в очереди за пустым ожиданием.

## Что сделано (PR #952)

- `modules/radar/vk_intake.py`: `LP_WAIT` 10 → 3 (тик остаётся минутным);
- `tasks/celery_app.py`: `radar-intake-bot` раз в две минуты, `expires` 55 → 110.

Эффект ожидаемый: ~6–7 % слота возвращается волнам, ожидание волны за поллингом
сокращается с ~9 с до ~3 с.

## Что осталось (нужно решение/работа)

1. **Вынести оба поллинга в демон** — ровно так уже сделано с
   `poll_sarafan_vk_bot` (`scripts/vk_bot_daemon.py`): «воркер на проде
   однопроцессный, минутный тик давал клиенту минуту ожидания на каждый шаг».
   Тот же довод теперь применим и к интейкам радара. Освобождает ещё ~13 % слота.
2. **`classify_pending_posts`** — 589 с (10 минут) за прогон, 8 раз в сутки.
   В пиковые часы это ровно тот прогон, за которым стоят волны. Кандидат — либо
   отдельная очередь, либо ночное окно.
3. **Вторая очередь для периодики** вообще (второй процесс с `--concurrency=1`)
   упирается в память: свободно ~373 МБ при 1 536 МБ и без swap (P164). Пока не
   решён вопрос памяти — только сокращение частоты.
4. **Карта `/pipeline` показывает только волны.** Периодика (31 % слота) в ней
   невидима — то есть владелец не видит того, что на самом деле занимает воркер.
   Добавить в карту блок «периодика: задача, интервал, средняя длительность».

## Что проверено и НЕ является дублем (чтобы не переоткрывать)

- **Фолбэк «все сообщества района»** в волнах (18 % чтений VK) — самый урожайный
  путь, а не лишняя работа: `sport` 39.8 % публикаций против 8.3 % по своим
  сообществам, `detsad` 29.1 / 2.0, `kultura` 55.2 / 16.3, `admin` 50.0 / 25.0.
- **Кэш донорских стен** — замерен и выключен 22.09: 2.3 % попаданий против
  семикратного роста памяти Redis.
- **VK-вызовы уже батчированы**: `execute` по 20 стен, 12 254 чтения стен в сутки
  ≈ 2.6 тыс. запросов (счётчики `setka:vk_usage:<день>:<токен>`).
