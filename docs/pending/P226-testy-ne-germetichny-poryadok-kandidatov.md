Полный прогон на боксе (Linux, Python 3.12.3, 11.11.2026) — `2 failed, 4624

  — ждали `probed == ['dead_tok', 'live_tok']`, получили `['live_tok']`;

  — ждали порядок `['MAMA', 'VITA', 'VALSTAN']`, получили `['VITA', 'VALSTAN', 'MAMA']`.

Оба — про **порядок кандидатов**: код отдаёт их в другом порядке, чем ждёт тест.

Что проверено, чтобы отделить «сломан код» от «сломан контекст прогона»:

- тот же файл **в изоляции — 40 passed**: на боксе и локально, под четырьмя разными
  `PYTHONHASHSEED` (0/1/2/3);
- падения воспроизводятся и с **живым Redis** (db 15), и с **недоступным** Redis
  (порт 6399) — то есть Redis ни при чём;
- те же два падения даёт **продовое дерево `5ed3c5d` без правок 11.11** — то есть
  падения давние и к документации отношения не имеют;
- обязательная проверка CI `test (3.12)` на `main` зелёная (PR #1070) — на
  `ubuntu-latest` тот же набор проходит.

Гипотеза (не проверена до конца): порядок кандидатов берётся из hash-упорядоченной
коллекции, поэтому он зависит от того, что нарегистрировано **до** этих тестов в
том же прогоне, — а не от окружения. Отсюда и расхождение «зелёное у одного, красное
у другого» при одном и том же коде.

Хвост (dev): сделать выбор кандидатов детерминированным (сортировка по имени или по
`last_used` — как и требует сам тест) либо сортировать в тестах. Пока порядок
плавает, «прогон зелёный» ничего не значит: красным может оказаться прогон у того,
у кого окружение богаче.

Факт (11.11.2026): бокс `~/SETKA`, Python 3.12.3, **1 ядро**; Redis прода — db 0
(976 ключей), тесты шли в db 15, прод не тронут. Побочно: на Windows тот же

## Состояние на 26.11.2026 — причина найдена, тест сделан герметичным

**Причина.** Гипотеза выше про hash-упорядоченную коллекцию — **неверна**. Порядок
READ-кандидатов задаёт ключ в `modules/vk_token_router.py`:

```python
calls_today = _calls_today_safe()          # ← ЖИВЫЕ счётчики token_usage
def _balance_key(name):
    lu = getattr(row, "last_used", None)
    return (calls_today.get(name, 0), lu is not None, lu or datetime.min)
```

Первая составляющая — **расход за сутки с той машины, где продукт реально
работает** (`token_usage`, читается из живой БД/Redis). Второй — `last_used`.

**Замер на стенде 26.11:** `VALSTAN=694, MAMA=706, VITA=768` — и порядок по этим
числам `['VALSTAN', 'MAMA', 'VITA']` **в точности** совпал с тем, что пришло в
ошибке (`assert ['VALSTAN', 'MAMA', 'VITA'] == ['MAMA', 'VITA', 'VAL...']`).

**Почему раньше было зелено.** Файл в изоляции проходит: без `DATABASE_URL`
живые счётчики недостижимы, `_calls_today_safe()` ловит исключение и отдаёт
`{}` → все расходы нулевые → порядок решает `last_used` (как и ждёт тест). В
полном прогоне на стенде env несёт **боевой** `DATABASE_URL` → счётчики живые →
порядок другой. Поэтому тест краснеет **только на машине, где продукт
работает**, и зелен на CI с чистой базой. Проверка 26.11 01:57 (последний
сохранённый полный прогон) была зелёной именно потому, что **стенд тогда ещё
не работал** — счётчиков не было.

**Починено** (`fix/hermetic-token-policy-test`): в тесте первая составляющая
ключа обнуляется явно — `monkeypatch.setattr(router, "_calls_today_safe",
lambda: {})`, тем же приёмом, который уже применён в этом же файле
(`test_load_community_tokens...`, ~строка 1092). Проверено в обоих контекстах:
с живым `DATABASE_URL` стенда и без него — 42 passed.

**Что осталось.** Второй тест из 11.11
(`test_pick_healthy_read_token_skips_dead_and_cooldowns_it`) в прогонах 26.11
не воспроизводился — падал только тест порядка. Если он снова всплывёт — чинить
тем же способом (изолировать внешнее состояние), а не ослаблять проверку.

## Состояние на 26.11.2026 (второй симптом того же класса) — прогон зависел от RAM машины

После починки величины памяти (`PR #1297` — на Windows она читается по-настоящему,
через `psutil`) полный прогон упал на **другом** тесте:
`tests/test_classifier/test_minimax_cli_state.py::test_cli_killed_by_memory_is_retried_once_after_state_reset`
(«после сброса состояния повтор должен удаться»). В изоляции тот же тест проходил
4/4 — RAM машины гуляла вокруг порога 384 МБ: на тесной машине повтор после
ядерного убийства **не делается**, и это правильно, но не предмет теста.

**Корень глубже, чем сам тест.** `tests/conftest.py` выключает механизм ёмкости
в тестах одной строкой (`MINIMAX_CLI_CAPACITY_ENABLED=0` — «в тестах регулятора
нет»), но выключатель касался только **слота**: `memory_decision()` его
игнорировала и продолжала мерить память по-настоящему. То есть «выключить всё»
не выключало всё — и прогон зависел от состояния машины.

**Починено:**

1. `memory_decision()` уважает выключатель (`capacity_check: disabled`) —
   аварийный откат теперь откатывает обе половины регулятора, как и обещает
   документация модуля («0 — выключить всё»).
2. Тест повтора мокает величину явно (`mem_available_mb → 664`) — его предмет
   «сброс состояния и ровно один повтор», а не запас RAM машины.
3. Тест порядка READ-кандидатов мокает балансировку (`_calls_today_safe → {}`) —
   см. выше.

**Класс, который стоит помнить:** тест, который читает **живое** состояние
машины, зелен на CI (чистая база, много RAM) и краснеет на живой машине. И
наоборот: прогон 26.11 01:57 был зелёным именно потому, что **стенд тогда ещё
не работал** — счётчиков `token_usage` не было, а RAM была свободна. «Прогон
зелёный» на такой машине значит мало: он говорит, что машина в тот момент была
свободна.
