## Простыми словами: что такое «радар» и «репосты»

**Радар** (`modules/radar/`) — это отдельная «разведка» рядом с основным конвейером.
Она ходит по внешним источникам (RSS-ленты сайтов, веб-источники), вылавливает оттуда
новые материалы и **доставляет** их дальше: в архив радара, в веб-ленту и — главное —
**в Telegram-каналы через наших ботов**. Отдельный демон `radar-intake.service`
крутится на боксе и каждые 25 секунд опрашивает источники («sources-poll: sources=3,
new_items=1» в логе).

**Репост** (`modules/publisher/telegram_repost.py`) — это перепечатка найденного
материала в Telegram-канал конкретного бота. Например, бот **AFONYA** («Малмыж-Инфо»)
должен перепечатывать свежие новости района в свой канал. Репост делается **токеном
бота**: без токена в процессе код не знает, от чьего имени слать, и честно пишет
в лог «No Telegram token for bot 'AFONYA'; skipping repost to …» — то есть **материал
в канал не уходит**.

Это **не** основная лента районов: основные посты идут из нашего собственного
конвейера (парсинг ВК → классификатор → сводка → публикация в VK-группе). Радар —
это про внешние источники и про Telegram-каналы.

Почему токена нет: демон радара стартует **без окружения** (`Environment=` пуст) и
**не вызывает** `secrets_bootstrap`, а токены ботов лежат только в комнате КАРМАНА
(`TELEGRAM_TOKEN_AFONYA`, `TELEGRAM_TOKEN_VALSTANBOT`). Основное приложение bootstrap
вызывает и потому токены у него есть; радар — нет.

**Что это значит по деньгам и работе:** с 31.10 в Telegram-канал AFONYA не дошло
349 репостов из радара. Основная лента и наши VK-группы от этого не страдают —
страдает только Telegram-канал бота «Малмыж-Инфо» (и любые другие каналы, куда
радар сам перепечатывает).

**Что предлагается (нужно решение владельца)** — подробности ниже, в разделе
«Что предлагается»: дать радар-приёмнику окружение (тогда репосты поедут) или
оставить как есть и заглушить предупреждение.

## Причина найдена (08.11) и исправлена

**Демон стартовал в тот момент, когда комната КАРМАНА была недоступна.**

Лог `radar-intake.log`, 31.10 15:39 (старт текущего процесса):

```
15:39:17 WARNING modules.secrets_bootstrap: SETKA: vault недоступен (попытка 1/3): URLError: <urlopen error timed out>
15:39:21 WARNING modules.secrets_bootstrap: SETKA: vault недоступен (попытка 2/3): URLError: <urlopen error [Errno 111] Connection refused>
15:39:24 ERROR   modules.secrets_bootstrap: SETKA: восстановление из vault не удалось: URLError: <urlopen error [Errno 111] Connection refused>
15:39:24 INFO    radar_intake_daemon: radar intake daemon: старт (wait=25 c, ...)
15:39:27 INFO    radar_intake_daemon: tg-intake: выключен — no TELEGRAM_TOKEN for AFONYA (проверяю конфиг раз в 60 с)
```

Код был **правильный**: `bootstrap_secrets()` в демоне есть с 21.10 (`8a3297f`), и
юнит подгружает `/etc/setka/setka.env` + `/etc/setka/secrets-token.env`. Но
`bootstrap_secrets()` — best-effort: комната была недоступна, токен не приехал,
а **демон остался без него навсегда**: процесс жив, выглядит здоровым, а
`tg-intake` молча выключен («проверяю конфиг раз в 60 с» — он проверяет конфиг,
а не комнату). Ни ретрая, ни сторожа, который заметил бы «токена так и нет».

**Исправление (08.11 20:53, по решению владельца):** перезапуск демона. Комната
жива, `bootstrap_secrets()` отработал: «восстановлено секретов из vault: 10», и
через 2 секунды `tg-intake: {'ok': True, 'updates': 17, 'processed': 17, 'added': 0,
'replied': 0}` — приём каналов заработал (17 накопившихся событий обработаны).

**Профилактика (в этом же PR):** сторож `_vault_watchdog` в демоне — если токена
бота нет, комната опрашивается раз в 5 минут (`RADAR_VAULT_RETRY_SECONDS`), а
после удачной попытки словари `config.runtime` обновляются явно
(`refresh_token_globals()`): они собираются **при импорте**, а секреты из комнаты
могут приехать позже — без этого обновления они остались бы пустыми. Пока токен
есть, сетевых вызовов у сторожа нет вовсе. Тесты: `tests/test_radar/test_intake_daemon.py`
(2 кейса), `tests/test_config/test_runtime.py` (3 кейса).

⚠️ **Отдельная дыра, не закрытая этим PR:** видео-репосты идут через сырой
`requests.post` (`modules/publisher/telegram_repost.py::_send_video_multipart`) —
мимо `telegram_http`, то есть мимо relay. С бокса `api.telegram.org` недоступен,
поэтому **видео в Telegram-канал не уйдёт** (текст и фото — уходят, они идут
через `tg_http`). Заметка на будущее, отдельной правкой.

## Замер (08.11)

| Что | Факт |
|---|---|
| Частота | **349** пропусков в логе, первые — **31.10 15:39**, последний — 08.11 18:59 |
| Юнит | `radar-intake.service`: `Environment=` пуст, `EnvironmentFiles=` нет |
| Стартовая строка в логе | `radar intake daemon: старт` → `tg-intake: выключен — no TELEGRAM_TOKEN` |
| Токены ботов в приложении | лежат **только в комнате КАРМАНА** (`TELEGRAM_TOKEN_AFONYA`, `TELEGRAM_TOKEN_VALSTANBOT`), в `/etc/setka/setka.env` их нет |
| Как их получает основное приложение | `modules/secrets_bootstrap.py` тянет vault при старте (префикс `TELEGRAM_TOKEN_` в allowlist) — а радар-приёмник этот bootstrap **не вызывает** |
| Проверка на блок | не связано: блок IP Telegram чинили в P219 (08.11), радар-приёмник с тех пор работает по RSS/web-источникам |

## Почему это не «просто лог»

Репосты из радара в Telegram-канал бота AFONYA не уходят с 31.10 — то есть почти
месяц. При этом `failed: 1` в сводке доставки выглядит как обычный шум, а в
живой ленте это просто «мало постов из радара».
