# 🟡 Ссылки на источники убраны из постов — второй рубеж дедупа ослеп, нужен ключ из БД

> Запись `P206` реестра [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md). Индекс грепается, запись читается целиком, реестр целиком не читается никогда ([D-097](../../AGENTS.md)).

`⏱ 2026-10-20 · snooze 0 · fresh`

## Что случилось

Решение владельца 20.10: ссылки на пост-источник из публикаций убрать совсем, оставить только название источника строкой «Источник: …» (ADR-0011, [P183](P183-ssylki-na-istochnik-i-svoy-zagolovok.md) закрыт этим решением).

Ссылки были не только подписью. Второй рубеж дедупа —
[`extract_source_lips_from_target_group_posts`](../../modules/deduplication/bulletin_history.py) — **читает нашу стену и вынимает lip'ы источников из wall-ссылок внутри сводок**. Новые посты таких ссылок больше не содержат, значит этот слой на них находит пустое множество.

## Что осталось работать

Первый рубеж — курсор опубликованных lip'ов в БД (`published_posts` / `read_cursor`): он пишется на каждой публикации и от формата текста не зависит. То есть штатная защита «не опубликовать один пост дважды» жива.

## Чего мы лишились

Стена была **восстановительным** слоем: если курсор потерян/сброшен или пост опубликован мимо конвейера, ссылки в старых постах всё равно говорили «этот источник уже выходил». Теперь такого источника сведений нет, и после сброса курсора история начинается с нуля.

## Что сделать (варианты, по возрастанию цены)

1. Пересобирать `history_lips` не из текста стены, а из `published_posts` по региону за окно (30–60 дней) — тот же рубеж, но данные структурированные.
2. Хранить lip'ы источников в `published_posts.source_lips` (jsonb) при публикации и читать их напрямую.
3. Оставить как есть, если замер покажет, что сбросов курсора не бывает (тогда слой был ритуальным).

Проверить перед работой: есть ли в `published_posts` привязка «публикация → lip'ы включённых постов» (`post_lips`/аналог). Если есть — вариант 1 стоит одной функции чтения и не требует миграции.
