# P256 — Остановка задачи планировщика не останавливает приложение: рестарт юнитов размножал их

**Приоритет:** 🟡 техдолг (процедура перезапуска в репозитории отсутствовала; теперь есть, но привычка «Stop → Start» всё ещё размножает юниты)
**Открыто:** 2026-11-26 · `⏱ 2026-11-26 · snooze 0 · fresh`

## Симптом

26.11 владелец перезапустил юниты стенда штатной командой — и вместо замены
процессов **получил вторые**:

```powershell
Stop-ScheduledTask -TaskName setka-celery-worker
Stop-ScheduledTask -TaskName setka-celery-worker-wave
Start-ScheduledTask -TaskName setka-celery-worker
Start-ScheduledTask -TaskName setka-celery-worker-wave
```

После этого на каждую очередь висело **по два** воркера: старый (09:58:43,
поднятый до смержей PR #1297 и PR #1306) и новый (22:40). Работу делали
**старые** — то есть правки в бою не работали, а диагностика P253 не
появлялась. Тот же механизм к вечеру дал **11 экземпляров веба** (22 процесса,
P255).

## Механизм (замер, не версия)

Задача планировщика поднимает цепочку:

```
wscript.exe → cmd.exe → powershell.exe (-Foreground) → python.exe (venv) → python.exe (базовый)
```

`Stop-ScheduledTask` снимает **верхушку** цепочки (wscript/cmd/powershell).
Процесс `python` переживает остановку и остаётся сиротой: он продолжает
держать порт 8000 (веб) или забирать задачи из очереди (воркер). Следующий
`Start-ScheduledTask` поднимает **второй** экземпляр рядом с первым.

Это уже было описано в коде — но только для веба
(`infra/windows/common.ps1:75-79`: «остановка задачи убивает обёртку, но не
сам python — процесс-сирота остаётся держать порт») и не было оформлено как
процедура: шаги «снять процессы» лежали только в теле P255 и в будильнике
как ручной рецепт владельца.

Живой замер 26.11 23:05–23:08:

| что | факт |
|---|---|
| воркеров на очередь `celery` | 2 процесса (09:58:43 и 22:40:06) |
| воркеров на очередь `wave,digest` | 2 процесса (09:58:44 и 22:40:08) |
| после `Stop-ScheduledTask` | **все 8 процессов выжили**, задачи перешли в `Ready` |
| код, который работал | старый (до PR #1297/#1306): в трейсе `celery_asyncio.py, line 59` — в текущем файле `run_until_complete` на строке 138 |
| диагностика PR #1306 в логе | 0 строк `run_coro: общий event-loop занят другим потоком` |
| экземпляров веба к 20:36 | 11 (22 процесса) |

## Побочный эффект жёсткой остановки: задачи висят в `unacked`

Остановка воркера — жёсткая (`Stop-Process`), а сообщение из очереди
подтверждается (ack) после выполнения. Убитый воркер не успевает подтвердить
то, что забрал, и сообщение остаётся в хеше `unacked` — **в очереди его уже
нет**. Компоновщик (kombu) возвращает такие сообщения сам, но по таймауту
видимости и только для доставок **своего** потребителя; доставки погибшего
воркера не принадлежат никому.

Живой замер 26.11 23:08–00:27 (ночной сторож, срез каждые 5 минут):

| что | факт |
|---|---|
| сообщений в `unacked` | **64** — 58 задач веера сводки + 6 задач волны |
| сроки возврата (ZSET `unacked_index`) | 22:12–23:07 — все прошли |
| очередь `digest` | **0** всё время |
| сборников у регионов | 22 из 84 — не изменилось с 23:06 |
| вызовов движка после рестарта | **0** (последний — 23:07, от старого воркера) |
| P253-диагностика | 0 (коллизии нет: держателя петли — задачи сводки — тоже нет) |

То есть **хвост веера не вернулся сам за час** и без ручного возврата 62
региона не получат вечерний сборник. Инструмент возврата — в репозитории:
[`scripts/restore_unacked.py`](../../scripts/restore_unacked.py) (тот же
механизм, что у компоновщика: `QoS.restore_by_tag`). По умолчанию — сухой
прогон; запись в очередь — только с `--apply`.

## 27.11 06:40 — задачи сводки протухли, возврат потребовал продления срока

У задачи веера есть **срок**: `expires = countdown + 4 ч`
(`DIGEST_TASK_EXPIRES_SEC`). Хвост, провисевший в `unacked` дольше этого
срока, **протух**: вернуть его в очередь как есть — значит отбросить его как
просроченный («Discarding revoked task»), то есть не сделать ничего.

Живой замер 06:40 — все 58 задач сводки с истечением **02:07–02:21 MSK**,
то есть протухли за четыре часа до этого. Возврат без правки срока был бы
пустым делом.

Инструмент поэтому умеет:
* показывать состояние срока по каждой задаче (сухой прогон: «жива» /
  «протухла») — чтобы решение принималось по факту, а не по надежде;
* `--refresh-expiry` — продлить срок протухшим задачам (`--expiry-ttl`, по
  умолчанию 4 ч, как у веера);
* `--eta-in` — сдвинуть «срок наступления», чтобы задачи не начали бить все
  разом.

**Возврат выполнен 27.11 06:45** (решение владельца): 58 задач сводки
возвращены в очередь `digest` со сроком +4 ч и началом через 15 минут. Очередь
после возврата: `digest` — 35, `unacked` — 81 (остались только живые
ETA-задачи волны, которые держит воркер, — это норма).

⚠️ **Найденный при этом баг инструмента:** `channel._qos` у канала пуст
(`None`) до первого потребителя — QoS создаётся ленивым свойством
`channel.qos`. С `--apply` инструмент падал с `AttributeError`, и сухой
прогон это скрывал: он брокера не трогает. Исправлено.

## 27.11 06:44 — возврат прошёл, а задачи отбросились как просроченные

**Хвост веера за 26.11 потерян.** Разбор по шагам:

1. Возврат отработал: 58 задач ушли в очередь `digest`, воркер их забрал
   (06:44:26) — и **сразу отбросил**: «Discarding revoked task:
   publish_daily_digest_region[…]». Для celery это `expired`.
2. Причина — **правка срока не дошла до брокера.** `restore_by_tag` читает тело
   сообщения **из хеша `unacked` заново** (а не из того объекта, который мы
   разобрали и изменили), поэтому обновлённый `expires` остался в памяти
   инструмента, а в очередь ушла задача со **старым** сроком — 02:07–02:21.
3. Восстановить было уже нечего: задачи забраны из очереди и отброшены.

**Исправление:** обновлённое тело пишется обратно в хеш `unacked` перед
возвратом (`write_back`), плюс `--only-expired` (вернуть только протухшие, живые
не трогать — их и так ждёт брокер) и отчёт о сроке в сухом прогоне.

**Живая проверка исправления (07:22):** 6 протухших волновых задач
возвращены со сроком +4 ч — воркер их **выполнил** (06:58–06:59), а не
отбросил. Прежний путь давал «Discarding revoked task».

**Решение по потерянному хвосту:** переиздавать не будем. Сборник не несёт
даты (заголовок «Короткой строкой») и по замыслу это **последний пост дня** —
утренняя публикация вчерашнего вечернего сборника читателю ничего не
объясняет. Свежий сборник за 27.11 выйдет в 21:40 всем 84 регионам. Разрыв
за 26.11 (сборник не вышел у 62 регионов) зафиксирован здесь.

## Что ещё в записи

- **Логи обнуляются на каждом старте** (`Start-Process -RedirectStandardError`
  создаёт файл заново) — прошлая ошибка стирается. Отдельно: после рестарта
  в 22:40 старый воркер продолжил писать в свой файл со старого смещения —
  в `logs/setka-wave-worker.err.log` образовался NUL-разрыв, и чтение такого
  лога даёт дыру в середине ночи (усиливает P254).
- **Веб-логи тоже обнуляются** — «address already in use» не остался ни
  разу, поэтому полная картина шторма собиралась только по косвенным
  признакам (P255).
- **Процедура не вписана в будильник** — рестарт до сих пор делается руками
  владельцем, и «Stop → Start» без шага «снять процессы» снова размножит
  юниты.
