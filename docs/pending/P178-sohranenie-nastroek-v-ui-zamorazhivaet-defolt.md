# 🟡 Сохранение настроек в UI замораживает дефолт: правка кода молча не доезжает до района (найдено 2026-09-22)

> Запись `P178` реестра [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md). Индекс грепается, запись читается целиком, реестр целиком не читается никогда ([D-097](../../AGENTS.md)).

`⏱ 2026-09-22 · snooze 0 · fresh · КОД ГОТОВ 29.09 (ветка fix/sparse-bulletin-filters): PUT пишет только отличия от DEFAULT_PIPELINE (_sparse_bulletin_filters), GET/превью по-прежнему слитые; ДАННЫЕ — ход владельца: mi/vp/bal/kukmor снова заморожены (сохранение UI после 22.09, уже без max_post_age_hours, но с остальными пятью ключами) — чистить тем же #-приёмом`

## Как нашлось

Выкат решения владельца 22.09 «устаревание поста — сутки». Перед правкой дефолта проверили,
нет ли у районов собственного значения:

```sql
SELECT region_code, bulletin_filters::text
FROM region_configs
WHERE bulletin_filters::text LIKE '%max_post_age%';
```

Нашлись **четыре**: `mi`, `vp`, `bal`, `kukmor` — и у всех четырёх записано
`"max_post_age_hours": 72`.

## Механизм

Сохранение настроек фильтрации из UI идёт через
[`web/api/filtration._normalize_bulletin_filters`](../../web/api/filtration.py):

```python
defaults = {**DEFAULT_PIPELINE, **(data.get("defaults") or {})}
```

То есть в БД пишется **весь блок дефолтов целиком**, а не только то, что оператор
действительно менял. Значение, которое на момент сохранения было дефолтом кода, становится
собственной настройкой района. Дальше
[`get_effective_pipeline_settings`](../../modules/bulletin_pipeline_settings.py) честно
отдаёт приоритет записанному — и правка `DEFAULT_PIPELINE` до этого района **не доезжает
никогда**, без единой строки в логе.

Признак того, что 72 у этих четырёх — не решение оператора, а слепок: рядом в том же блоке
лежит `"max_posts_per_bulletin": 1`, то есть строки переписаны около 19.09, когда владелец
переключил сеть на одиночные посты (P168). Оператор менял не возраст.

## Чем это опасно шире одного случая

Класс отказа тот же, что у трёх приборов 22.09: **всё зелёное, никто не ошибся, а работа не
сделана**. Дефолт правится в коде, тесты на дефолт зелёные, выкат прошёл — и часть сети живёт
по-старому. Чем дольше проект существует, тем больше районов оператор успел открыть в UI, то
есть **тем меньше сила любого дефолта**, и заметить это можно только запросом в БД.

Под тем же механизмом лежат и остальные ключи блока: `max_posts_per_bulletin`,
`posts_per_community_fetch`, `text_similarity_threshold`, оба `min_rafinad_len_*`.

## Что сделать (два разных хода)

**1. Данные — ход владельца, гейт #025.** Снять закрепление у четырёх районов, чтобы решение
про сутки применилось ко всей сети:

```sql
UPDATE region_configs
SET bulletin_filters = jsonb_set(
        bulletin_filters::jsonb, '{defaults,max_post_age_hours}', '24'
    )::json
WHERE region_code IN ('mi', 'vp', 'bal', 'kukmor');
```

Альтернатива — удалить ключ вовсе (`#-` вместо `jsonb_set`), тогда район будет следовать
дефолту кода и дальше. Это предпочтительнее по смыслу, но меняет поведение «настройка
сохранена» в UI, поэтому решение тоже за владельцем.

**2. Код — отдельная правка, не бандлить.** Писать в БД только то, что ОТЛИЧАЕТСЯ от
`DEFAULT_PIPELINE`, а на чтение по-прежнему отдавать слитый блок (UI показывает эффективные
значения, поведение для оператора не меняется). Проверено: прямых читателей
`bulletin_filters["defaults"]` в обход `get_effective_pipeline_settings` нет, так что разрежённая
запись безопасна. Не сделано в PR про сутки сознательно — один PR решает одну задачу, а у этой
правки своя цена (round-trip UI) и свой гейт.

## Чем проверить

Тот же запрос из шапки: после решения владельца в выдаче не должно остаться `72`. Тест
[`tests/test_bulletin_pipeline_settings.py::test_stored_region_value_still_wins_over_the_code_default`](../../tests/test_bulletin_pipeline_settings.py)
фиксирует само поведение, чтобы оно не выглядело случайностью.


## Сделано 2026-09-22

Владелец выбрал «убрать ключ совсем»:

```sql
UPDATE region_configs
SET bulletin_filters = (bulletin_filters::jsonb #- '{defaults,max_post_age_hours}')::json
WHERE region_code IN ('mi', 'vp', 'bal', 'kukmor');
```

`UPDATE 4`, проверка после — у всех четырёх ключа нет, по сети закреплённых районов **0**.
Теперь все 57 регионов следуют дефолту кода, и следующая его правка доедет до всех.

**Открытым остаётся код-лекарство** из раздела выше: пока `_normalize_bulletin_filters` пишет
в БД весь блок defaults, первое же сохранение настроек района в UI закрепит текущие значения
заново — и ловушка вернётся, только уже на других районах и других ключах.
