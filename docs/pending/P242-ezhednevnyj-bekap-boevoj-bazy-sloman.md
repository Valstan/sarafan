# P242 — Штатный ежедневный бэкап боевой базы падает и оставляет пустые файлы

**Приоритет:** 🔴 блокер (у боевой базы нет работающего бэкапа)
**Открыто:** 2026-11-26 · `⏱ 2026-11-26 · snooze 0 · fresh`

## Состояние на 26.11.2026 — боевой база теперь локальная, бэкап у неё ботает

После переезда (26.11) боевой база живёт на локальной машине, и бэкап у неё
**работает**: задача планировщика `sarafan-db-backup` (03:00, скрипт
`infra/windows/backup_db.ps1`), первый дамп снят 26.11 — 296 МБ за 66 с,
каталог вне репозитория. Поломка этого пункта — в bash-скрипте **бокса**
(`scripts/backup_database.sh`, ошибка awk на разборе `DATABASE_URL`), и бокс
уходит (P249).

**Запись parked:** пока бокс существует, его cron продолжает писать пустые
файлы. Условие расконсервации: **бокс удалён у хостера (P249)** → закрыть.

## Симптом

`scripts/backup_database.sh` (запускается на боевом боксе по cron ежедневно в
03:00) падает **до** `pg_dump`:

```
awk: cmd. line:1: BEGIN{FS=\"=\"} $1==\"DATABASE_URL\"{sub(/^DATABASE_URL=/, \"\"); print; exit}
awk: cmd. line:1:          ^ backslash not last character on line
```

Скрипт идёт с `set -euo pipefail`, поэтому падает и не создаёт дамп. В
каталоге бэкапов приложения лежат **файлы по нулям** — последний непустой
дамп датирован началом января, то есть **ежедневного бэкапа боевой базы
фактически нет уже несколько месяцев**.

Проверено 26.11.2026 чтением каталога бэкапов и журнала `logs/backup.log` на
боевом боксе.

## Причина

В `awk`-программе внутри **одинарных** кавычек bash остались экранированные
кавычки:

```bash
sudo -n awk 'BEGIN{FS=\"=\"} $1==\"DATABASE_URL\"{...}' "$ENV_FILE"
```

В одинарных кавычках `\` не экранируется, поэтому awk получает `\"` и
спотыкается. В двойных кавычках bash (или в heredoc) экранирование сработало
бы — но здесь кавычки одинарные.

## Что сделано в рамках переезда

* Снят **правильный** дамп боевой базы (297 МБ, формат custom) скриптом
  `infra/windows/prod_dump.sh` — там разбор env-файла сделан без
  экранированных кавычек.
* Перенос базы на локальную машину выполнен именно этим дампом; счётчики
  сверены построчно.
* **26.11.2026 — корень починен в репозитории** (`scripts/backup_database.sh`):
  * `awk`-строка разбора `DATABASE_URL` переписана в ту же форму, что у
    соседней строки `AD_UPLOAD_DIR` (где awk работает) — без `\"` внутри
    одинарных кавычек;
  * дамп пишется **во временный файл** и переносится на место только после
    проверки размера (раньше перенаправление `>` создавало целевой файл до
    `pg_dump`, и упавший дамп оставался файлом нулевого размера — «бэкапом»,
    который ничего не значил);
  * нулевые хвосты (`setka_backup_*.sql` размером 0 байт — 84 штуки с
    октября) чистятся **самим скриптом** с записью в журнал, что именно
    убрано.
* **На боевой боксе скрипт ещё не выкачен** — до этого пункт не закрыт.

## Что нужно сделать (владелец или владелец репозитория `scripts/`)

Правка **однострочная** — убрать `\"` внутри одинарных кавычек:

```bash
DATABASE_URL="$(sudo -n awk -F= '$1=="DATABASE_URL"{sub(/^DATABASE_URL=/, ""); print; exit}' "$ENV_FILE")"
```

После правки:

1. Прогнать `scripts/backup_database.sh` вручную на боевом боксе.
2. Убедиться, что файл **не пустой** (`ls -l`), и что `pg_restore --list`
   его читает.
3. Проверить, что cron больше не кладёт пустые файлы (в журнале нет строки
   «awk: cmd. line»).
4. Разобрать накопившиеся пустые файлы в каталоге бэкапов (удаление — с
   подтверждением владельца, это прод).

**Почему это отдельная запись, а не «починил по ходу».** Файл `scripts/` в
рамках заявки на переезд **не моя территория**, а правка боевого скрипта —
это изменение прод-контура, которое требует гейта #025. Правка самого
файла — вопрос владельца репозитория.

## Граница

* Пока скрипт не починен, **не считать бэкапы рабочими**: наличие файла в
  каталоге бэкапов ничего не значит, если он нулевой.
* Дамп, снятый для переезда, лежит отдельно и в перечень ежедневных не
  входит.
