Три района закрывают две дыры сети: **северо-восток** (Агрызский + Актанышский, оба висят

## Что не сделано и почему

- **Публикация идёт только в одну группу из трёх** (`published_posts` за 20.11: agryzsky — 9,
  aktanyshsky — 0, yutazinsky — 0). Разбор по логу воркера (`logs/celery-worker.log`):
  - **`agryzsky` — работает.** `novost` 20:42: `отобрано=5`, `publication journal: записано 1 постов
    (вид=regular)` + `вид=headliner`; `korotko/digest` 22:07 — 5 пунктов.
  - **`aktanyshsky` — отбор пуст.** `novost` 20:43: `collected=272 kept=0 records=38 added=38` —
    все посты отсеяны ещё на сборе (content-drops), до нейро-фильтра не доходит; `admin` (23:09) и
    `sport` (23:12): `kept` 3 и 0 — ниже порога 5, политика `skip-wave`. Это **не ключ и не
    оформление**, а региональный фильтр: пул Актаныша не проходит под свой район.
    ✅ **Разобрано 21.11 (см. ADR-0018).** Причина «порог 5 → skip-wave → публикаций 0»
    оказалась общей поломкой контура, а не особенностью Актаныша: модель при кандидатах
    меньше порога **не зовётся**, а отбор принимал отсутствие вердиктов за молчание
    движка и вычитал волну целиком. Исправлено (prepublish отдаёт состояние движка,
    политика деградации срабатывает только на реальном отказе).
    ✅ **И «отдельный вопрос» (`kept=0` на сборе) закрыт — замером, а не догадкой.**
    Волны Актаныша за 21.11: `06:41 novost collected=272 kept=0` (пул реально пуст — 234
    поста старше 24 ч, 38 дублей аудита), `07:23 kultura kept=2`, `13:31 detsad kept=3` —
    все три уходили в `skip-wave` из-за невызванного движка; `16:42 novost kept=2` — та же
    волна уже на новом коде: `движка не звали … волна идёт по обычным фильтрам` →
    **публикация есть**. То есть `kept=0` в 06:41 — не поломка фильтра, а реально пустой
    час пула (доноры Актаныша пишут редко), и раньше он стоил СУТОК тишины. С шестью
    слотами `novost` пустой час больше ничего не стоит: материал ловит следующий слот.

## Уроки

- **Счёт районов по базе против Википедии сходится только с поправкой на упразднённые.**
  В сети было 37 активных районов Татарстана (после активации порции — 40), а в Википедии
  43 района — разница не «шесть
  неразобранных», а пять (43 − 37) + Тукаевский, который пропущен сознательно. Проверка
  по коду `bal` показала: это **Балтасинский** район (Балтаси), а не Балтинский —
  Балтинского в списке 43 уже нет (упразднён), и без сверки «Балтасинский» легко принять
  за ещё один неразобранный район.
- **Границы районов Татарстана не всегда симметричны в статьях.** Агрызский в Википедии
  описан как сосед Мензелинского/Тукаевского/Менделеевского «по акватории
  Нижнекамского водохранилища» — это ребро засчитывается, но формально это граница по воде,
  а не по суше.
- **Код района не читается по префиксу: `bal` — это Балтасинский (Балтаси), а не
  Балтинский.** Балтинского района в списке 43 уже нет (упразднён), и без сверки по
  названию группы легко принять Балтасинский за «ещё один неразобранный район» и выкинуть
  его из кандидатов на порцию. Смотреть надо `regions.name` / `region_config`, а не код.
- **`groups.edit` в API мёртв для пользовательского токена, но жив для community-ключа.**
  `[3] Unknown method passed` — только на user-токене (проверено 20.11 на 5.103/5.131/5.199, и
  через `vk_api`, и сырым HTTP). Community-ключом работают **и `description`, и `city`** ⇒
  описание и город ставятся скриптом, а `screen_name` (короткий адрес) — наоборот, только
  user-токеном ⇒ короткий адрес только руками в браузере. Урок: различать **тип токена**, а не
  «API-метод сломан».
- **Короткий адрес не ставится группе без тематики.** У `leninogorsky` и `bugulminsky` activity
  «Публичная страница», поле «Тематика» пустое, и ВК отклоняет сохранение **целого блока**
  «Основная информация». Единственный путь — пересоздать группу с тематикой
  «Городское сообщество» (необратимо: старый `vk_group_id` умирает, нужен новый COMM-ключ).
- **`--repair` нельзя запускать раньше `--apply` по новым группам.** Repair ставит аватар
  user-токеном, после чего группа перестаёт быть «голой» и full-режим `--apply` (описание +
  обложка + визитка + закреп) больше не срабатывает.
- **Стена и предложка правятся на старой странице `?act=sections`,** а не через «Контент» →
  «Посты» → «Настроить»: клик там попадает в переключатель показа раздела и **выключает** его.
- **Ранг мест ждёт постов:** `--rank-localities --apply` на новых районах записал 0 рангов —
  у них ещё нет собранных постов.
- **Значение ключа читать из DOM, а не из `inspect`.** `inspect` отдаёт текст поля обрезанным
  (100 символов), и такой токен уходит в БД битым: `[5] User authorization failed: invalid
  access_token`. Рабочий путь — `query(kind="dom", selector='input[value*="vk1"]')`: там
  `value`-атрибут целиком (220 символов).
- **Передача файла на прод — через base64, а не конвейером PowerShell.** `Get-Content -Raw | ssh`
  дописывает `\r\n` и ломает байты: токен приезжал длиной 222 вместо 220 и не проходил
  валидацию. Надёжно — `[Convert]::ToBase64String(...)` + `printf %s <base64> | base64 -d`.
- **`groups.edit` принимает параметр `city` (строка), а не `city_id`.** С `city_id` вызов
  проходит без ошибки, но город не меняется — молчаливый no-op. Проверять город чтением
  `groups.getById(fields="city")` сразу после записи.
- **Push-подтверждение ВК живёт около 10 минут.** Несколько запросов подряд (в разных
  вкладках) истекают молча — страница просто возвращается к пустому списку ключей. Рабочий
  режим: один ключ за раз, сразу читать значение после подтверждения. — опции выпадающего списка
  тематик не имеют `ref`, и `query(kind=semantic)` их не находит. Рабочий путь: клик по
  координате, посчитанной из скриншота (масштаб кадра 1:1 к CSS-пикселям), плюс проверка
  скриншотом. `run_script` в этом провайдере выполняется, но **вывода не возвращает** —
  читать DOM через него бесполезно.
- **PowerShell 5.1 портит кавычки в аргументах `ssh`** — `-c "SELECT …"` теряет кавычки и
  доходит до bash как голые слова. Рабочие формы: `sudo -u postgres psql -d setka -f file.sql`
  и короткие команды без кавычек; всё сложное — через файл-обёртку на `/tmp`.
- **Хост-гейт режет не всё подряд:** работает полная форма
  `sudo bash -c 'set -a; . /etc/setka/setka.env; set +a; cd /home/valstan/SETKA && exec ./venv/bin/python …'`
  — так отработали `activate_regions.py --apply` и `setup_groups.py --audit/--apply`. Форма
  `sudo bash <скрипт>` без `-c` режется («cannot prompt for permission»), а
  `sudo -u postgres psql -f` с `SELECT` — проходит. Проверять форму команды, а не права на сервере.
