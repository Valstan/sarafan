# P211 — `os.kill(pid, 0)` на Windows УБИВАЕТ процесс: проверка живости неверна, а тесты падали молча

> Запись `P211` реестра [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md). Индекс грепается, запись читается целиком, реестр целиком не читается никогда ([D-097](../../AGENTS.md)).

**Статус:** ⏱ 2026-11-01 · snooze 0 · fresh · **закрыто в этой сессии** (правка + регрессия-тест, PR #1000)

## Что было

`monitoring/metrics.py::_default_pid_alive(pid)` спрашивал «жив ли процесс» через
`os.kill(pid, 0)`. Это POSIX-привычка: `kill -0` шлёт нулевой сигнал — проверка
без последствий.

**На Windows `os.kill(pid, 0)` — это `TerminateProcess(pid, 0)`, то есть
УБИЙСТВО.** Ноль тут не «сигнал ноль», а код завершения.

## Как это выглядело

Полный прогон тестов на этой машине молча обрывался на ~59 % — **без единого
сообщения, без traceback**, код возврата 1. CI этого не видит: он гоняется на
`ubuntu-latest` (`.github/workflows/ci.yml:11`), где `kill -0` — действительно
проверка.

Поймано 01.11, при попытке прогнать гейт перед мержем D-096:

```
tests\test_monitoring\test_multiproc_prune.py [100%]   ← на этом файле прогон умирал
```

Файл проходил по отдельности с `--co` (сбор) и падал при выполнении. Сузил
бисекцией до одного теста: `test_default_pid_helpers_behave` зовёт
`m._default_pid_alive(os.getpid())` — то есть **проверяет живость самого
pytest и убивает его**.

Проба, подтвердившая механизм (`probe_kill.py`, 01.11):

```python
os.kill(os.getpid(), 0)
print("AFTER kill — процесс выжил")   # ← до этой строки процесс не доходит
```

Файл с выводом писался **до** вызова `os.kill` и содержал обе строки, а
`print` после — уже нет: процесс умер между ними. Проверено и на дочернем
процессе.

## Что задевало не только тесты

`_default_pid_alive` и `_default_pid_cmdline` — не только тестовые помощники:
ими пользуется `prune_stale_multiproc_files`, который вызывается **при старте
web-приложения** (`monitoring/metrics.py`, чистка multiproc-сирот, PR #866).

На Windows это значило: чистка метрик на старте **убивала процессы, которые
считала живыми**, а проверка «наш ли это процесс» не работала вовсе — `/proc`
в Windows не существует, `_default_pid_cmdline` честно возвращала пустую
строку, а пустая cmdline не содержит ни одного из наших маркеров
(`SETKA`, `setka`, `uvicorn`, `celery`) → живой процесс читался как чужой, и его
файл multiproc-метрик сносился как сирота.

Прод — Linux, там обе функции корректны; поэтому баг жил незамеченным и не
проявлялся на бою.

## Правка

`monitoring/metrics.py`: на Windows спрашиваем `psutil` (уже зависимость
проекта, `requirements.txt:42`) вместо `os.kill`; на POSIX поведение не
трогаем — `kill -0` там честная проверка.

```python
if os.name == "nt":
    try:
        import psutil
        return psutil.pid_exists(pid)
    except Exception:
        return False
```

`_default_pid_cmdline` на Windows берёт команду из `psutil.Process(pid).cmdline()`
— иначе живой процесс читался бы как чужой (см. выше).

## Тест

`tests/test_monitoring/test_multiproc_prune.py`:
- утверждение про `/proc` заменено на платформенное («команда своего процесса
  доступна: на POSIX из `/proc`, на Windows из `psutil`»);
- добавлен `test_pid_alive_does_not_kill_the_calling_process` — регрессия на
  саму ловушку: тест зовёт проверку живости на собственном PID, и если
  реализация убьёт процесс, тест просто не завершится.

## Переносимо?

**Да** — ровно тот класс, что brain просит присылать: «способ проверки живости
процесса через `kill -0` убивает процесс на Windows; на Windows нужен
`psutil.pid_exists`». Любой проект с multiproc-метриками, стартовой чисткой
каталога или health-check'ом по PID на этой платформе ловит то же самое — и
ловит **молча**, потому что умирает не тест, а интерпретатор.

## Чего НЕ делал

- Не трогал POSIX-ветку: `kill -0` там корректен, менять — риск без выгоды.
- Не менял семантику `prune_stale_multiproc_files`: двойная проверка
  (PID жив **и** cmdline наш) — правильная, она и ловит чужие PID.
- Не откатывал ADR-0006/PR #866: они правы, ломало их окружение.
