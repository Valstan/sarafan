# 🔴 Процессы MiniMax CLI переживают рестарт юнита — и это выглядит как новые отказы

> Запись `P240` реестра [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md). Индекс грепается,
> запись читается целиком, реестр целиком не читается никогда ([D-097](../../AGENTS.md)).

`⏱ 2026-11-25 · snooze 0 · fresh · найдено разбором таймлайна ядерных убийств 25.11 12:45:
после рестарта воркеров (08:12:52–08:12:56) ядро сняло ещё 26 процессов minimax-code
(08:13:25–08:30:36), хотя все вызовы движка в этом окне прошли успешно`

## Состояние на 26.11.2026 — на Linux починено, разрыв Windows вынесен в P250

Linux-решатель на месте (`modules/minimax_cli_reap.py`, PR #1276) и на боксе
работал. На локальной машине он **не работает**: он Linux-only — читает
`/proc/*/status` и ищет процессы с `PPid = 1`, а в Windows родитель умершего
процесса не становится «единицей».

Разбор вынесен в
[P250](P250-sbor-osirotevshih-cli-ne-rabotaet-na-windows.md): там и замер
состояния машины, и маркер для порта (`--output-last-message` есть только у
вызовов движка — у интерактивных сессий агента его нет), и альтернатива через
Job Object с `KILL_ON_JOB_CLOSE`.

**Запись parked:** часть про бокс снимается с его удалением (P249).

Рестарт Celery-воркера **не убирает уже поднятые процессы MiniMax CLI**. На боксе с 1536 МБ
и swap = 0 такой осиротевший процесс ест 200–260 МБ ещё минут 18 после рестарта, а потом его
снимает ядро.

Последствие — **ложная тревога в логах**: рядом с успешными вызовами движка идут ядерные
убийства, и по журналу расхода вызовов не видно, кто именно умер. В записи
[P239](P239-minimax-cli-pamyat-i-platnyj-dipisk.md) это выглядело как «процессы поднимаются в
обход слота» — а на деле это были **процессы, пережившие рестарт**.

## Доказательства (прод, 25.11)

| Что | Факт |
|---|---|
| Убитые PID | **781302…781875** — все 35 |
| Старые воркеры | остановлены 08:12:52–08:12:56, PID **778944/778952** |
| Новый воркер | создан 08:12:56, PID **782045** (fork-ребёнок **782052**) |
| Вывод по PID | Linux выдаёт PID по возрастанию ⇒ **все убитые процессы созданы ДО 08:12:56** — они пережили рестарт |
| `KillMode` юнитов | `control-group`, `TimeoutStopUSec=1min 30s`, `SendSIGKILL=yes` ⇒ SIGTERM в 08:12:52, SIGKILL в 08:14:22 |
| Противоречие | пережить SIGKILL в своей группе нельзя ⇒ **убитые были вне cgroup воркеров** |
| Движок в этом окне | 08:13–08:31 — **все вызовы успешны** (журнал расхода), отказов 0 |
| Раннее окно | 08:00–08:12 — 13 вызовов, **все `exec_failed`** (шторм повторов старого кода) |

**Живой замер 25.11 13:40–13:45 — причина найдена (и гипотеза про cgroup опровергнута).**
Пойман естественный вызов движка (без собственного запуска CLI) — четыре процесса подряд,
все как дочерние fork-ребёнка волнового воркера:

| Что смотрели | Факт |
|---|---|
| cgroup живого `minimax-code` | **`/system.slice/setka-celery-worker-wave.service`** — тот же, что у воркера |
| потомки (`/proc/<pid>/task/*/children`) | **пусто** — CLI не порождает ни одного процесса |
| новые transient-юниты | **не создаются** (в `/run/systemd/transient/` только два юнита от 13–14.11) |
| `SigIgn` | `0x0000000080001000` — SIGTERM **не** проигнорирован |
| `SigCgt` | `0x000000017380ee37` — бит сигнала 15 (SIGTERM) **пойман** ⇒ есть обработчик |

**Причина: CLI перехватывает SIGTERM.** `systemctl restart` шлёт SIGTERM всей cgroup — CLI его
обрабатывает и **не умирает**, а родитель (fork-ребёнок воркера) уходит ⇒ CLI остаётся
сиротой (`PPid` = 1), продолжает расти (187 → 291 МБ RSS) и живёт ещё ~18 минут, пока его
не снимет ядро. Никакого «ухода из cgroup» нет — просто **мягкая остановка не работает для
этого процесса**. Побочный вывод: `KillMode=control-group` тут не при чём — он и не срабатывал,
потому что процесс переживал и сам уборку, и SIGKILL в общем потоке уборки не было.

**Что ещё исключено живым замером:** отдельный «путь в обход слота» (в репозитории
единственная точка запуска CLI — `modules/minimax_engine.py`, `subprocess.run` внутри
`lease()`), сторож `check_minimax_engine_heartbeat` (только читает журнал), cron и
systemd-юниты на боксе (не запускают `mcode`). Два транзиентных юнита `run-u4711`/`run-u5141`
в корне — от 13–14.11, старые.

**Чего в коде нет:** в репозитории **единственная** точка запуска CLI —
[`modules/minimax_engine.py`](../modules/minimax_engine.py), `subprocess.run` внутри `lease()`
(строка 1412). Сторож `check_minimax_engine_heartbeat` только читает журнал. На боксе нет ни
cron, ни systemd-юнитов, запускающих `mcode` (два транзиентных юнита `run-u4711`/`run-u5141`
в корне — от 13–14.11, старые).

## Чем это вредно

1. **Ложные отказы в логах.** Ядро снимает процесс, которого уже никто не ждёт, а рядом идут
   успешные вызовы. Читатель логов делает вывод «движок отказывает» — и ищет несуществующую
   причину (так и вышло в P239).
2. **Съеденная память после каждого рестарта.** На боксе в 1536 МБ каждый выживший CLI — это
   200–260 МБ поверх базы ~1000 МБ. Рестарт воркера в разгар ночи/утренней волны — худшее
   время для этого.
3. **Счётчики врут.** `dmesg` показывает окно, а не сутки, и буфер чистится — см. методическую
   поправку в [P239](P239-minimax-cli-pamyat-i-platnyj-dipisk.md).

## Что сделано (25.11)

**Новый модуль [`modules/minimax_cli_reap.py`](../../modules/minimax_cli_reap.py)** — убирает
**только осиротевшие** процессы CLI: те, у кого `comm` = `minimax-code` **и** `PPid` = 1
(родитель умер ⇒ процесс переподобран init'ом). Живой CLI чужого воркера не трогаем никогда:
его родитель — fork-ребёнок воркера, а не init. Сигнал — **SIGKILL** (SIGTERM CLI
перехватывает, «мягко» он не выйдет).

Вызывается в двух местах:

- **перед каждым запуском CLI** в [`modules/minimax_engine.py`](../../modules/minimax_engine.py)
  (рядом с проверкой ёмкости) — сирота снимается в первую же секунду после появления;
- **на старте воркера** ([`tasks/celery_app.py`](../../tasks/celery_app.py), сигнал
  `worker_ready`) — сироты появляются **из-за** рестарта, значит убирать их надо в момент
  подъёма нового воркера, даже если вызовов пока нет.

**Проверено живьём на боксе** (25.11 13:45): три подставных процесса с тем же `comm` и
`PPid` = 1 сняты, а **живой CLI движка (PPid = fork-ребёнок воркера) не тронут** — он
продолжил работу. Проверено и на живом `/proc` бокса, и 11 тестами
(`tests/test_classifier/test_minimax_cli_reap.py`).

**Что это даёт:** после каждого деплоя/рестарта сироты снимаются за секунды, а не живут
18 минут, съедая по 250–290 МБ на боксе с 1536 МБ и заканчиваясь ядерными убийствами,
которые в логах читаются как «новые отказы движка».

## Живая проверка после выката (25.11 15:34) — уборщик нашёл дыру в себе

Первая выкатка (PR #1273 → `6718703c`, рестарт воркеров 14:0x) показала, что **уборщик стоял
не там**: вызов уборки был **после** проверки слота, а при отказе слота функция возвращалась
раньше — то есть на голодном боксе (слот отказывает по `insufficient_memory`) уборка **не
выполнялась вовсе**. Именно тогда сироты и вредны.

Как это выглядело на живом боксе:

- **15:34:23** — ядерное убийство `minimax-code` (PID 796942, anon-rss 249 МБ) **после**
  выката, и **ни одной строки** об этом в логах воркеров ⇒ убит процесс, у которого не
  было родителя (логировать было некому);
- **36 платных вызовов DeepSeek** подряд (19 `post_rewrite` + 17 `headless`) с 14:00 —
  слот отказывал из-за нехватки памяти (available ~150 МБ при живом CLI на 278 МБ), то
  есть уборка не шла именно тогда, когда была нужна;
- сирот в моменте замера — 0 (их успела снять либо память, либо ядро).

**Починка (PR #1276):** вызов уборки перенесён **перед** проверкой слота — теперь сироты
снимаются при **каждой попытке** вызова, включая отказанную. Закреплено тестом
`test_reaper_runs_even_when_slot_refuses` (уборка выполняется, когда слот отказал).

**Отдельно — что этим НЕ решается.** Память бокса (1536 МБ, база ~1000 МБ, swap = 0) не
влезает под два CLI: один живой вызов (280–315 МБ) опускает `MemAvailable` до ~150 МБ, и
слот честно отказывает. Пока это так, платные отказы при голодном боксе — это следствие
**потолка бокса**, а не утечки сирот. Лечится решением владельца (RAM или баланс) и/или
снижением расхода слота (`post_rewrite` — 433 вызова/сутки по 1 посту).

## Что осталось (варианты, решение — за владельцем)

1. **`PR_SET_PDEATHSIG` в движке** — CLI умирает вместе с родителем, сирота не появляется
   вовсе. Точнее по корню, но требует `preexec_fn` (в многопоточных процессах Python он
   опасен) — поэтому сделан безопасный вариант выше, а этот оставлен на решение владельца.
2. **Чистка перед рестартом на стороне systemd** (`ExecStopPost=` в юните): юнитов в
   репозитории нет, правка была бы только на боксе — не версионируется.
3. **Ничего не делать**: уборка уже сделана в коде; пункты 1–2 — только улучшение.
