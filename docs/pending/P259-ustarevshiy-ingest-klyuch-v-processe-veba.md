# P259 — В работающем веб-процессе устарел CLASSIFIER_INGEST_KEY: 401 на верном ключе

**Приоритет:** 🟡 техдолг (ломает операторский инструмент, боевой классификатор не трогает)
**Открыто:** 2026-11-27 · `⏱ 2026-11-27 · snooze 0 · fresh`

## Симптом

Локальный веб стенда отвечает **401** на ingest-эндпоинты с ключом, который
**правильный**:

- `config/local-stand.env` → `CLASSIFIER_INGEST_KEY` (43 символа);
- комната (`GET {SECRETS_VAULT_URL}/api/secrets`) → то же имя, **тот же ключ**
  (сверено по sha256 отпечатку — совпадают);
- веб (pid 14796, старт 26.11 23:29) → `401 {"detail":"bad or missing X-API-Key"}`
  на `GET /api/classifier/postulates` с этим ключом.

Значит, **в процессе лежит третья копия ключа** — старая. Проверка ключа в
`web/api/classifier_ingest.py` — константное сравнение с
`os.getenv("CLASSIFIER_INGEST_KEY")`, то есть читается окружение процесса.

## Почему окружение процесса разошлось с файлом

`infra/windows/local_env.py` грузит env-файл через
`modules/prod_env.load_env_files(..., override=False)`: **уже заданные переменные
не перетираются** («systemd сильнее файла» — на Windows то же правило). Переменная,
заданная в окружении процесса **до** загрузки файла, остаётся прежней — файл её
не переписывает. Значение в окружении процесса берётся в момент старта юнита, а
файл правился позже (26.11 16:18), и после рестарта **веба** (26.11 23:29) новое
значение в процесс так и не попало.

## Чем это грозит

- **Живой классификатор не затронут.** Headless- и local-движок читают базу
  внутри процесса (`modules/classifier/*`), HTTP-ingest им не нужен.
- **Операторские инструменты сломаны:** `scripts/classifier_routine.py
  corrections` (забор корпуса для дистилляции) получает 401. Именно этим
  инструментом проверяется сырьё дистилляции — без него шаг `/start` «проверь
  корпус» закрыть нечем (27.11 обошли прямой выборкой из БД).
- **Ключ, раздающий постулаты проекта, крутится вхолостую:** 41 КБ правил под
  `/api/classifier/postulates` защищены ключом, который в процессе другой.

## Что делать

1. **Перечитать окружение веба** — рестарт юнита `setka` (юнит поднимает новый
   процесс, а тот читает env-файл). Это же решает вопрос P255: рестарт — как раз
   тот штатный момент, в котором проверяют, что перерегистрация задачи
   планировщика не поднимает второго супервизора.
2. **Не считать, что файл — источник истины для процесса.** Правило уже есть в
   `modules/prod_env.py` («уже заданные переменные не трогаются»), но его следствие
   не записано: **правка env-файла не доезжает до живого процесса без рестарта**,
   а ключи в комнате и в файле могут разъехаться так же незаметно.
3. **Проверка после рестарта:** `GET /api/classifier/postulates` с ключом из
   `config/local-stand.env` → 200, и `scripts/classifier_routine.py corrections`
   отдаёт `count`.
