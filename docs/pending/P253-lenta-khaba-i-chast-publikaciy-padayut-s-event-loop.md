## Симптом

На локальном стенде (теперь это боевой контур) общий персистентный event-loop
процесса оказывается **занят** к моменту, когда очередная задача зовёт
`utils.celery_asyncio.run_coro`. Отказ приходит снизу, чужим текстом:
`RuntimeError: This event loop is already running`.

Живой замер 26.11, окно 09:58–18:57 (логи живут и продолжают расти, поэтому
числа — снимок на момент замера). **Оба воркера**, потому что поломка бьёт по

**Читать так:** лента хаба (`copy/setka`, «Короткой строкой») не работает **ни

## Что означает «Discarding revoked task» (проверено по коду celery)

Сообщение celery **одинаково** означает «отозвано» и «просрочено» — в
`venv/Lib/site-packages/celery/worker/request.py:492`:

```python
if any((expired, revoked_by_id, revoked_by_header)):
    log_msg = 'Discarding revoked task: %s[%s]'
    ...
    self._announce_revoked('expired' if expired else 'revoked', False, None, expired)
```

В репозитории **никто не отзывает задачи** (`revoke` не встречается ни в одном
`*.py`, кроме несвязанных `revoked_at` в моделях ОИДК). Значит, все 58 + 333 —
это **`expired`**: задачи простояли в очереди дольше своего срока. У задач
регионов срок — `expires = countdown + 3600`
(`tasks/parsing_scheduler_tasks.py:1278`), то есть волновой воркер не успевал
разбирать очередь, и публикации терялись по сроку. Общий воркер отбрасывал так
же мелкую периодику — это тот самый «кладбище общей очереди» из 25.11
(`config/celery_config.py:133-153`), сегодня в 100 раз мягче (333 против 3434).

## Локализация (трейсбек из лога, не догадка)

```
tasks/parsing_scheduler_tasks.py:1263  run_all_regions_theme → regions = run_coro(_get_regions())
utils/celery_asyncio.py:59             run_coro → return _loop.run_until_complete(coro)
asyncio/base_events.py:626             raise RuntimeError('This event loop is already running')
```

То есть `_loop` (общий персистентный цикл процесса) **уже крутится** к моменту
вызова. Первое падение — 10:42:00,083, через 4 мс после получения задачи, при
том что предыдущая задача (район `agryzsky`, тема `novost`) ещё работала секунду
назад и логировала свои последние строки в 10:41:53.

## Почему сторож не поймал

`utils/celery_asyncio.py` (сторож `run_coro`) проверяет **только** «цикл крутится
в текущем потоке»:

```python
try:
    asyncio.get_running_loop()
except RuntimeError:
    pass
else:
    raise RuntimeError("run_coro() cannot be called from within a running event loop")
```

Если цикл занят **другим** потоком (а `run_coro` зовут из `asyncio.to_thread`),
`get_running_loop()` в текущем потоке ничего не видит — сторож пропускает, и
отказ приходит снизу, чужим текстом. Это ровно тот класс, о котором уже писали
мозгу (`mailbox/to-brain/2026-09-01-a-guard-that-catches-its-own-raise-silences-itself.md`)
и который закрыт тестом `tests/test_core/test_celery_asyncio_guard.py` — но тест
ловит лишь «вызов из async-контекста», а не «цикл занят другим потоком».

## Кандидаты в держатели цикла (нужен живой замер, не версия)

1. **Sync-мост `get_active_parse_tokens_sync`** (`modules/vk_token_router.py:979`)
   — сегодня уже известен как негодный в async-контексте: три его вызова в
   `tasks/discovery_tasks.py` и `tasks/parsing_tasks.py` переписаны на прямой
   `await` именно из-за этого. Если его позвать **из потока**
   (`asyncio.to_thread`), он заберёт общий цикл — и следующая задача упадёт.
2. `asyncio.to_thread` в копи-пути (`modules/copy_setka_network.py:81,182`):
   там крутится синхронный `VKClient`; если внутри него есть мост на `run_coro`,
   цикл уходит в поток.
3. **Цикл в другом потоке вообще** — механизм отказа требует именно этого:
   `run_until_complete` бросает «This event loop is already running», когда цикл
   уже исполняется **в другом потоке** (`loop._thread_id` установлен). В том же
   потоке такой вызов был бы заблокирован сторожем.

⚠️ **Прежняя гипотеза снята замером:** «незавершённая корутина от прерванной
задачи» (из `config/celery_config.py:105-115`) — **не причина**. Предупреждения
`RuntimeWarning: coroutine ... was never awaited` (17 штук) — **следствие**
отказа: когда `run_coro` бросает исключение, переданная ему корутина
(`_execute` либо `_save_failure`, `tasks/parsing_scheduler_tasks.py:1148`)
не ожидается вовсе и срабатывает `GC` с предупреждением. Именно так и
предупреждает `parsing_scheduler_tasks.py:1150` — это `except Exception: pass`
вокруг `run_coro(_save_failure())`.

## Что делать

1. **Живой замер (первым шагом):** в `run_coro` при отказе логировать
   `threading.get_ident()`, `getattr(_loop, "_thread_id", None)` и
   `_loop.is_running()` — кто держит цикл, видно сразу.
2. **Полный сторож:** отказывать и когда `_loop` уже занят (`_loop.is_running()`),
   и говорить **своим** сообщением вместо чужого «This event loop is already
   running». Это чинит диагностику, но не ленту.
3. **Убрать мосты из потоков:** все `run_coro`-вызовы из `asyncio.to_thread` —
   либо переписать на async (как сделано в `tasks/discovery_tasks.py`), либо
   передавать токен аргументом.
4. **Проверка сценария:** «прервать задачу (revoke) во время работы» → следующая
   задача обязана стартовать без «This event loop is already running».

⚠️ **Лечение требует рестарта юнитов стенда** — гейт хоста не даёт
(`Stop-ScheduledTask` — `HOST_CAPABILITY_UNAVAILABLE`). Владельцу рестарт всё
равно нужен (защита памяти движка, PR #1297) — значит, фикс стоит залить **до**
того рестарта, иначе он не встанет к ночи.

## 27.11 07:10 — кто такой `Timer-1`: ответ на п.3 закрыт

Имя потока оказалось не угадкой, а прямо в коде celery:

- `venv/Lib/site-packages/celery/utils/timer2.py:65` —
  `self.name = f'Timer-{next(self._timer_count)}'`. Потоки вида `Timer-N` — это
  **ETA-таймер celery** (счётчик на процесс), а не `threading.Timer` из нашего
  кода (`threading.Timer` в проекте ровно один — `modules/opencode_engine.py:328`,
  это убийца CLI, в бою не используется; в kombu 5.5.4 `class Timer` в
  `transport/redis.py` тоже нет).
- `venv/Lib/site-packages/celery/worker/strategy.py:199` — задача с ETA:
  `call_at(eta, apply_eta_task, (req,), priority=6)`, где
  `call_at = consumer.timer.call_at`. То есть **ETA-задачу поднимает поток
  таймера**, а не главный поток.
- `venv/Lib/site-packages/celery/worker/consumer/consumer.py:572` —
  `apply_eta_task`: «Method called by the timer to apply a task with an
  ETA/countdown».
- На стенде воркер идёт с `--pool=solo`, а solo-пул исполняет тело задачи
  **inline в том же потоке** (`celery/concurrency/solo.py` → `on_apply`).
  Значит, тело ETA-задачи выполняется **в потоке таймера**.

**Полная цепочка коллизии (06:47:00):**

1. ETA-задача (у нас это `countdown=` — `tasks/parsing_scheduler_tasks.py:1276`
   для волн и `tasks/digest_tasks.py:134` для сводки, а также ретраи с
   `countdown=60`) срабатывает по таймеру celery → её тело исполняется **в
   потоке `Timer-1`**.
2. Тело нашей задачи — обычный sync `def`, и оно зовёт `run_coro(_execute())`
   (`tasks/parsing_scheduler_tasks.py:1077`) → **общий персистентный цикл
   процесса оказывается в руках потока таймера**.
3. Пока цикл занят, в главный поток приходит задача от beat'а — `copy/setka`
   (крон `minute="2,7,12,17,22,32,37,42,47,52"`, минута 47 в списке) → её
   `run_coro` отказывает по сторожу → «Task failed for copy/setka».
4. Держал петлю в этот момент **синхронный Redis внутри корутины**:
   `redis/connection.py` → `connect_check_health` → `retry.call_with_retry` →
   connect с ретраями. Клиенты у нас обычные (не async): `modules/minimax_capacity.py:126`
   (`lease()`, зовётся из движка `modules/minimax_engine.py:1419`),
   `modules/wave_lock.py:61`, `modules/task_timings.py:58`. Такое I/O **блокирует
   поток петли** и заметно продлевает коллизию.

**Ответ на п.3 — какой мост тянуть в async:**

- **Кандидат №2 (`asyncio.to_thread` в копи-пути, `modules/copy_setka_network.py:81,182`) — снят замером.**
  `VKClient` не зовёт `run_coro` (`modules/vk_monitor/vk_client.py` — только
  `asyncio.to_thread` вокруг rate-limit'а), а потоки `to_thread` называются
  `ThreadPoolExecutor-N_M`, а не `Timer-1`. Держателем был именно таймер celery.
- **Кандидат №1 (sync-мост `get_active_parse_tokens_sync`,
  `modules/vk_token_router.py:957-982`) — остался единственным sync→`run_coro`
  мостом в коде** (единственный вызов — `tasks/parsing_tasks.py:726`), но
  **виновником 06:47 он не был**: его зовут из sync-контекста, а не из
  ETA-потока. Чинить его всё равно стоит (см. ниже), но это не петля.
- **Настоящий «мост» — вызов `run_coro` из тела ETA-задачи.** Общий цикл
  процесса не должен уезжать в поток таймера. Варианты починки:
  1. **вынести персистентную петлю в выделенный поток-владелец**: `run_coro`
     из любого потока кладёт корутину в очередь владельца и ждёт результат.
     Тогда «петля занята» невозможно по определению, а пул asyncpg остаётся
     привязан к петле владельца. **Это правильная починка**;
  2. на стенде — уйти от `--pool=solo` к prefork: там ETA-задачу исполняет
     **дочерний процесс**, а таймер только диспетчеризирует. Отдельное
     операционное решение (память, конфигурация юнитов);
  3. убрать `countdown=` из публикации волн/сводки — **не рекомендуем**: срок
     нужен для раскладки по времени и для `expires`.
- **Попутно:** синхронный Redis внутри корутины (перечислен выше) надо
  переводить на async-клиент либо выносить из петли — иначе коллизия
  растягивается на секунды connect'а с ретраями.

**п.4 (сценарий «прервать задачу во время работы») — закрыт:** он и есть
живой случай 06:47 (задача в работе, следующая приходит и падает), плюс
регресс-тест PR #1306 `test_run_coro_refuses_when_loop_busy_in_another_thread`
(сценарий «петля занята другим потоком») — зелёный.

## 27.11 08:30 — починка: пул `threads` и петля под замком

Диагноз п.3 позволил воспроизвести дефект **в изоляции** и проверить
починку до того, как она коснётся боевых юнитов. Проба: своя очередь
`probe`, зонд — `publish_daily_digest_region` с несуществующим регионом
(трогает общий цикл, ничего не публикует); 200 обычных задач + 30 задач с
разнесённым ETA.

| Пул и конфигурация | Коллизий P253 | Отказов задач | Успешных задач |
|---|---|---|---|
| `solo`, старый `run_coro` | **16** | 24 | 230 |
| `threads`, старый `run_coro` | 0 | 0 | 178 |
| `solo`, новый `run_coro` (ждёт петлю) | 0 | 0 | 230 |
| `threads` × 2, новый `run_coro` | 0 | 0 | **282** |

Строки-образцы из пробы на `solo` подтверждают механизм п.3: держатель —
`holder_thread=… (Timer-1)`, звал `caller_thread=… (MainThread)`.

**Что изменено (две правки, обе в репозитории):**

1. **`infra/windows/start-worker.ps1` и `start-wave-worker.ps1`: пул
   `threads` вместо `solo`.** При `solo` ETA-задачу исполняет поток таймера
   celery, а обычные — главный поток; оба зовут общий event-loop. При
   `threads` тела задач исполняют потоки пула, а таймер только раздаёт
   ETA-задачи — коллизии не бывает. Prefork на Windows не работает вовсе
   (`WinError 5`, проверено 26.11).
2. **`utils/celery_asyncio.py`: петля берётся под замком.** Раньше второй
   поток, пришедший за петлёй, получал отказ и задача падала; теперь он
   **ждёт** освобождения (таймаут ожидания — `SETKA_RUN_CORO_WAIT_TIMEOUT_SEC`,
   по умолчанию 30 мин). Отказ с диагностикой остался только для случая
   «петлю крутит кто-то вне нашего замка» и для таймаута.

**Два слота публикации на стенде.** На проде очередь `wave` обслуживают оба
воркера (ADR-0022) — то есть мест публикации там два. На стенде очередь
`wave` забирает один юнит, поэтому два места взяты concurrency'ем пула
(`--concurrency=2` в `start-wave-worker.ps1`). Замер 27.11 по логу волнового
воркера: задача региона — **24.7 с** в среднем (108 задач), мама волны —
**0.2 с**, веер сводки — 1–3 мин на регион. С одним слотом сводка забирает
слот на часы, и волны уходят в «кладбище» по сроку — ровно то, что было
26.11 (утрачены волны 22:00 / 22:20 / 22:50).

**Сторож:** `tests/test_infra/test_stand_unit_stop.py` — два новых теста
(«воркеры не вернулись к `solo`» и «у волнового юнита два слота»);
`tests/test_core/test_celery_asyncio_guard.py` — два новых теста на новое
поведение (второй поток **ждёт** петлю и получает результат; два потока
звут `run_coro` одновременно — оба получают результат, отказов нет).
