# 🔴 MiniMax CLI сбивается по памяти на боксе — волна уходит в платный Дипсик

> Запись `P239` реестра [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md). Индекс грепается,
> запись читается целиком, реестр целиком не читается никогда ([D-097](../../AGENTS.md)).

`⏱ 2026-11-25 · snooze 0 · fresh · найдено ночным замером 25.11 04:00–04:25: движок
MiniMax 16 раз сбит ядром по памяти, 14 откатов в платный Дипсик, свободная память бокса
186 МБ из 1536 МБ при swap = 0, оба Celery-воркера не отвечают друг другу на heartbeat`

## Что это

Рутина discovery в 04:00 поднимает CLI MiniMax (`/usr/bin/mcode`) как дочерний процесс
Celery-воркера. На боксе (1536 МБ, swap = 0) этот процесс **ядро снимает по памяти
(код -9)** — раньше, чем CLI успевает отказать сам. Движок ловит отказ, сбрасывает
накопленное состояние CLI и **повторяет вызов**; повтор умирает так же, и тогда
`discovery` закрывается **платным Дипсиком**.

Это не «MiniMax не отвечает» — это **MiniMax не успевает**: памяти на боксе не хватает
даже на один живой вызов CLI.

## Замер (прод, 25.11 04:00–04:25)

| Что | Факт |
|---|---|
| `minimax: CLI снят по памяти (код -9)` за сегодня | **16 раз**, первая — 04:00:26 |
| `discovery: minimax не ответил (exec_failed) — закрываем платным Дипсиком` | **14 раз** |
| Вызовов платного Дипсика за сегодня | **14** (из них 9 — реальные промахи мимо кэша) |
| Процессы `minimax-code` на боксе | **3 одновременно**, RSS 101–204 МБ каждый (≈470 МБ) |
| Свободная память | **186 МБ** из 1536 МБ, swap = 0 (на пике сводки было 416 МБ) |
| Load average | **10.3** при 1 CPU-воркере (обычная ночь — единицы) |
| Heartbeat воркеров | `missed heartbeat from wave@/` **38 раз**, и встречно от wave — непрерывно с 04:05 |
| SSH к боксу | 2 из 3 попыток — таймаут баннера (04:07–04:20) |
| Область CLI `~/minimax-accounts` | **186 МБ** (потолок состояния — 64 МБ, сброс работает) |

## Почему CLI сбивается именно сейчас

Движок уже умеет ограничивать себя: `MINIMAX_STATE_MAX_MB` (по умолчанию 64) держит
накопленное состояние CLI, `MINIMAX_NODE_MAX_OLD_SPACE_MB` (по умолчанию **384**) —
потолок кучи V8, сделанный ровно для этого: «потолок превращает это в быстрый отказ
самого CLI (и наш откат), а не в убийство чужого процесса» (комментарий в
`modules/minimax_engine.py`).

**Но на боксе `MINIMAX_NODE_MAX_OLD_SPACE_MB` не задан** (в окружении воркера есть
`MINIMAX_ACCOUNTS_DIR`, `MINIMAX_CLI`, `MINIMAX_MAX_STEPS=14`, `MINIMAX_MODEL`,
`MINIMAX_TIMEOUT=240`, `MINIMAX_CHUNK_SIZE=20`, `MINIMAX_REPORT_ACTIVATION=1`,
`MINIMAX_PUBLISH_TIMEOUT=180` — и потолка кучи среди них нет). Значит CLI разрешает
себе расти до 384 МБ кучи, тогда как свободно **186 МБ**: V8 своего предела не
достигает, а ядро снимает процесс раньше.

Сброс состояния (который движок делает после -9) тут не помогает: состояние и не
раздуто — 186 МБ на всю область, и причина не в нём, а в том, что **сам вызов CLI
не помещается в свободную память**.

## Что это ломает

1. **Деньги.** Каждый отказ — платный вызов Дипсика. Пока движок «молчит» дольше
   `MINIMAX_DEAD_AFTER_SEC` (600 с), весь поток discovery идёт платной страховкой
   целиком — это и был сценарий двухдневного отказа 20–21.11 (945 отказов и 945
   вызовов Дипсика за два дня).
2. **Вечерние слоты.** Бокс в 04:00 уже на 186 МБ свободных при load 10, оба
   Celery-воркера не отвечают друг другу на heartbeat, SSH флапает. Слоты 22:20/22:50
   после рестарта бита уйдут в `wave` ([ADR-0022](../adr/0022-publikacionnye-sloty-v-ocheredi-wave.md)),
   но воркер, который должен их разобрать, сейчас **не отвечает** — роутинг в
   `wave` без здоровых воркеров не спасёт.
3. **Решение по [P238](P238-kladbishche-v-ocheredi-celery.md) вариант (а) — третий
   воркер** снимается с таблицы: при 186 МБ свободных (и 0 swap) третий воркер
   не поднимается, а добивает бокс.

## Рычаг (решение владельца, без правки кода)

Строка в env бокса + рестарт воркеров:

```
MINIMAX_NODE_MAX_OLD_SPACE_MB=96
```

Потолок кучи V8 становится ниже того, что бокс может дать, — CLI **сам** честно
отказывается (быстрый отказ, наш откат, без ядерного убийства), RSS процесса падает с
200+ МБ до ~100 МБ, и ядро перестаёт вмешиваться. Побочный эффект: при нехватке
памяти волна уходит в Дипсик так же, как сейчас, — но **без дёрганья бокса и без
пропущенных heartbeat**.

Откат — та же строка, заменить значение или убрать (тогда снова 384).

**Чего это не чинит.** Если CLI не может уложиться даже в 96 МБ кучи, он будет
отказываться ещё быстрее, и доля Дипсика вырастет. Тогда нужен второй шаг — решать,
не поднимать ли discovery в 04:00 ночи, когда бокс и так на пределе.

## Чего я не делал

Ничего на проде не менял: ни env, ни рестарт, ни `rm` в области CLI. Все замеры —
только чтение (`ps`, `free`, логи, `tr '\0' '\n' < /proc/<pid>/environ`).
