# P262 — Полный прогон на боевой машине падает на VK-токен-роутере: тест зависит от живых счётчиков

> Запись `P262` реестра [PENDING_FOLLOWUPS](../PENDING_FOLLOWUPS.md). Индекс грепается, запись читается целиком, реестр целиком не читается никогда ([D-097](../../AGENTS.md)).

**Статус:** ⏱ 2026-11-28 · snooze 0 · fresh · **заведено 28.11 при прогоне гейта (промт КАРМАНА #203); правки не вносились — чужой код не трогали**

## Симптом

Полный прогон на этой машине (боевой контур = локальная машина владельца, Redis
живой на 6379) падает на одном тесте:

```
tests/test_vk_token_router/test_token_policy.py::test_pick_healthy_read_token_skips_dead_and_cooldowns_it
assert ['live_tok'] == ['dead_tok', 'live_tok']
```

Тест ждёт, что мёртвый токен `dead_tok` (имя `VALSTAN`) будет **проверен первым**,
а живой `live_tok` (`VITA`) — вторым. Фактически мёртвый не проверили вовсе:
кандидатом оказался только `live_tok`.

**Тест зелёный в одиночку и в своём пакете** (45 passed) — падает только в полном
прогоне. То есть зависимость не от кода, а от **состояния машины в момент прогона**.

## Причина

`TokenPolicy.pick(TokenOp.READ)` (modules/vk_token_router.py) балансирует
READ-кандидатов по **живым** счётчикам запросов за сегодня:

```python
calls_today = _calls_today_safe()      # ← читает живой Redis стенда

def _balance_key(name: str):
    ...
    return (calls_today.get(name, 0), lu is not None, lu or datetime.min)

for name in sorted(user_tokens.keys(), key=_balance_key):
```

`get_calls_today()` → `modules/vk_monitor/token_usage.py` → **Redis**. На боевой
машине в Redis лежит реальный расход за сегодня: пока `VALSTAN` потратил больше
запросов, чем `VITA`, первым кандидатом идёт `VITA`, он здоров, и цикл
`pick_healthy_read_token` возвращается **не проверив** мёртвый токен.

Тест же завязан на порядок, а не на состояние: мок-сессия отдаёт строки из
очереди по порядку вызовов `execute()`, и весь смысл теста — «мёртвый первый
уходит в cooldown, живой второй выдаётся». Как только балансировка переставляет
кандидатов по живому счётчику, тест падает.

**Почему в CI зелёно:** там Redis пустой (`get_usage()` → пусто → `calls_today`
пустой → порядок детерминированный по `last_used`). На живой машине счётчики
меняются в течение суток — тест то красный, то зелёный **в зависимости от
времени прогона**.

Это тот же класс, что [P226](P226-testy-ne-germetichny-poryadok-kandidatov.md)
(«порядок READ-кандидатов читает живые счётчики `token_usage`») и PR #1299
(«полный прогон не должен зависеть от состояния живой машины»): починен порядок
в одном месте, зависимость осталась в другом.

## Почему это мешает

Гейт локально становится **недетерминированным**: красный прогон читается как
«что-то сломалось», хотя код цел. Это ровно тот класс отказа, о котором
говорит постулат линзы П9 («молчание — не успех») и правило #125: гейт, который
иногда краснеет без причины, teaches обходить гейт, а не чинить.

## Что предлагается (не сделано — чужой код не трогали)

1. **Герметизировать тест**: подменить `_calls_today_safe` (или
   `token_usage.get_calls_today`) фикстурой с фиксированными счётчиками —
   например, `{"VALSTAN": 0, "VITA": 0}` — и проверять порядок явно.
   В модуле уже есть `token_usage.reset_for_tests()` — фикстуры, которые его
   зовут, есть; этот тест их не зовёт.
2. **Шире**: тем же способом проверить остальные тесты, полагающиеся на
   `get_calls_today` / балансировку кандидатов (поиск: `_balance_key`,
   `calls_today`, `get_usage`).
