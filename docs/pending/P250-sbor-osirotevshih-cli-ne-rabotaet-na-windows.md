# P250 — Сбор осиротевших CLI на Windows не работает: утечка процессов не ловится

**Приоритет:** 🟡 техдолг (риск латентный — но ловится до того, как станет дорого)
**Открыто:** 2026-11-26 · `⏱ 2026-11-26 · snooze 0 · fresh`

## Симптом

`modules/minimax_cli_reap.py` — сбор осиротевших процессов CLI — **Linux-only**:

- он читает `/proc/<pid>/status` и ищет процессы `minimax-code`, у которых
  `PPid = 1` (родитель умер, процесс переподан init'у);
- на Windows нет ни `/proc`, ни «единицы в качестве родителя»: Windows не
  переиспользует init, `PPid` осиротевшего процесса остаётся PID'ом умершего
  родителя.

Итог: на локальном стенде модуль **не находит ничего** — утекшие после смерти
воркера процессы CLI не собираются никем.

## Чем это грозит

На боксе CLI, переживший воркер, жил ещё **~18 минут** и подрастал до
**250–290 МБ RSS**; за ночь таких набралось 26, и ядро снимало их по одному —
в логах это читалось как «новые отказы движка», а не как утечка (P240).

На стенде запас **меньше**, а не больше: замер 26.11 — свободно **1.0–1.6 ГБ из
15.8 ГБ**, потому что машина занята **19 областями MiniMax Code владельца**
(`p-brain`, `p-ideas`, `p-matricarmz`×3, `p-minigen`, `p-orca`, …). Один
утекший CLI (node + дети Electron, 300–500 МБ по замеру) — треть запаса; три —
конец машины. На боксе это было «125 ядерных убийств за ночь и 122 платных
вызова в Дипсик», здесь цена отказа другая: Windows не убивает крупнейший
процесс, он просто не даёт выделить память — и упавший вызов всё равно уйдёт
в **платную страховку**.

## Замер 26.11 (состояние на момент записи)

- Движковых CLI-процессов на машине **нет**: `mcode.cmd` встречается только у
  интерактивных сессий агентов (`--session`, `--cwd`).
- Форма утечки на машине при этом **есть**: `cmd.exe` одной из сессий агента
  живёт с уже мёртвым родителем (родитель — тот shell, который её запустил,
  давно вышел). То есть «процесс пережил своего родителя» на Windows
  случается буквально.
- Перезапуск воркера на стенде делает Task Scheduler (`setka-celery-worker`,
  `setka-celery-worker-wave`), и у него есть «перезапускать при сбое» — но
  **дерево процессов CLI он не убирает**.

## Что уже сделано 26.11

**Проверка памяти на Windows починена** (`modules/minimax_capacity.py`:
`mem_available_mb()` теперь читает `psutil.virtual_memory().available`, а не
только `/proc/meminfo`). Она ловит нехватку места **до** запуска CLI — но
уже утекшие процессы не убирает, и подменой ей быть не может.

## Что делать

1. **Портировать сбор на Windows через `psutil`** (он уже в зависимостях):
   - маркер движка в командной строке — `--output-last-message` (у интерактивных
     сессий агента его нет: там `--session` и `--cwd`); по нему отбираются
     **только** процессы движка, чужие не трогаются;
   - родитель мёртв — `psutil.Process().parent()` вернул `None` или PID, которого
     уже нет;
   - таких завершать через `psutil.Process.kill()` (на Windows это
     `TerminateProcess`).
2. **Или жёстче и правильнее:** поднимать CLI в **Job Object** с
   `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` — тогда Windows сама убивает дерево при
   смерти воркера. Это аналог `PDEATHSIG` в Linux и работает нативно; минус —
   ~60 строк на `ctypes` и риск ошибки в самом механизме запуска.
3. **Проверка сценария:** на стенде — «убить воркер во время вызова CLI» и
   убедиться, что процессы исчезли, а память вернулась.

**Что НЕ нужно:** «чистить все процессы MiniMax Code» — на этой машине
работают 19 областей владельца, это его инструменты, а не наши сироты.
