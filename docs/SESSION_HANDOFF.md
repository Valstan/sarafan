## Следующий шаг

**Срез ночи — один инструмент, два прогона в правильные окна:**

```powershell
cd D:\valstan\REPO\sarafan
# 1. МЕЖДУ 19:40 и 21:40 — база хвоста + снимок логов (база пишется только тут):
.\venv\Scripts\python.exe scripts\stand_night_cut.py
# 2. ПОСЛЕ 23:50 — вердикт (ночь закрывается, когда последняя волна развела регионы):
.\venv\Scripts\python.exe scripts\stand_night_cut.py
```

**Раньше 23:50 вердикта не будет** — скрипт отвечает «ночь не закончена» (код возврата 2), а не ложными «провалами». Это главная правка: в 22:10 волны 22:20/22:50 ещё не начинались, сводка разошлась на треть сети — вердикт в 22:10 был красным на любой ночи.

Гейты инструмента: диагностика event-loop = 0 · отбрасывания **волн/сводки** = 0 · **три вечерних слота по расписанию** (копир 22:00, admin 22:20, sport 22:50 — у каждого своё «succeeded» в окне ±10 мин) · **регионов со сборником сводки ≥ 84 по журналу публикаций** (не по логу) · **в хвосте `unacked` нет волн/сводки** (относительно базы, снятой до волн) · платных DeepSeek в окне «21:40 → утро» = 0. Код возврата: 0 — зелёные, 1 — провалы, 2 — данных не хватило / ночь не кончилась / базовый прогон.

**Если гейты зелёные:** закрыть P253 (✅ в теле, строка индекса → `docs/pending/CLOSED.md`), а техдолговый хвост (sync-Redis в корутинах, петля под мьютексом, sync-мост `get_active_parse_tokens_sync`) вынести в отдельные P-номера. **Если нет:** читать лог воркера в момент коллизии — диагностика сама назовёт держателя.

## Failed approaches (этой нитки)

- **«`unacked` пуст» как критерий приёмки.** Хвост прошлой ночи лежит часами (10 сообщений), и гейт красный ещё до начала ночи. **Не повторять:** суд — «не вырос» относительно базы, снятой до волн, и только по классу волн/сводки.
- **Гейт «0 “Discarding revoked task”» без разделения классов.** Даёт ложную тревогу: копии периодических задач отбрасываются штатно. Правило: один класс — гейт, остальное — отдельной строкой.
- **«3 × `run_all_regions_theme`» как критерий вечерних волн.** В вечернем окне `run_all_regions_theme` отрабатывает **дважды** (admin 22:20, sport 22:50); третий «слот» — копир-волна 22:00 (`parse_and_publish_theme`), а прежний счёт «3» добирался волной новостей 20:40 — если она успевала дойти после 21:40. Критерий то краснел на здоровой ночи, то проходил на больной. **Правило:** слот — это конкретное время и конкретная задача, а не «сколько всего успело».
- **Вердикт среза в 22:10.** В это время волны 22:20/22:50 ещё не начинались, сводка разошлась на треть сети — вердикт красный на любой ночи. **Правило:** ночь закрывается в 23:50 (последний слот + разведение регионов 50 мин + запас 10 мин); раньше — «неполно», а не «провалы».
- **Считать сборники сводки по логу воркера.** Логи обнуляются на рестарте (P257) — суд по ним невозможен после рестарта посреди ночи, а на сломанной ноче 26.11→27.11 счёт «124 сборника» выглядел бы как зелёный при 22 регионах из 84. **Правило:** число сборников — по журналу публикаций, лог — сверка.
- **«Платные DeepSeek за московские сутки 26.11 — 0».** В будильнике так и стояло, хотя в той же строке указан последний платный вызов 20:17 — а он в сутки 26.11 входит. База была неверной (7 вызовов). **Правило:** базу приёмки считать из журнала, а не переносить из прошлой строки будильника.
- **Читать отчёт среза из лога воркера.** Логи юнитов обнуляются на рестарте (P257), а результат задачи celery истекает через час (`result_expires = 3600`) — 27.11 отчёт среза 04:00, проверенный в 04:12, исчез после рестарта 07:43. **Не повторять:** отчёт надо сохранять (P258); инструмент среза снимает снимок логов, но поля отчёта задачи он не вернёт.
- **Правка длинной строки будильника через `edit` по полному тексту.** Не совпало (длинная строка, кавычки, стрелки); многострочные блоки в CRLF-файлах — тоже. **Работает:** замена по префиксу скриптом с записью обратно в CRLF.
- **`pre-commit` не блокирует коммит.** Black переформатировал файл уже после `git add` — в коммит уехала не-black версия, CI упал за 53 с. **Правильный порядок:** гейт → `git add` → гейт ещё раз (уже на staged) → коммит.
- **Считать, что RAM едят утечки движка.** Движок спавнит `mcode.cmd` (CLI), и его процессов на машине нет. RAM держат **десктоп-сессии MiniMax Code владельца** — это уже записано в P250; замер 27.11 это подтвердил (4 забытые сессии с мёртвым родителем).
