### Что сделано в этой сессии (26.11, 19:35–22:05)

* **P253 — лечение в коде теперь есть (PR #1306 → `13548b6`, смержен 18:57).**
  Прошлая сессия поставила диагноз, но **лечение не было написано**: сторож в
  `utils/celery_asyncio.py` ловил только «цикл крутится в текущем потоке», а
  отказ из **другого** потока проскакивал и падал уже внутри
  `run_until_complete` — с чужим текстом «This event loop is already running».
  Теперь: полный сторож (отказ **своим** сообщением **до** вызова
  `run_until_complete`) + диагностика держателя (id и имя потока, поток вызова,
  **стек держателя** через `sys._current_frames()`) + регресс-тест на сценарий
  «петля занята другим потоком».
* **Цифры в PENDING уточнены (PR #1307 → `8a3ad73`):** прежняя запись
  «47 отказов, 100 % попыток» была завышена. Факт: **73 отказа `copy/setka` из
  615 полученных задач**; дефект срабатывает **в коллизующие с волнами минуты**
  (21:07 / 21:12 / 21:17 / 21:22 / 21:32 / 21:37 / 21:42 / 21:47 / 21:52 /
  22:02 — минуты тика `*/5`), в остальные тики копи-путь отрабатывает. По
  задачам: `copy/setka` — 73, `copy/krugozor` — 1, `tatarstan_obl/oblast` — 1;
  в общем воркере (`celery`) — **0**, значит дело в коде копи-пути.

  дефект — коллизия за общий цикл, а не «всё сломалось».

### Чего фикс НЕ делает

PR #1306 **диагностирует** виновника, а не устраняет его: держатель петли нужно
назвать на живом стенде. ⚠️ **В боевые процессы фикс не встал без рестарта
юнитов** — а рестарт владельцу всё равно нужен ради PR #1297 (защита памяти
движка). Значит порядок: **сначала рестарт, потом читать лог** — в нём будет
строка `run_coro: общий event-loop занят другим потоком (holder_thread=… holder_stack=…)`,
и по стеку станет видно, какой мост тянуть в async (P253 п.3).

## Failed approaches (этой нитки)

- **Считать, что `copy/setka` падает «целиком, 100 % попыток»** — неверно: по
  живому логу 73 отказа из 615 задач, дефект срабатывает в коллизующие с
  волнами минуты. Прежняя запись PENDING была завышена — исправлено в PR #1307.
  **Не повторять** без свежего среза лога.
- **Чинить `run_coro`, не имея живого замера** — сторож даёт диагностику, а
  виновника не называет: держатель петли нужно увидеть на живом стенде, а это
  требует рестарта юнитов (гейт хоста не даёт `Stop-ScheduledTask`).
- **Считать, что порядок READ-кандидатов ломается из-за hash-упорядоченной
  коллекции** — неверно: причина — живой `calls_today` из `token_usage`
  (VALSTAN=694, MAMA=706, VITA=768 — порядок из ошибки совпал с этими числами
  точно). **Не повторять** без новой инфы: гипотезу о порядке проверять замером
  живой величины, а не догадкой о структуре.
- **Чинить тесты, послабляя ожидания** — не делали: внешнее состояние
  изолируется явно (`_calls_today_safe → {}`, `mem_available_mb → 664`), иначе
  тест продолжил бы проверять не то.
- **Останавливать/перезапускать юниты стенда из сессии** — гейт хоста не даёт
  (`HOST_CAPABILITY_UNAVAILABLE` на `Stop-ScheduledTask`); не обходили — ушло
  владельцу в TICKLER.
- **Включать env-файл стенда в процесс вручную** (инъекция 79 переменных с
  секретами) — гейт; пробы делаются штатными скриптами (`local_status.py`,
  `minimax_renew_check.py`), они работают без инъекции.
- **Читать профиль области напрямую** (`minimax-accounts\work\profile.json`) —
  гейт; состояние видно через `infra\windows\setup_minimax_area.py --check`.
- **Гонять полный `pytest` на боевой машине вечером** — не делали: машина теперь
  боевой контур; pytest-гейт отрабатывает в CI (`test (3.12)` на Linux), локально
  гоняются `pre-commit` и целевые тесты.
