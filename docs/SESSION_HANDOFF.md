## Почему в ленте 3–4 поста в сутки (замер 27.10, прод, только чтение)

Владелец: «постов реально совсем мало теперь выходить стало». Замер всей цепочки:
**ни одно звено не сломано — сломан баланс «сколько постов судит нейросеть = сколько выходит»**.

| Звено | 26.10 (полные сутки) | 27.10 (до 20:45) |
|---|---|---|
| собрано (kept) | 5168 из 5812 | 3684 из 4149 |
| волн `classifier selection` | 669 | 609 |
| кандидатов в волнах | 8623 | 8818 |
| **отобрано по вердиктам** | **237 (2.7 %)** | **98 (1.1 %)** |
| волн с `отобрано=0` | 466 (70 %) | 516 (85 %) |
| опубликовано `regular` | 269 на 72 района (**3.7/район**) | 93 |

Механизм: `CLASSIFIER_SELECTION_ENABLED=1` — в сводку идёт только пост с вердиктом
`action=publish`, а вердикты пишет движок. Объём ленты равен объёму вердиктов:
21.10 — 2531 publish → 1025 постов; 25.10 — 265 → 174; 27.10 — 138 → 93.
27.10 движок не судил ничего свежего: из 4446 собранных постов вердикт есть у 5,
`publish` — у 1 (ошибки `http_402`/`breaker_open`).

**28.10 (до выката #988, до 23:00):** движок частично ожил (869 вердиктов, 489 `publish`), но
`regular` — **49**; из 489 `publish`-вердиктов в ленту попали **48 lip'ов** (kaybitsky 13→0,
afanasyevo 11→0, cheremshansky 11→0, kamsko_ustinsky 11→0). Вердикт появляется **после** того,
как волна с этим постом уже прошла отбор. Итого за 28.10 — 63 `regular` (14 из них — спортивный
блок 23:06–23:14, уже после рестарта с правкой; он прошёл по вердиктам, а не по `fallback`).

**Почему не спасает политика деградации** (первая волна — пропуск, вторая — алгоритмы):
`decide_mode` смотрел `publish_lips` на **регион целиком** (окно 1 сутки), а не на кандидатов
волны. Пока в окне лежит вчерашний `publish`, режим всегда `verdicts`, и свежие посты молча
выкидываются. 27.10: `skip-wave` — 2 из 609, `fallback` — 0. **Починено 28.10 (#988)** —
см. Ф4 выше: триггер считается по кандидатам волны.

**Связь с #983:** `floor=15` снимает движок с волн, где <15 новых кандидатов (26.10: 394 из
685) — эти волны уже не получат `publish` и опубликуют 0. После #988 такие волны больше не
публикуют ноль молча: они попадают в «тихие» и идут по политике деградации (первая — пропуск,
вторая — алгоритмы). Порог по-прежнему экономит вызовы, но перестал быть ручкой, выключающей
ленту.

- **Сокращать волны, не трогая широкие темы** — 44 % волн, ~0 % вызовов модели. Смотреть
  надо на `floor`/`chunk`/широкие слоты, а не на число запусков.
- **Минута `:27` для `copy-setka`** — гейт `test_beat_stagger` поймал: 1 мин до
  `check-unread-messages-hourly` (:28). Взята `:37` (зазор ≥9 мин).
- **Замер «по времени старта волны»** — шумит из-за дрейфа. Для решений по квоте считать
  по строкам `classifier prepublish:` (кандидаты → вызовы).
- **Считать волны по числу строк `prepublish`** — завышает почти вдвое: упавший чанк пишет
  `чанков отказали` **и** `вердиктов=0`. Волна = строка с `новых=N` в одном уникальном
  наборе (26.10: 1209 строк = 685 волн).
- **`ssh sarafan "…"` с пайпом и кириллицей** — и argv теряет кириллицу (G235), и канал
  висит после вывода; скрипт файлом через `bash -s` решает оба.
- **`./venv/bin/python scripts/smoke_test.py` из голого ssh-шелла** — уходит в `PENDING` на
  240 с: без env-файла приложения `REDIS_URL` берётся по дефолту, задача публикуется не в тот
  брокер. Рабочий вызов: `sudo -n bash -c 'set -a; . /etc/setka/setka.env; set +a; cd
  /home/valstan/SETKA && ./venv/bin/python scripts/smoke_test.py …'` (значения не печатать).
- **Считать dry-run smoke за реальную волну** — путь кода тот же, в логе те же строки
  `политика деградации`; отличие только в `dry_run: True` в строке успеха задачи. Первые
  «живые» `fallback`-строки вечера 28.10 оказались smoke'ом, а не волной.
