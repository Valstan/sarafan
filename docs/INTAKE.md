# Порядок приёма нового промта

> Как задание попадает в проект, кто его принимает, кого зовёт, что отдаёт дальше
> и чем заканчивается. Схема **одна на весь проект** — под каждое задание она не
> пересоздаётся.

Схема приёма — часть «системы мозга» проекта: [`AGENTS.md`](../AGENTS.md)
(конституция), [`docs/PROJECT_LENS.md`](PROJECT_LENS.md) (карта),
[`docs/EXPERTS.md`](EXPERTS.md) (роли и границы совета), этот документ (приём).

## 2. Маршруты приёма

**Маршрут выбирает координатор**, но основание выбора — заранее записанное
правило, чтобы спор о маршруте не возникал каждый раз заново.

### Маршрут «простая задача» — координатор → программист

Признаки (все четыре должны быть верны):

1. затрагивает не больше двух частей проекта;
2. не меняет схему данных и не требует миграции;
3. не меняет контракт между частями (нет нового API, новой очереди, новой роли);
4. критерии приёмки проверяемы тестом.

Маршрут: **координатор → программист → критик → приёмка.** Тестер — по
решению координатора (если затронуто пользовательское поведение).

### Маршрут «сложная задача» — через совет

Признаки: хотя бы один из признаков простоты нарушен, **или** задача затрагивает
несколько частей сразу, **или** решение спорное (два разумных варианта), **или**
затрагивает прод, деньги или публикацию.

Маршрут: **координатор → разведчик → совет → программист → критик → тестер →
приёмка.**

Границы совета (потолок, кто входит, когда шут) — в `docs/EXPERTS.md` §5.

## 3. Шаги приёма

| Шаг | Кто | Что делает | Что оставляет |
|---|---|---|---|
| 0. Подготовка | координатор | `git fetch`, чтение канона и SoT, индекс `docs/PENDING_FOLLOWUPS.md`, письма мозга, разборы похожих заданий | список «что уже знаем по теме» |
| 1. Разбор промта | координатор | суть, что должно измениться, критерии приёмки (из промта), границы (файлы/задача), что НЕ делаем, риски | раздел «Разбор» в файле разбора |
| 2. Маршрут и состав | координатор | выбор маршрута (§2) и явная запись «кого зовём и почему столько» | раздел «Совет» в файле разбора |
| 3. Разведка | разведчик | факты по **названному** участку: модули, связи, процессы | раздел «Факты» |
| 4. Совет | роли по составу | обсуждение по ролям, выводы и решение в одном месте | раздел «Решение совета» |
| 5. План | координатор | шаги, файлы, тесты, критерии приёмки, что не делаем | раздел «План» |
| 6. Код | программист | реализация + тесты + обновление линзы/реестра, если менялся проект | PR |
| 7. Ревью | критик | ошибки, «сделать лучше», сверка с планом | раздел «Вердикт критика» |
| 8. Стенд | тестер | живые пользовательские ситуации | раздел «Стенд» |
| 9. Приёмка и закрытие | координатор | PR → CI `test (3.12)` → squash-merge → запись опыта → handoff → архив промта | PR, письмо в мозг, запись в `docs/pending/`, архив промта |

**Шаги 3–4 обязательны только для сложного маршрута.** В простом маршруте
шаг 1 сразу переходит в шаг 5.

## 4. Форма разбора

Каждое задание оставляет **один** файл: `docs/experts/<YYYY-MM-DD>-<слаг>.md`.
Шаблон:

```markdown
# Разбор задания: <название> (<YYYY-MM-DD>)

**Промт:** <источник: раздел КАРМАНА #N / письмо мозга / P<NNN> / замечание владельца>
**Маршрут:** простая задача | сложная задача

## Разбор (координатор)
- Суть:
- Что должно измениться:
- Критерии приёмки (из промта):
- Границы (файлы/задача):
- Что НЕ делаем:
- Риски:

## Что уже знаем по теме (опыт проекта)
- <запись из docs/pending/, ADR, письмо мозга, прошлый разбор>

## Совет
- Кого позвали и почему столько:
- Решение совета:
- Отвергнуто и почему:
- Шут: идеи → что превращено в применимое:

## План
- Шаги, файлы, тесты, критерии:

## Что сделал программист
- <файлы, что поменялось>

## Вердикт критика
- По коду: / По плану: план выполнен | нет (перечень недоделок)

## Стенд (тестер)
| Ситуация | Результат | Примечание |
|---|---|---|

## Приёмка
- PR: #N · гейт: pre-commit / pytest (число тестов) / CI `test (3.12)`
- Что ушло в опыт проекта: <P<NNN> / ADR / письмо в мозг / линза>
```

**Метка роли обязательна.** Каждый раздел и каждая реплика в разделе «Совет»
начинается с метки: `[координатор]`, `[разведчик]`, `[критик]`, `[тестер]`,
`[шут]`, `[антропогенез]`, `[эффективность]`, `[нужность]`, `[программист]`.
Разбор без меток — монолог, а не совет.

## 5. Что считается «план выполнен»

Список — в `docs/EXPERTS.md` §6. Коротко: все пункты плана закрыты или явно
перенесены; критик дал вердикт по коду и по плану; тестер зафиксировал
«решает / уходит в тупик» по каждой ситуации; гейт зелёный; линза и реестр
обновлены, если менялся проект; опыт записан в принятые места проекта.

## 6. Приёмка не размывается

Экспертная система **добавляет обсуждение**, но не заменяет привычный порядок:

1. работа — в feature-ветке (`git checkout -b <type>/<slug> origin/main`);
2. PR с описательным телом: что меняли, почему, тесты, границы; для заданий
   КАРМАНА — строка «Промт КАРМАНА #<N>»;
3. гейт: `pre-commit run --all-files` + `pytest tests/ -q` (с числом собранных
   тестов) + CI-проверка `test (3.12)`;
4. **решение за человеком** — squash-merge по правилам `AGENTS.md`.

## 7. Что делать, если задание не выполнено

- Не выполнил — **не архивируй** промт: архив = «сделано» (постулат П5).
- Хвост пишется в `docs/pending/` (`P<NNN>`), а не в чат и не «в голову».
- Нитка между сессиями — `docs/SESSION_HANDOFF.md`: что осталось и следующий шаг.

## 8. Куда писать опыт

Карта мест — в `docs/EXPERTS.md` §8. Коротко: техдолг → `docs/pending/`,
решение → `docs/adr/`, переносимая находка → `mailbox/to-brain/`,
правило классификатора → `config/classification_postulates.md`,
правило проекта → `AGENTS.md`. **Второе хранилище не заводим.**

## Связанное

- `docs/EXPERTS.md` — роли, границы совета, «план выполнен», каталог скиллов.
- `docs/PROJECT_LENS.md` — карта проекта и правило её обновления.
- `AGENTS.md` — конституция, гейты, порядок работы с Git.
- `docs/adr/0026-sistema-mozga-proekta-linza-i-reestr-ekspertov.md` — решение о введении.
- `docs/experts/` — разборы заданий (по одному файлу на задание).
