# ADR-0024 — Единый агентный слой: «модель выдаёт задание — инструмент выполняет»

## Контекст

**Что уже было в проекте (и чего не хватало).**

| Опора | Что это | Чего не хватало |
|---|---|---|
| `gateway_mcp/` | FastMCP-сервер с read-only инструментами `vk_get_community`, `vk_get_wall`, `vk_call` | Схемы инструментов и вызов живут **в MCP-обёртке**; вне MCP этим инструментом пользоваться нельзя, а «описать инструмент для модели» означало переписать текст |
| `modules/minimax_engine.py` | MiniMax Code CLI, пул аккаунтов с ротацией и чек-ином | Движок умеет только «спросить и получить текст» — вызов инструмента в нём нет |
| `modules/deepseek_client.py` + `modules/engine_guard.py` | Платный движок, fail-open, 402-предохранитель | То же |
| `infra/engine/`, `config/opencode.py` | Оставшийся self-hosted контур (выведен из эксплуатации 06.11) | Готовый каркас, но не «задача → инструмент» |

**Что хотел владелец.** Чтобы на локальной машине под каждую задачу
поднимался свой агент: модель получает задание, решает, какой инструмент
вызвать, получает результат и возвращает его в конвейер.

**Почему это не «просто ещё одна функция».** Требование владельца —
«под каждую задачу свой агент» упирается в разделение слотов: на проде волна
и периодика делят один воркер и его слоты (ADR-0020, ADR-0022), и длинная
задача волны съедает слот, а мелкая периодика протухает по `expires`.
Значит, разделение должно быть **по очередям**, и у каждого агента должен
быть свой инструментарий и свой предел шагов.

## Решение

**Вводится единый слой: у каждого инструмента есть схема и вызов, модель
ставит задачу и получает результат.**

### 1. Реестр инструментов — `gateway_mcp/tool_registry.py`

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str
    title: str
    description: str
    input_schema: Dict[str, Any]   # JSON Schema аргументов
    handler: ToolHandler            # async (arguments: dict) -> Any
    annotations: Dict[str, Any]     # readOnlyHint и прочие
```

`ToolRegistry` даёт: регистрацию (дубль имени — ошибка), каталог (то, что
видит модель), и **вызов с валидацией аргументов** по схеме. Реестр никогда
не бросает: падение инструмента — это `{"ok": False, "error": ...}`, которое
агент видит и может обойти.

Схема рождается из pydantic-модели (`schema_from_model`), поэтому описание
инструмента пишется **один раз** — и его читают и модель, и MCP-обёртка, и
документация.

### 2. Цикл агента — `gateway_mcp/agent.py`

```
задание → [модель → {"tool": ..., "arguments": {...}} → инструмент → результат] × N → {"final": ...}
```

Протокол ответа модели — **один JSON-объект**: либо вызов инструмента, либо
финальный ответ. Это сделано намеренно: «агент позвал инструмент» должно
быть **проверяемым**, а не фразой в промте.

Результат — `AgentResult` (`ok`, `output`, `tool_calls`, `steps`), который
возвращается в конвейер **словарём**: разбирать ответ модели на стороне
потребителя не должен никто, иначе каждый потребитель заведёт свой разбор.

### 3. Профили агентов — `gateway_mcp/profiles.py`

| Профиль | Очередь | Движок | Шагов |
|---|---|---|---|
| `generic` | `agent` | DeepSeek API | 4 |
| `wave` | `agent_wave` | MiniMax Code CLI | 6 |
| `discovery` | `agent_discovery` | MiniMax Code CLI | 6 |

* **Очередь на профиль** → у профиля свой процесс воркера → свой слот.
  Разделение задач — по очереди, а не по флажку внутри задачи.
* **Маршрутизация явная** (`apply_async(queue=...)`), а не через
  `task_routes`: переезд не должен требовать правки боевой конфигурации.
* **Движок — поле профиля.** Локальные модели вместо внешнего API — это
  смена значения поля, а не правка кода.
* **Пул аккаунтов.** Отдельный процесс воркера = отдельная аренда аккаунта
  в пуле (`modules/karman_minimax`): агент, съевший лимит, не валит
  остальных.

### 4. Вход в конвейер — `tasks.celery_app.run_agent_task`

Задача в очереди профиля → агент отрабатывает → `AgentResult` возвращается
словарём. Ошибка движка **не** роняет задачу: неуспех — это `{"ok": False,
"reason": ...}`; ронять имеет смысл, когда повтор попросит другой результат,
а это решает потребитель.

## Граница

* **Слой не выбирает движок и не ходит в сеть сам.** Движок — адаптер
  (`DeepSeekModel`, `MinimaxModel`, `ScriptedModel`), все три отдают один
  контракт `{"ok": True, "content": ...}`.
* **Инструменты — только read-only.** Весь нынешний набор (`vk_*`,
  `sarafan_*`) читает. Запись появляется отдельным решением и отдельным
  allowlist'ом; молчаливый доступ на запись в MCP-обёртке — не то, что
  здесь задумано.
* **Локальная база — импорт ленивый.** Пакет `gateway_mcp` по-прежнему
  работает в среде потребителя, где базы Сарафана нет: `DATABASE_URL`
  требуется только в момент вызова инструмента.
* **Замер ёмкости измеряет контур, а не движок.** Число «заданий в час» при
  подставленной задержке — потолок, заданный задержкой движка; боевые
  лимиты (API, аккаунты, VK) — отдельная величина. Замер — в
  [`AGENT_RUNTIME.md`](../AGENT_RUNTIME.md) §4.

## Альтернативы

- **Оставить MCP-обёртку как есть и звать инструменты из кода.** Отклонено:
  у инструмента остаются две жизни (описание в MCP, вызов в коде), и
  «рассказать модели про инструмент» приходится делать заново.
- **Дать модели «свободные» вызовы без схем.** Отклонено: без схемы модель
  угадывает имена аргументов, а ошибка в аргументах выглядит как «модель
  не поняла» и стоит второго вызова.
- **Один агент на все задачи, различать по флагу.** Отклонено: это ровно
  текущая картина на проде — одна очередь, один слот, длинная задача съедает
  короткие (ADR-0022). Владелец просил противоположного.
- **Вынести слой в отдельный репозиторий.** Отклонено: инструменты и
  движки живут в этом проекте, и переезд слоя отдельно от проекта создал бы
  вторую точку правды.

## Последствия

* Появляется **перечень инструментов с описанием** в репозитории:
  [`AGENT_RUNTIME.md`](../AGENT_RUNTIME.md) §3 и живой каталог
  (`build_registry().catalog()`).
* Появляется тест приёмки: агент получает задание → вызывает инструмент →
  возвращает результат в конвейер
  (`tests/test_agent_tools/test_agent_loop.py`).
* `gateway_mcp/server.py` больше не источник истины по описаниям
  инструментов: описания живут в `gateway_mcp/tools.py`, MCP-обёртка их
  читает.
