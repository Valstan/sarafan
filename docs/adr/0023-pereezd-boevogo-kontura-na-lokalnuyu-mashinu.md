# ADR-0023 — Боевой контур Сарафана переносится на локальную машину владельца (Windows)

## Контекст

**Замер боевого бокса (26.11.2026):** 1 ядро, 1536 МБ RAM, свопа нет,
Redis 7.4.1, PostgreSQL 17.11, Python 3.12.3. Одновременно на боксе живут
**четыре** задачи Сарафана (`setka`, `setka-celery-worker`,
`setka-celery-worker-wave`, `setka-celery-beat`), демон VK-бота, приём радара
и сбор метрик.

Этот потолок — причина почти всех аварий последних месяцев:

* ночной срез подбора сообществ **не влезал в 3-часовую рамку** задачи
  (ADR-0017, P239): 233 сообщества штучным режимом давали 4–7 часов;
* ядро снимало процессы MiniMax CLI, движок отказывался по ёмкости, часть
  вердиктов уходила в **платный** DeepSeek — за ночь 25.11 на это ушло
  435 минут слота;
* общая очередь `celery` выросла до **467 сообщений** и стала кладбищем:
  вечерние волны протухали по `expires` (ADR-0022).

**Заказ владельца (зачитка 25.11.2026):** перенести боевой контур на
локальную машину, чтобы он крутился круглосуточно на агентах с нейросетью, со
своей базой и веб-интерфейсом, а прод-сервер закрыть.

**Ограничения, которые владелец оставил открытыми** (выбор хранилища,
движок, железо, судьба радара) — и которые надо закрыть до переезда, а не
после.

## Решение

**Боевой контур переносится на локальную машину владельца (Windows 11,
Python 3.12, PostgreSQL 17, Redis 8).** Прод при этом **не останавливается**
до отдельной команды владельца: переезд идёт параллельно, сначала полная
копия базы, потом сверка, и только потом — решение об остановке.

### 1. Хранилище — PostgreSQL, не SQLite

В `database/models.py` индексы объявлены через `postgresql_where=...` —
частичные индексы. SQLite — это не «замена драйвера», а правка схемы: свои
частичные индексы, свои планы, свои расхождения с продом. Приёмка требует
**точной копии** боевой базы (счётчики совпадают, расхождение 0), и SQLite
эту приёмку не выполняет.

Отдельно: дамп снимается `pg_dump -Fc` и разворачивается `pg_restore` —
частичные индексы, триггеры и расширения переезжают как есть.

### 2. Интерфейс — существующий веб-интерфейс, отдельного десктоп-приложения не делаем

Интерфейс уже есть: FastAPI + Jinja2 (`web/templates/*`), API в `web/api/*`.
Все 13 страниц из `docs/paths.md` §5 открываются локально и показывают
данные локальной базы.

Отдельное десктопное приложение под Windows потом тяжело переносить на
Linux, а браузерный вариант даёт ту же функциональность: работа с файлами
и печать в браузере есть штатно, автозапуск и фоновый режим — это задача
планировщика, а не программы. Разбор ограничений — в
[`LOCAL_WINDOWS_BROWSER_LIMITS.md`](../LOCAL_WINDOWS_BROWSER_LIMITS.md).

Слушает интерфейс **только `127.0.0.1`**. Публикация в сеть — отдельное
решение владельца, и при нём обязательно возвращается гейт
(`WEB_AUTH_ENABLED=1`): на стенде гейт выключен как dev-режим.

### 3. Секреты — тем же путём, что на проде

Ключи приезжают bootstrap'ом из комнаты КАРМАНа
(`modules/secrets_bootstrap`; worker и beat восстанавливают обязательные
секреты до старта — `tasks/celery_app.py`). В репозитории секретов нет.

Два отличия от прода, оба вынужденные:

* **env-файл на Windows читает сам процесс.** На Linux переменные даёт
  systemd (`EnvironmentFile=`); на Windows такого механизма нет, и процесс
  падал бы на `config.runtime._require("DATABASE_URL")` ещё на импорте.
  Поэтому `main.py` и `tasks/celery_app.py` перед bootstrap'ом читают
  env-файл, заданный переменной `SETKA_ENV_FILES`
  (`infra/windows/local_env.py`). На проде шаг — no-op.
* **Локальные `DATABASE_URL` и `REDIS_URL` заданы явно** — и это не
  формальность: bootstrap не перебивает уже заданное значение, и без
  локальных адресов процесс подхватил бы из комнаты **боевые** и писал бы
  в продовую базу.

### 4. systemd → планировщик задач Windows

Каждому юниту боевого контура — своя задача планировщика с тем же именем.
Подробности и таблица замен — в
[`MIGRATION_TO_WINDOWS.md`](../MIGRATION_TO_WINDOWS.md) §3 и
[`infra/windows/README.md`](../infra/windows/README.md).

### 5. Пул Celery — `solo` на Windows

Prefork (`billiard`) на Windows не работает: дочерний процесс падает с
`PermissionError: [WinError 5]` на общем счётчике пула, воркер рапортует
`ready` и бесконечно перезапускает детей. На боевом Linux остаётся prefork.

## Граница

* **Прод не останавливается.** Порядок остановки и чек-лист отката готовы
  ([`PROD_SHUTDOWN_RUNBOOK.md`](../PROD_SHUTDOWN_RUNBOOK.md)), но запуск —
  **только по слову владельца в том же ходе** (гейт #025).
* **От того же бокса зависят соседние проекты**: ЕСА, каталог `/services`,
  VK-шлюз, Радар. «Закрыть прод» = остановить юниты Сарафана и отключить
  домен Сарафана; сам бокс — отдельное решение.
* **Судьба радара — решение владельца** ([ADR-0025](0025-sudba-radara-pri-pereezde.md)).
  До решения действует вариант по умолчанию: радар остаётся в Сарафане, его
  юнит приёма на локальной машине **не поднимается** (иначе радар начнёт
  принимать события вторым экземпляром и дублировать доставку).
* **Движок — решение владельца.** Боевой путь — DeepSeek API; контур MiniMax
  Code CLI с пулом аккаунтов работает на локальной машине (профили агентов
  `wave` и `discovery` уже на нём). Выбор движка определяет железо и
  экономику, но **не** требует переписывания кода: движок — поле профиля
  агента ([ADR-0024](0024-agentnyy-sloy-zadanie-instrument.md)).
* **VK-токены и IP.** Токены работают с адреса боевого бокса; смена адреса
  может упереться в привязку и лимиты по IP. Проверяется **до** переезда.

## Альтернативы

- **SQLite на локальной машине.** Отклонено: частичные индексы
  `postgresql_where=...` потребовали бы правки схемы, а приёмка требует
  точной копии. Проще в развёртывании, но расхождение с продом — не
  «закрытый вопрос», а постоянный риск.
- **Docker Desktop / WSL2 с Linux-окружением.** Отклонено как основной
  вариант: это перенос **на Linux**, а не на Windows — задача владельца
  именно про Windows-машину. (WSL2 на машине есть и остаётся запасным
  вариантом для PostgreSQL/Redis, если portable-сборки окажется
  недостаточно.)
- **Отдельное десктопное приложение на Windows.** Отклонено: браузерный
  вариант даёт ту же функциональность, а приложение потом тяжело переносить
  на Linux. Разбор ограничений — в
  [`LOCAL_WINDOWS_BROWSER_LIMITS.md`](../LOCAL_WINDOWS_BROWSER_LIMITS.md).
- **Перенести только код и оставить базу на проде.** Отклонено: цель
  заказа — уйти с потолка «1 ядро, 1,5 ГБ» и закрыть прод. База переезжает
  вместе с кодом, а прод остаётся как страховка до сверки.

## Последствия

- Боевой контур получает 8 ядер и 16 ГБ RAM вместо 1 ядра и 1,5 ГБ — то
  есть потолок, который и был причиной аварий.
- В репозитории появляется Windows-специфичное: `infra/windows/` и две
  правки точек входа (`main.py`, `tasks/celery_app.py`).
- Появляются **две** точки правды о размещении (прод и локальная машина) —
  до остановки прода. После остановки прод перестаёт быть источником
  правды, и `AGENTS.md` §«Состояние проекта» обновляется.
- Число тестов выросло: на Windows собирается 5297 (на Linux — 5281 на
  `main` + 16 новых тестов агентного слоя).
