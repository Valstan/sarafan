# Перенос Сарафана на локальную машину (Windows)

> Документ переезда. Инвентаризация боевого контура, план переезда, порядок
> проверок и то, что осталось за владельцем.
> Решения — в [ADR-0023](adr/0023-pereezd-boevogo-kontura-na-lokalnuyu-mashinu.md)
> (переезд), [ADR-0024](adr/0024-agentnyy-sloy-zadanie-instrument.md) (агентный
> слой), [ADR-0025](adr/0025-sudba-radara-pri-pereezde.md) (радар).
>
> **Статус на 26.11.2026:** локальный стенд поднят на этой машине и проверен;
> перенос базы выполнен и сверен; прод **не тронут**.

---

## 1. Зачем

Боевой контур Сарафана живёт на VPS: 1 ядро, 1,5 ГБ RAM, без свопа. Этот потолок
— причина почти всех аварий последних месяцев (ADR-0021, ADR-0017): ночной
срез не влезал в память, движок отказывался по ёмкости, часть вердиктов
уходила в платный API.

Владелец решил перенести контур на локальную машину и держать там круглосуточно.
Этот документ — что именно переносится, чем заменяется и как проверяется.

---

## 2. Решения, которые приняты (кратко)

| Вопрос | Решение | Почему |
|---|---|---|
| Хранилище | **PostgreSQL 17 локально**, не SQLite | В `database/models.py` индексы объявлены через `postgresql_where=...` — частичные индексы. SQLite — это не «замена драйвера», а правка схемы и риск разойтись с продом. Приёмка требует точной копии. |
| Интерфейс | **Существующий веб-интерфейс** (FastAPI + Jinja2), отдельного десктоп-приложения не делаем | Отдельное приложение под Windows потом тяжело переносить обратно на Linux; браузерный вариант даёт ту же функциональность. |
| Секреты | Тем же путём, что на проде: **bootstrap из комнаты КАРМАНа** | Ключи не хранятся в репозитории и не копируются вручную. |
| Радар | См. [ADR-0025](adr/0025-sudba-radara-pri-pereezde.md) — решение владельца требуется | Радар обслуживает соседние проекты, а не только Сарафан. |
| Прод | **Не трогаем** до отдельной команды владельца | Порядок остановки и чек-лист отката готов: [PROD_SHUTDOWN_RUNBOOK.md](PROD_SHUTDOWN_RUNBOOK.md). |

## 3. Инвентаризация боевого контура

Снято с боевого бокса 26.11.2026 (SSH, только чтение). Колонки: **что крутится →
чем заменяем на Windows → как проверяем**.

### 3.1. Основные юниты

| Юнит / задача | Что делает | Чем заменяем на Windows | Как проверяем |
|---|---|---|---|
| `setka` (веб) | FastAPI на `127.0.0.1:8000`, интерфейс и API за nginx | **Задача планировщика Windows** `setka` → `infra\windows\start-web.ps1` (uvicorn, `--host 127.0.0.1 --port 8000`) | `GET http://127.0.0.1:8000/api/health/` → 200 `{"status":"healthy"}`; все 13 страниц из [paths.md §5](paths.md) отдают 200 |
| `setka-celery-worker` | Воркер очереди `celery` (мелкая периодика) | Задача планировщика `setka-celery-worker` → `start-worker.ps1`. **Пул `solo`** — prefork на Windows падает с `WinError 5` | `celery -A celery_app inspect ping`; в логе воркера `celery@<host> ready`; очередь `celery` разбирается |
| `setka-celery-worker-wave` | Второй слот: очереди `wave` и `digest` (длинные задания) | Задача планировщика `setka-celery-worker-wave` → `start-wave-worker.ps1` | `celery -A celery_app inspect active_queues`; задания из `wave` уходят отдельному воркеру |
| `setka-celery-beat` | Планировщик Celery (расписание задач) | Задача планировщика `setka-celery-beat` → `start-beat.ps1` (путь к файлу расписания задан явно — иначе beat теряет его при смене рабочего каталога) | В логе beat `Scheduler: Sending due task`; счётчик отправленных задач растёт |
| `setka-vk-bot` | Демон VK-бота (Bots Long Poll сообщества) | Задача планировщика `setka-vk-bot` → `start-vk-bot.ps1` | Процесс жив; в логе `bot` — успешный Long Poll |
| `setka-radar-intake` | Приём радара: VK Bots Long Poll + Telegram getUpdates | Задача планировщика `setka-radar-intake` → `start-radar-intake.ps1`. **Условно**: зависит от решения по радару ([ADR-0025](adr/0025-sudba-radara-pri-pereezde.md)) | Процесс жив; в логе приёма — успешный опрос источников |
| `opencode-engine.service` | Self-hosted движок OpenCode | **Не переносится**: контур выведен из эксплуатации 06.11 (ADR-0014), юнит на проде `disabled` | — |
| `prometheus.service` | Сбор метрик (`config/prometheus.yml`: скрейп `/metrics` каждые 15 с, node_exporter) | **Не переносится в полном виде.** Метрики отдаёт сам `/metrics` (Prometheus-формат, без изменений); внешнего сбора на локальной машине нет. Если нужна история — Prometheus поднимается отдельно (контейнер) | `GET http://127.0.0.1:8000/metrics` → 200, формат Prometheus; счётчики `setka_regions_active`, `setka_communities_monitored` — ненулевые и совпадают с локальной базой |
| nginx (`config/setka.conf.editable`) | Reverse proxy + `/static`, домен боевого контура | **Не переносится.** Локальный интерфейс открывается прямо по `http://127.0.0.1:8000`; слушать что-то кроме `127.0.0.1` нельзя (машина в домашней сети) | Порт 8000 слушает только `127.0.0.1` (`netstat -ano | findstr :8000`) |

### 3.2. Cron и таймеры

| Юнит / задача | Что делает | Чем заменяем на Windows | Как проверяем |
|---|---|---|---|
| cron `infra/engine/local-engine.cron` (каждые 5 минут) | Локальный движок классификатора через OpenCode (`--local`, без сети и SSH) | **Не переносится.** Он работал только при живом self-hosted-контуре, который выведен из эксплуатации. Если владелец вернёт локальный движок — запускается **задачей планировщика** с шагом 5 минут (`New-ScheduledTaskTrigger -Once -RepetitionInterval (New-TimeSpan -Minutes 5)`) | См. решение владельца о движке: [ADR-0023](adr/0023-pereezd-boevogo-kontura-na-lokalnuyu-mashinu.md), §«Движок» |
| cron бэкапа БД (ежедневно, 03:00) | `pg_dump` боевой базы в сжатый файл | **Задача планировщика** `sarafan-db-backup` → `pg_dump` в локальный каталог (формат custom). ⚠️ Штатный `scripts/backup_database.sh` на проде **сломан** (см. §7) | Файл дампа свежий; `pg_restore --list` читается |
| таймеры `infra/neural/neural-egress-guard.timer` (каждые 2 мин) | Сторож сетевого выхода self-hosted-контура | **Не переносится** — контур выведен из эксплуатации | — |
| таймеры `infra/neural/neural-identity-reset.timer` (каждые 15 мин) | Сброс идентичности self-hosted-движка | **Не переносится** — то же | — |
| таймеры `infra/neural/opencode-rss-guard.timer` (каждые 2 мин) | RSS-сторож OpenCode | **Не переносится** — то же | — |
| таймер `minimax-dns-pin.timer` (каждый час) | Фиксация DNS для CLI MiniMax | **Не переносится**: DNS-пин привязан к сетевому контуру боевого бокса. На локальной машине CLI ходит через обычный DNS | — |

> **Факт, а не догадка:** на боевом боксе таймеры `infra/neural/*.timer` **не
> установлены** — в списке таймеров их нет. В репозитории они лежат как код
> self-hosted-контура, который выведен из эксплуатации. Переносить нечего.

| Что | Как переносится |

## 4. Что НЕ переносится и почему

| Что | Почему |
|---|---|
| nginx и боевой домен | Локальная машина — не сервер. Домен и TLS остаются на боевом контуре, пока он жив (см. порядок закрытия) |
| Prometheus + node_exporter | Внешнего сбора с локальной машины нет; `/metrics` отдаётся, история — отдельная задача |
| Self-hosted контур OpenCode | Выведен из эксплуатации 06.11 (ADR-0014) |
| DNS-пин MiniMax | Привязан к сетевому контуру боевого бокса |
| ЕСА, каталог `/services`, VK-шлюз для соседних проектов | Живут на том же боксе, что и Сарафан; их переезд — **отдельная** работа, не эта (см. §9) |

## 6. Перенос базы и сверка

### 6.1. Перечень таблиц для сверки

Сверка идёт **по всем таблицам публичной схемы** (их 59), а не по выборочным
пяти. Пять таблиц из приёмки — обязательные:

`posts`, `communities`, `regions`, `filters`, `publish_schedules`

### 6.2. Процедура

```bash
# 1. Дамп с прода (только чтение базы)
Get-Content -Raw infra\windows\prod_dump.sh | ssh sarafan "bash -s"
#    → <корень деплоя>/backup/sarafan_migration_<метка>.dump  (297 МБ)

# 2. Забрать на машину
scp sarafan:SETKA/backup/sarafan_migration_<метка>.dump .\downloads\sarafan_migration.dump

# 3. Развернуть в локальный PostgreSQL
pg_restore -h 127.0.0.1 -p 5433 -U setka -d sarafan --no-owner --no-privileges .\downloads\sarafan_migration.dump

# 4. Счётчики с прода
Get-Content -Raw infra\windows\prod_counters.sh | ssh sarafan "bash -s" > downloads\prod_counters.txt

# 5. Счётчики локально (тот же запрос) — и построчное сравнение
```

### 6.3. Результат сверки (26.11.2026)

| Таблица | Прод | Локально | Расхождение |
|---|---|---|---|
| `posts` | 0 | 0 | **0** |
| `communities` | 3415 | 3415 | **0** |
| `regions` | 85 | 85 | **0** |
| `filters` | 1202 | 1202 | **0** |
| `publish_schedules` | 126 | 126 | **0** |
| **все 59 таблиц** | — | — | **58 таблиц совпали построчно; 1 (`published_posts`) — живой журнал, расхождение в единицы, причина — параллельная запись на проде** |

> **Про `posts = 0` — это факт боевой базы, а не потеря при переносе.**
> Таблица `posts` на проде пуста: её чистит ежедневная задача
> `cleanup_old_posts` (посты старше 30 дней), а основной корпус собранных
> постов лежит в `collected_post_audit` (317 520 строк) и
> `content_classifications` (286 586 строк). Локальная копия содержит ровно
> то же.

> **Про `published_posts` — единственное расхождение, и оно живое.** Таблица
> журнала публикаций пишется непрерывно (~1200 строк в сутки), поэтому её
> счётчик на проде меняется между снятием дампа и сверкой. На 26.11 в
> момент повторной сверки значения сошлись (70 137 = 70 137). Все остальные
> таблицы совпали **точно** — то есть копия полная.

### 6.4. Построчная сверка классификатора

Отдельный пункт приёмки: «один и тот же набор постов классифицируется локально
и прод-движком одинаково — сравнение вердиктов построчно».

**Инструмент готов:** `infra/windows/classifier_parity.py`. Он берёт посты из
аудита сбора, у которых в локальной (скопированной) базе лежит **боевой**
вердикт, прогоняет их через **локальный** движок тем же кодом
(`modules/classifier/headless.py`) с той же рубрикой (постулаты считаются из
локальной базы тем же кодом, что отдаёт боевой рутине) и сравнивает вердикты
построчно по решающим полям `action`, `theme`, `urgent`, `confidence`.

```powershell
.\venv\Scripts\python.exe infra\windows\classifier_parity.py --limit 40
```

**Состояние на 26.11.2026:** инструмент работает — выбор постов, чтение
рубрики, сравнение и печать таблицы. **Сам прогон вердиктов не выполнен:**
локального движка нет, потому что ключ DeepSeek лежит в комнате КАРМАНа, а
`SECRETS_TOKEN` на локальной машине ещё не подключён (см. §8). Скрипт в этом
случае честно печатает `Отказы движка: ['no_api_key']` и `без локального
вердикта: N` — **не притворяясь, что сверка прошла**.

Как только токен подключён, сверка — одна команда; отдельного решения, кроме
пункта 1 из §8, для неё не нужно.

## 7. Найденное по дороге: штатный бэкап на проде сломан

`scripts/backup_database.sh` падает на разборе `DATABASE_URL`:

```
awk: cmd. line:1: BEGIN{FS=\"=\"} ... ^ backslash not last character on line
```

Причина — экранированные кавычки внутри одинарных кавычек в bash. Скрипт
падает **до** `pg_dump`, поэтому в каталоге бэкапов с начала января лежат
**пустые (0 байт) файлы** — то есть ежедневного бэкапа боевой базы фактически
нет уже несколько месяцев.

* Что сделано в этом переезде: снят **правильный** дамп (297 МБ) своим
  скриптом `infra/windows/prod_dump.sh` с исправленным разбором env-файла.
* Что не сделано и почему: правка `scripts/backup_database.sh` — **не моя
  территория** в этой задаче, а файл боевой. Запись о починке — в
  [`PENDING_FOLLOWUPS.md`](PENDING_FOLLOWUPS.md).
* Правка однострочная: убрать `\"` внутри одинарных кавычек awk.

## 8. Секреты

Секреты приезжают **тем же путём, что на проде**: bootstrap'ом из комнаты
КАРМАНа (`modules/secrets_bootstrap`). В репозитории секретов нет и не будет.

| Имя | Где живёт | Комментарий |
|---|---|---|
| `DATABASE_URL`, `REDIS_URL` | `config/local-stand.env` (машинный файл, в git не едет) | Локальные адреса. Это же **защищает боевую базу**: bootstrap не перебивает уже заданное значение (свойство 3 спеки секретов) — без локальных адресов процесс подхватил бы из комнаты боевые и писал бы в прод |
| `DEEPSEEK_API_KEY`, `VK_TOKEN_*`, `TELEGRAM_TOKEN_*` | Комната КАРМАНа | В репозитории их нет; на машину приезжают через bootstrap |
| `SECRETS_TOKEN` | Отдельная строка в локальном env-файле | Токен комнаты — «дверь», а не «товар». Копируется владельцем с боевого бокса; в репозиторий не попадает |
| `SECRETS_VAULT_URL` | Там же | Адрес хранилища — технический домен, поэтому в отслеживаемом файле его нет |

**Проверка:** стенд поднимается с env-файлом, в котором **нет ни одного
ключа приложения** — ключи приезжают сами. Механика bootstrap'а покрыта
тестами (`tests/test_secrets_bootstrap/`); путь «потерян env → ключи не
доехали → процесс упал на `_require`» закрыт вызовом bootstrap **до** импорта
`config.runtime` (он и раньше стоял в `main.py` и `tasks/celery_app.py`;
переезд добавил туда же чтение локального env-файла — на Windows нет
systemd'овского `EnvironmentFile=`).
