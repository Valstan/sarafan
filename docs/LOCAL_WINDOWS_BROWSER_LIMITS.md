# Ограничения браузерного варианта на Windows и что с каждым делать

> Разбор ограничений, которые интерфейсу реально нужны. По каждому пункту —
> либо реализация, либо запись «не нужно» с причиной. Документ отдельный,
> чтобы решение не потерялось: переезд боевого контура не должен снова
> превратиться в «а как мы это будем делать на Windows».
>
> Контекст решения: [ADR-0023](adr/0023-pereezd-boevogo-kontura-na-lokalnuyu-mashinu.md)
> — отдельное десктопное приложение **не делаем**, берём существующий
> веб-интерфейс (FastAPI + Jinja2). Здесь — что этот выбор значит на практике.

---

## 0. Короткий ответ

Ни одно из перечисленных ограничений **не является блокирующим**. Четыре
реализованы штатными средствами (файл-менеджер браузера, планировщик задач,
служба Windows, сетевой доступ), два — признаны ненужными с причиной.

| № | Ограничение | Решение | Статус |
|---|---|---|---|
| 1 | Работа с файлами: импорт и экспорт | Реализовано — HTTP-загрузка/выгрузка | ✅ работает |
| 2 | Автозапуск вместе с машиной | Реализовано — планировщик задач Windows | ✅ работает |
| 3 | Фоновый режим без открытой вкладки | Реализовано — службы и задачи, вкладка не нужна | ✅ работает |
| 4 | Доступ с других устройств | Реализовано с ограничением — только из локальной сети, и только по решению владельца | ⚠️ условно |
| 5 | Печать | Не нужно — в интерфейсе нет печатных форм | ➖ не нужно |
| 6 | Работа с локальными файлами программы (открытие файлов из папок приложения) | Не нужно — весь доступ к файлам идёт через веб-ручки | ➖ не нужно |

## 1. Работа с файлами: импорт и экспорт

**Что интерфейсу нужно.** Загружать файлы (фото рекламных клиентов, картинки
офферов и рассылок) и выгружать их (фото, отчёты и результаты разбора).

**Решение — реализовано, ничего не менялось.** В проекте вся работа с файлами
уже идёт через HTTP-ручки, а не через «открыть файл на диске»:

| Операция | Ручка | Тип |
|---|---|---|
| Загрузка фото рекламного клиента | `POST /api/advertiser/.../photo` | `UploadFile` |
| Загрузка картинки в библиотеку офферов | `POST /api/ad-cabinet/offer-images` | `UploadFile` |
| Загрузка картинки для рассылки | `POST /api/broadcast/images` | `UploadFile` |
| Выгрузка результата разбора | `GET /api/parsing/download/{job_id}` | `FileResponse` |
| Выгрузка отчёта разбора | `GET /api/parsing/report/{job_id}` | `FileResponse` |
| Выгрузка фото | `GET /api/advertiser/.../photo`, `GET /api/ad-cabinet/...` | `FileResponse` |
| Выгрузка файла радара | `GET /api/radar/.../file` | `FileResponse` |

**Почему в браузере это не ограничение, а наоборот.** Браузер умеет и
`<input type=file>`, и скачивание файла — это штатные возможности, а не
костыль. Отдельное десктопное приложение здесь дало бы **меньше**: там
пришлось бы самому писать диалоги, drag-and-drop и «сохранить как».

**Проверка на стенде:** страница `/ad-cabinet` отдаёт 200; загрузка и выгрузка
идут теми же ручками, что и на бою, — код не различается.

**Нюанс, который стоит знать.** Куда физически ложатся загруженные файлы —
переменная `AD_UPLOAD_DIR` (каталог `web/uploads/` на стенде). На бою это
каталог внутри деплоя; на локальной машине — то же самое. Отдельного
десктоп-приложения, у которого была бы «своя папка», не существует, и
поэтому «куда делись фото» — вопрос к настройке, а не к программе.

## 2. Автозапуск вместе с машиной

**Что интерфейсу нужно.** Чтобы после перезагрузки компьютера стенд поднялся
сам, без «не забудь запустить».

**Решение — реализовано: планировщик задач Windows.** Скрипт
[`infra/windows/register-scheduled-tasks.ps1`](../infra/windows/register-scheduled-tasks.ps1)
регистрирует задачи `setka`, `setka-celery-worker`, `setka-celery-worker-wave`,
`setka-celery-beat`, `setka-vk-bot`, `setka-radar-intake` — по одной на юнит
боевого контура, с теми же именами.

| Свойство systemd | Замена в Windows | Как задано |
|---|---|---|
| `WantedBy=multi-user.target` | Триггер «при входе в систему» | `New-ScheduledTaskTrigger -AtLogOn` |
| `Restart=always`, `RestartSec=10` | Перезапуск задачи при сбое | `RestartCount 999` + `RestartInterval 1 мин` |
| `KillMode` (не убивать при остановке) | `ExecutionTimeLimit = 0` | Лимита выполнения нет — задача живёт, пока живёт процесс |
| Не запускать вторую копию | `MultipleInstances = IgnoreNew` | — |
| Живой процесс при закрытом окне | Сама суть задачи планировщика | Процесс не привязан к окну |

**Ограничение, которое надо назвать честно.** Триггер «при входе» означает:
пока владелец не залогинился — стенд не работает. Альтернатива «при старте
системы» требует сохранить пароль учётной записи в задаче, а это ровно то,
чего канон не хочет. Для режима «круглосуточно» нужно, чтобы машина была
залогинена (или чтобы задача была заведена как служба с отдельной учётной
записью — это отдельная работа, если понадобится).

**Проверка:** `Get-ScheduledTask -TaskName 'setka*'` показывает задачи;
`Start-ScheduledTask -TaskName 'setka'` поднимает веб без окна.

## 3. Фоновый режим без открытой вкладки

**Что интерфейсу нужно.** Работать без браузера: сбор постов, классификация,
публикация, рассылка — всё это фоновая работа, а не страница.

**Решение — реализовано, отдельного десктоп-приложения не требуется.** Вся
фоновая работа и так живёт не в браузере, а в процессах:

* **Celery worker** — очередь `celery` (мелкая периодика);
* **Celery worker** — очереди `wave`, `digest` (длинные задания);
* **Celery beat** — расписание;
* **демон VK-бота** — Long Poll;
* **демон приёма радара** — Long Poll + Telegram getUpdates.

Вкладка в браузере для этого **не нужна вообще**: ни одна из этих задач не
инициируется из интерфейса «вручную» — они запускаются по расписанию или по
событию. Единственное, что делает интерфейс, — показывает состояние.

**Проверка на стенде:** воркер и beat подняты как отдельные процессы; в логе
воркера `celery@<host> ready`, в логе beat — отправка задач по расписанию.

## 4. Доступ с других устройств

**Что интерфейсу нужно.** Возможно, смотреть витрину с телефона или планшета,
не подходя к компьютеру.

**Решение — условно реализовано, по умолчанию выключено.**

Сейчас веб слушает **только** `127.0.0.1:8000`. Это сделано намеренно:
интерфейс админский, за гейтом `middleware/auth_gate.py`, а kill-switch
`WEB_AUTH_ENABLED=0` на локальной машине **выключает гейт целиком** (он
нужен для локальной разработки без пользователей БД).

Значит два условия должны выполняться одновременно:

1. **Слушать не только петлю.** `--host 0.0.0.0` вместо `127.0.0.1`.
2. **Вернуть гейт.** `WEB_AUTH_ENABLED=1` — иначе интерфейс откроется всему,
   кто дотянется до адреса машины в домашней сети.

**Что для этого нужно и чего не хватает:**

| Нужно | Есть ли | Комментарий |
|---|---|---|
| Слушать на сетевом интерфейсе | Да, параметр запуска | `--host 0.0.0.0` |
| Аутентификация | Да, гейт по умолчанию | Сессия в подписанной cookie, роли `operator` и `radar` |
| Kill-switch локального dev | Да | `WEB_AUTH_ENABLED=0` — **на стенде выключен**, при публикации наружу его надо включить |
| Имя хоста в домене | Нет | Домашний IP меняется; нужен либо DDNS, либо доступ по IP |
| TLS | Нет | Без HTTPS cookie по сети передаётся открытым текстом; нужен либо reverse-proxy с сертификатом, либо доступ только из доверенной сети (VPN) |

**Вывод и рекомендация.** По умолчанию — **только петля**. Если владелец
захочет доступ с других устройств, минимально безопасная схема такая:
`--host 0.0.0.0` + `WEB_AUTH_ENABLED=1` + доступ из домашней сети; лучше —
через VPN. Публиковать интерфейс в интернет с этой машины **нельзя**: это
админская панель проекта.

**Проверка:** `netstat -ano | findstr :8000` — в стенде адрес `127.0.0.1`,
внешнего слушания нет.

## 5. Печать

**Что интерфейсу нужно.** Ничего: в интерфейсе нет печатных форм — ни
списков для прошивки, ни квитанций, ни отчётов, которые печатают как
документ.

**Решение — не нужно.** Обоснование:

* данные Сарафана (посты, сводки, рекламные заявки) печатаются, когда нужны,
  из экспорта или из текста — отдельная печатная форма ничего не добавляет;
* печать из браузера (`Ctrl+P` → «Сохранить как PDF») доступна и в
  браузерном варианте, и в десктопном — разницы нет;
* «свой формат для печати» потребовал бы отдельного шаблона и отдельной
  страницы — это работа без спроса.

**Если понадобится** (например, печатная форма для рекламного договора) —
это отдельная страница Jinja2 с `@media print`, а не отдельное приложение.

## 6. Работа с локальными файлами программы

**Что интерфейсу нужно.** Иногда подразумевается: «открыть файл прямо из
папки, где лежит программа» — то есть интерфейс должен уметь показывать и
открывать файлы с диска (дампы, логи, результаты разбора) мимо HTTP.

**Решение — не нужно.** Обоснование:

* всё, что интерфейсу положено показывать, оно и так получает по HTTP
  (`/api/parsing/download/{job_id}`, `/api/system-monitoring/...`);
* «папка программы» на боевом сервере — это корень деплоя, а на локальной
  машине — каталог репозитория; лезть к нему из веб-ручки значило бы открыть
  путь обхода всех ограничений (случайный путь из запроса — это чтение любого
  файла на диске);
* для оператора есть ровно то же, что и раньше: `ssh`/PowerShell и
  `logs/`, `downloads/` на диске. Для локальной машины это даже проще.

**Где это всё-таки нужно и как решено:** файлы, которые интерфейс
**отдаёт** (фото, отчёты, результаты разбора), лежат в известных каталогах и
отдаются по ручкам, которые проверяют путь. Файлы, которые интерфейс
**принимает**, попадают в каталог загрузок. Ни «произвольный путь», ни
«покажи мне весь диск» в интерфейсе нет и не требуется.

## 7. Сводка: что отличается от боевого варианта

| Аспект | На бою | На локальной машине |
|---|---|---|
| Адрес | Домен, nginx, TLS | `http://127.0.0.1:8000` |
| Аутентификация | Гейт включён | Гейт выключен (`WEB_AUTH_ENABLED=0`) — для локальной работы |
| Фоновые процессы | systemd-юниты | Задачи планировщика Windows |
| Метрики | Prometheus скрейпит `/metrics` | `/metrics` отдаётся, внешнего сбора нет |
| Файлы | Каталоги внутри деплоя | Те же каталоги внутри репозитория |
| Бэкап БД | cron на боксе (и он сломан — см. [MIGRATION_TO_WINDOWS.md](MIGRATION_TO_WINDOWS.md) §7) | Задача планировщика `pg_dump` в локальный каталог |

**Отдельно.** Ни один из пунктов не потребовал **отдельного десктопного
приложения**: всё, что в нём было бы, умеет браузер (файлы, печать), а всё
остальное (автозапуск, фоновый режим) — это задача планировщика, а не
программы. Это и есть содержательная причина решения «интерфейс оставляем
браузерным».
