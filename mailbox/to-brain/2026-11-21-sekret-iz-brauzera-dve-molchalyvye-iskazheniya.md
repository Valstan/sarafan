# Два молчаливых искажения секрета на пути «браузер → БД»

**Одна строка:** паттерн «секрет живёт вне репозитория» работает только если
значение **не меняется по дороге** — а два самых естественных способа донести
её до сервера портят его тихо, без ошибки, и всплывают это через два шага
как чужую ошибку авторизации.

## 1. Снимок страницы обрезает значение поля

Инструмент просмотра веб-страницы отдаёт два разных представления одного
элемента:

- **доступностное дерево** (`inspect`) — текст элемента, **обрезанный по
  длине** (у нас: ровно 100 символов);
- **DOM** (`query` с выборкой по атрибуту) — атрибут `value` **целиком**
  (у нас: 220 символов).

Значение токена в `<input readonly>` читается **только из DOM**. Из снимка
приходит первые 100 символов — строка правдоподобная, выглядит как токен, и
уходит в базу. Дальше API отвечает `[5] User authorization failed: invalid
access_token`, и виноватым кажется выпущенный ключ, а не способ чтения.

**Правило, которое стоит закрепить шире:** *любое значение, которое пойдёт
в систему как секрет или как идентификатор, читать из DOM-атрибута, а не из
доступностного представления.* Снимок годится, чтобы **найти** элемент, и
чтобы **увидеть, что поле заполнено**; содержимое — из DOM.

**Проверка, которая стоит копейку:** сразу после чтения сверить длину строки
с тем, что показывает сама страница. Если длина «круглая» (100, 128, 256) —
это обрезка, а не токен.

## 2. Текстовый конвейер до сервера портит байты

Файл с секретом, переданный на удалённый хост **текстовым пайпом**
(`Get-Content -Raw | ssh host "cat > file"`), приезжает длиннее на 1–2 байта:
конвейер дописывает перевод строки (у нас `\r\n`). Скрипт на той стороне
читает файл и **молча** получает значение с хвостовым `\r\n`; `.strip()`
его снимает — и всё выглядит исправным, пока значение не сравнивают побайтово.

**Правило:** секрет переносить **побайтово** — base64 на своей стороне,
`base64 -d` на другой:

```powershell
$b64 = [Convert]::ToBase64String([System.IO.File]::ReadAllBytes($p))
ssh host "printf %s '$b64' | base64 -d > /tmp/secret.txt"
```

**Проверка:** после переноса `wc -c` на сервере должен совпасть с
`(Get-Item $p).Length` на своей стороне. Расхождение — переносить заново, а
не чистить на сервере: «чистка» маскирует источник порчи.

## Общий вывод (переносимый за пределы setka)

Обе поломки — из класса «**всё зелёное, работа не сделана**»:

- значение выглядит как секрет, ошибка возникает позже и в другом месте;
- файл выглядит переданным, ошибка возникает позже и в другом месте.

Отсюда правило для любого «секрет вне репозитория»: **две сверки, обе
дешёвые** — длина сразу после чтения и размер сразу после переноса. Всё
остальное (валидация токеном, `strip()`, «да вроде записалось») проверяет
не то место, где порча произошла.
