# Env-файл — не источник истины для живого процесса

## Одна строка

Сервис, который читает env-файл **при старте** и **не перетирает уже заданные
переменные**, после ротации секрета живёт с **третьей копией** этого секрета:
файл обновили, комната обновили, а в процессе — старая. И если процесс
перезапускает **супервизор** (а не наоборот), то старый супервизор с устаревшим
окружением подмешивает старое значение **каждому новому ребёнку** — и рестарт
ребёнка не лечит ничего.

## Что было

Стенд отвечал **401** на ingest-эндпоинт с ключом, который мы считали
правильным:

- `config/local-stand.env` → `CLASSIFIER_INGEST_KEY` (43 символа);
- комната (`GET {SECRETS_VAULT_URL}/api/secrets`) → то же имя, **тот же** ключ;
- живой процесс → **401** `{"detail":"bad or missing X-API-Key"}`.

Проверка ключа — константное сравнение с `os.getenv(...)`, то есть читается
**окружение процесса**. Значит, в процессе лежала третья копия.

Механика: `modules/prod_env.load_env_files(..., override=False)` — «уже заданные
переменные не трогаются» (правило родилось из systemd: `EnvironmentFile` слабее
окружения юнита). На Windows, где systemd нет, правило осталось, а его следствие
никто не записал: **правка env-файла не доезжает до процесса без рестарта.**
Хуже — веб поднимает **супервизор** (Task Scheduler → PowerShell → python), и
окружение супервизора наследуется от сессии планировщика. Значит, перезапуск
юнита, если супервизор жив, снова подмешивает **старое** окружение.

## Что из этого переносимо

1. **Правило «сильнее» надо записывать вместе со следствием.** «Не перетирать
   заданное» — это не про силу, это про **срок жизни значения**: значение живёт
   в окружении процесса до его перезапуска. Правка источника (файла, комнаты,
   переменной окружения) без рестарта процесса не происходит. Записано правило
   без следствия — и получается «файл правильный, а сервис отвечает 401».
2. **Рестарт ребёнка не равен рестарту цепочки.** Если сервис перезапускает
   супервизор, то окружение супервизора — это окружение *всей* цепочки: старый
   супервизор подмешивает старые значения каждому новому ребёнку. Лечится
   рестартом супервизора (или его родителя).
3. **Сверять секреты по отпечатку, а не «на глаз».** Значения не выводить, но
   сравнивать их `sha256[:12]` — дешёво и показывает, **кто именно расходится**.
   У нас файл и комната совпали, и это сразу сузило поиск до процесса: без
   отпечатка мы бы искали «неправильный ключ» по всему контуру.
4. **Ротация секрета требует заранее описанного шага «перечитать окружение».**
   В нашем каноне такого шага не было вообще, потому что секреты брались из
   одного места. Теперь секрет может лежать в двух (файл + комната) — значит,
   и «перечитать» надо уметь.
