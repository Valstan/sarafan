# Ответ строкой: RS256, HS256 не будет

**Строка, которую ты просил: RS256.** Публичный ключ — из discovery-документа
эмитента, поле `jwks_uri` (`<issuer>/.well-known/jwks.json`). Никакого
HS256 у настоящих токенов не будет и не планируется.

## Почему это однозначно, а не выбор

Эмитент настоящего токена для Казанской — ЕСА, то есть наш Радар-ID
(модуль САРАФАНа, OIDC-провайдер экосистемы, ADR-0002). Он подписывает
access/id-токены **только RS256**, с `kid` в заголовке, и в discovery честно
объявляет ровно то, что исполняет:

- `id_token_signing_alg_values_supported: ["RS256"]`;
- `code_challenge_methods_supported: ["S256"]`.

Второго алгоритма подписи у эмитента нет по построению, поэтому «выбор»
стоит только перед кодом Казанской: либо он пин'ит RS256, либо этот вход
к нему не придёт.

## Что написать Казанской (три пункта, которые решают её fail-closed)

1. **Pin алгоритма**: `alg == "RS256"` в заголовке токена — и ничего больше.
   Токен с `alg: none` или `HS256` должен быть отвергнут как невалидный,
   без попытки «подобрать ключ».
2. **Ключ — по `kid`, а не «первый из JWKS»**: заголовок несёт `kid`, ключ
   матчится по нему; незнакомый `kid` — дотянуть свежий JWKS и повторить.
   Fail-closed при недоступном JWKS у Казанской сделан правильно, это
   оставляем.
3. **Issuer — строка символ-в-символ**: в discovery и в конфиге клиента
   должна стоять одна и та же punycode-строка
   `https://xn--b1ae3a1a.xn--80adkdyec4j.xn--p1ai` (G108/R16). Кириллический
   вид «вход.вмалмыже.рф» для сравнения `iss` не годится.

## Ловушка, из-за которой вопрос мог показать выбором

В discovery объявлено `token_endpoint_auth_methods_supported` с
`client_secret_post` / `client_secret_basic`. Это **аутентификация клиента
на token_endpoint**, а не алгоритм подписи токена: секрет туда передаётся
телом или basic-заголовком, и в подписи JWT он не участвует вообще. Если
код Казанской прочитал этот список как список алгоритмов подписи, он
решит, что «HS256 с client secret» — легальный вариант, и пойдёт проверять
подпись HMAC'ом. Этой развилки быть не должно: подпись id_token — всегда
RS256, секрет — только для обмена code на токены.

## Что ротация меняет у клиента

Приватный PEM лежит вне репозитория (пере-выпуск = ротация всей
экосистемы), JWKS отдаёт актуальный набор. Ротация меняет `kid`, поэтому
клиент, закэшировавший ключ навсегда, сломается **молча** — не «упадёт с
ошибкой», а начнёт отвергать валидные токены. Правильная форма —
JWKS по `kid` с докачкой; зашить ключ в код/конфиг Казанской нельзя.

Обратная просьба к Казанской — одна строка ack: «пиним RS256, ключ по `kid`
из JWKS, issuer сверяем punycode-строкой». Как придёт — выпускаем токен;
не торопим, согласен с тобой.
