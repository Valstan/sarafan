# «Токен сломан» ≠ «метод закрыт для этого типа токена»

## Одна строка

Вчера владелец прислал скриншот витрины: у девяти сообществ красное
«auto-disable: VK error 5». Токены были **живыми** — мы проверили их живой
валидацией (9 из 9 валидны, свойства на месте). Красным они стали потому, что
внешний API **отказал в удалении поста** ключом сообщества, а политика
auto-disable прочитала это как «ключ сломан».

## Приём 1 — один и тот же отказ приходит разными кодами

Метод `wall.delete` ключом сообщества не поддерживается в принципе. Внешний API
формулирует этот отказ двумя способами:

| Когда | Код | Формулировка |
|---|---|---|
| обычно (46 раз в логах за 7 недель) | **27** | «method is unavailable with group auth» |
| 21.11 (13 раз подряд) | **5** | «User authorization failed» |

Код 5 у нас означает «токен недействителен» ⇒ cooldown 24 часа + запись в БД. Код 27
означает «этот метод для токена такого типа закрыт» ⇒ просто уходим на другой
токен. **Отказ был один, а решение политики — противоположное.**

> **Правило для policy-ки, которая отключает по кодам: код ошибки нельзя читать
> без метода. Один и тот же отказ приходит разными кодами, и «здоровье токена» не
> выводится из кода отказа — оно выводится из того, что метод вообще доступен
> этому типу токена.**

Следствие-правило: **список «метод недоступен этому типу токена» обязан быть
инвариантом кода**, а не списком в доке. У нас он и был записан в доке
(`docs/ops/group-setup-probe.md`, живая проба 28.08: «wall.delete → community ⛔ 27,
user ✅»), но в коде отсутствовал ⇒ **док протух молча три месяца**, пока формулировка
отказа не сменилась.

## Приём 2 — «док-матрица» без привязки к коду протухает молча

Два места в одном репозитории сказали одно и то же разными словами: дока — «так
нельзя», код — «а мы пробуем». Никто не заметил: дока не проверяется тестами, а
код — не сверяется с докой.

> **Если в доке есть матрица «операция × токен/роль», каждая её строка должна
> иметь тест или константу в коде. Иначе это не канон, а воспоминание.**

Проверяемо: в коде уже был ровно такой список (`_USER_TOKEN_ONLY_METHODS` —
методы, которые физически нельзя звать ключом сообщества). Достаточно было
дописать в него одну строку — и целый класс дефекта закрылся.

## Приём 3 — как найти класс дефекта в прод-логах, не читая их глазами

Когда непонятно, где ломается, инвентаризация по методу даёт ответ за одну
команду:

```bash
grep -o "API error ([a-zA-Z._]*)" prod.log | sort | uniq -c | sort -rn
```

У нас 49 отказов внешнему API за период: **48 — `wall.delete`**, и только один
метод давал ложные отключения. Глазами по логу это читалось как «много разных
событий»; счётчик по методу показал один класс. **Перед разбором «почему столько
ошибок» посчитай их по методу — это сразу даёт гипотезу, которую потом подтверждает
живой замер.**

## Что стоило

Девять исправных ключей сообществ — на 24 часа каждый — и красные строки на
витрине, которые владелец видел четыре дня. При этом сами операции (удаление
постов) **прошли успешно** в том же каскаде: отказ был не на тупеже, а на первом
звене, которое заведомо не могло сработать.

> **Звон, который заведомо не может сработать, — это не «фолбэк», а расход: он
> тратит попытку, лимит и (если политика читает код отказа всерьёз) здоровье
> соседних сущностей.**
