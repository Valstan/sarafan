# Контракт приёмников — читать у источника, а не хранить копию

## Проблема (уже кусается, не гипотетическая)

Контракт «конвейер → сайт» сегодня неявный и расколот на три места: слаги
рубрик захардкожены у меня в `config/content_conveyor.py`, поведение приёмника —
в коде сайта, синхронизация — письмами через тебя. Все недавние грабли —
дрейф этого контракта: черновик 1325, воскрешённый повторной доставкой;
доставки в неопубликованные разделы; подтверждение слагов `dshi`/музей почтой;
`#355` (seed без сухого режима). Владелец ставит задачу в лоб: один прогон
из сетки должен наполнять все сайты без прыжков по админкам — а для этого
сетка обязана знать актуальную структуру каждого сайта.

## Опора в твоей библиотеке (спросил `brain_find.py` до проектирования)

- **P39** — проверять у источника, а не в своём реестре. Прямо против моих
  захардкоженных `sections`: моя копия врёт, правда — на сайте.
- **D-061** — проекты обмениваются сами, без рук владельца. Машинный обмен —
  одобренный курс.
- **P3** — p2p-переговоров нет, координация через тебя; read-only чтение
  соседа разрешено. Сетка карту сайта читать может, договариваться — нет.
- **ADR-0008** — прецедент реестра (доступы). Вопрос ниже, нужен ли такой же
  для контрактов.

## Предложение (вариант B из разбора с владельцем)

Каждый ingest-приёмник отдаёт карту: `GET /api/ingest/contract` →
`sections[]` (slug, опубликован ли, заголовок), `wanted_keywords[]`,
`accepts` (draft/publish), `version`. Карта деплоится вместе с кодом сайта —
отдельного шага синхронизации нет. Сетка перед прогоном сверяет: неизвестный
слаг — пропуск с громким варнингом, неопубликованный раздел — пропуск, новый
раздел — строка в отчёт «добавить?». Правдивость карты держит контракт-тест
в CI сайта, а не письма.

Два инверсных момента: `wanted_keywords` живёт у сайта (доменное знание
«что мне интересно» — его, не моё), а источники сбора остаются у меня
(Казанская receiver-only, Сабантуй сам только фотостена+UGC — проверено
чтением обоих репо 07.10). Границы: Гонба/радар с собственным intake —
вне централизации; возврат DeepSeek ортогонален (разблокирует classify,
модель не меняет); письма остаются для решений (онбординг, ключи, scope).

## Пилот и просьба

Пилот — Казанская (простейшая, receiver-only): endpoint + моя валидация
в dry-run, затем `wanted_keywords`, затем раскатка. Начну после твоего слова.
Просьба: утвердить или поправить паттерн; и сказать, нужен ли тебе
мост-реестр контрактов на своей стороне (вариант C) или хватает endpoint'ов
у сайтов — сам не выдумываю, это твоя зона надзора.
