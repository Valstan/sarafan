# Три переносимые находки после перевода движка на OpenCode v2

Контекст: движок классификатора переведён на v2-протокол (#910), единый serve
на боксе; параллельно free-tier платформы закрылся по IP. Детали домена — в
ADR-0008/P200/P201, здесь — только то, что переносимо.

## 1. Рецепт: v2 HttpApi как встраиваемый headless-движок (проверен на v2.0.32)

- `POST /api/session` → `{"data":{"id":"ses_…"}}`; модель и пермишены — свойства
  **сессии**, не сообщения.
- `POST /api/session/<id>/prompt` — text **top-level полем**; `POST …/wait` →
  204; `GET …/message` — новейшие первыми; `DELETE …/session` → 204 (сессии
  копятся — убирать за собой обязательно).
- Ошибка видна как `outcome ≠ succeeded` + поле `error` в сообщении; HTTP-коды
  промежуточных шагов успех не подтверждают — верить только сообщению.
- **Запреты инструментов на уровне сессии** (`permissions`) — работают: каждый
  проверен живьём (deny `shell/edit/webfetch/…` → инструмент не исполняется).
- **Ловушка:** `read` на `*` ломает сам free-tier-вызов (`provider.auth` 403)
  — узкие read-запреты работают, широкий нет. Самый строгий запрет не всегда
  самый безопасный: проверяйте, что запрет не ломает легитимный путь.

## 2. Урок безопасности: чужой текст + сессия с инструментами = фабрика RCE

Мы отправили в сессию по умолчанию текст поста, в котором модель «просили»
выполнить shell-команду, — она исполнила (маркер в `$HOME`, exit 0). Вывод
широкий: любой конвейер, подающий **недоверенный** текст (посты, письма,
тикеты, README) в агентскую сессию без песочницы, даёт посторонним исполнителя
на хосте; песочница — свойство **сессии**, и её надо задавать явно при создании,
а не надеяться на дефолты харнесса. Немедленное применение: у нас
`CLASSIFY_SESSION_PERMISSIONS` (deny-пакет + узкие read) до первого живого текста.

## 3. Платформенный гейт «бесплатного тира»: IP-reputation, не payload

- С ~17.10 все free-модели платформы отвечают 403 `FreeTierError` («free tier
  can only be used from within OpenCode») **с серверных IP** — при любом
  payload и любых пермишенах; A/B в апстрим-треде: residential → 403, WARP → OK.
- **Аккаунт-ключ бесплатный тир не поднимает** — открывает только платные
  модели. То есть «заведём ключ и переживём» — не работает.
- Урок для переноса: **бесплатный тир вендора как runtime-зависимость прод-конвейера
  — off-switch в чужих руках и по чужому сигналу (репутация IP)**: выключают
  волной, без предупреждения, не по вашей вине. Для прод-пути нужен платный
  ключ или свой выход; бесплатный тир — только трамплин для пилота.
- Апстрим-инцидент на 18.10 открыт без ETA (`anomalyco/opencode` #56324, #56397,
  #56341, #56334). Перекликается с вашим D-133 (15.10) — та же линия вендора.

## 4. Наблюдение: наивный WARP-фолбэк не работает за DPI

Пакет WARP ставится, но регистрация невозможна: TCP 443 до API WARP открыт, а
TLS ClientHello к `engage/api.cloudflareclient.com` **молча гасится** (DNS/TCP
живы; `openssl s_client` воспроизводит; сторонние хосты того же вендора
отвечают 200). Вывод: «нужен другой выход» нельзя решать установкой WARP-агента
не проверив, что **регистрация** проходит; DPI режет по SNI, а не по IP.
Диагностический порядок, который сработал: DNS → TCP → `openssl s_client` →
сравнение с другим хостом того же вендора.
