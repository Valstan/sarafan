# Ротация по чужому отказу съедает ресурс: разбор 22.11 (MiniMax Code)

**Одна строка:** вчера за сутки Сарафан взял у Кармана **118 аккаунтов и не сделал
ни одного успешного вызова** — потому что отказ «Sign in to MiniMax» (сломана
**сессия** CLI) трактовался как «аккаунт мёртв», и каждый следующий аккаунт
умирал ровно так же.

## Что было (все числа — из журналов, проверено на проде)

| Что | Значение |
|---|---|
| Выдач аккаунтов 22.11 | **118** (счётчик аудита Кармана), рост продолжался до ночи |
| Успешных вызовов после 11:21 МСК | **0** |
| Отказов `auth_expired` | **351** («Sign in to MiniMax to use Agent features») |
| Аренд без единого успешного вызова | **243 из 283** за весь контур 13–22.11 |
| Платный Дипсик-фолбэк 22.11 | **579** вызовов |

## Три урока (переносимые)

1. **Рантайм с внешним входом держит сессию в ОТДЕЛЬНОМ файле состояния, а не
   только в токен-сторе.** У MiniMax Code это
   `data/auth/<build>/<region>/<client>/auth-state.json`: поле `status`
   (`authenticated` / `anonymous` / `expired` …) решает всё. Живая проверка:
   access-токен **живой** (панель вендора отвечает, сеть в порядке), а рантайм
   отвечает «войдите». И обратно: если состояние = `authenticated`, тот же
   токен **работает** (вызов дошёл до модели).
   ⇒ **Проверять «а работает ли у нас вход» надо не по API вендора, а по
   состоянию рантайма.** API может быть зеленым, пока рантайм не пускает.

2. **Ротация по отказу, который не про ресурс, съедает ресурс.** Отказ «вход не
   годен» — это про **наше состояние**, а не про аккаунт. Правильный порядок:
   сначала починить состояние (продлить цепочку), и только если не вышло —
   брать следующий ресурс. У нас было наоборот: новый аккаунт умирал так же, и
   пул выедался за часы. **Перед ротацией спросить: отказ про аккаунт или про
   наше состояние?**

3. **Токен без refresh — это токен с часовым сроком жизни.** У MiniMax refresh
   одноразовый, и отдать его наружу нельзя (мандат владельца: наружу уходит
   только access). Значит **обновлять цепочку обязан владелец пула** (Карман
   хранит refresh и отдаёт потребителю свежий access через `renew`), а
   потребитель не должен подставлять заглушку: заглушка = смерть сессии через
   12 часов, и без вмешательства владельца пула восстановить её нечем.

4. **Предохранитель нужен на КАЖДЫЙ класс отказа, который можно замаскировать
   ротацией.** У нас стоял на «пустой аккаунт» (пауза после трёх сухих
   отказов) — и не было на «токен мёртв», то есть ровно на тот класс, который
   вчера съел пул. Классов отказа, при которых мы берём новый ресурс, должен
   быть ровно столько же, сколько предохранителей.

## Что сделано (Сарафан)

- `modules/minimax_engine.py`: состояние сессии CLI пишется **вместе** с
  токеном; отказ `auth_expired` → **продление того же** аккаунта (ручка
  `renew` у Кармана), и только если не вышло — следующий аккаунт.
- `modules/karman_minimax.py`: клиент ручки `renew`; журнальный проект в
  заголовке приведён к имени комнаты — иначе `renew` отклоняется с 409
  («аккаунт за другой комнатой»: журнальный проект выдачи становится
  владельцем аккаунта, а ручка сверяет его с проектом комнаты).
- Живой факт: сессия поднята вручную в 23:20 МСК → вызовы снова успешны
  (`ok: true`, 17–21 с), темп аренд упал с 7/мин до ~1 за четверть часа.
- Тесты: `tests/test_classifier/test_minimax_session_renew.py` (8 шт.).

## Что осталось / что нужно от соседа

- `renew` доступен только для аккаунтов, выданных под журнальным проектом
  комнаты. Аккаунты, выданные 22.11 под проектом `setka`, продлить нельзя
  (409) — они вернутся в оборот после ночного сброса (03:00 МСК 23.11).
- **Карману:** `renew` отдаёт только access — этого хватает (refresh-цепочка его),
  но «отдать наружу только access» стоит проговорить явно в контракте ручки:
  потребителю нужен **продлённый вход**, а не новый аккаунт.
