# Ack: ставим OpenCode + ВПН у себя (D-149)

Владелец 20.10 вернул тему в другой реализации: «ставить OpenCode+ВПН у себя —
да… будешь сам через него общаться с нейросетями для фильтрации потока постов
с парсинга и формирования постов для постинга». Владелец контура у нас —
SARAFAN (setka); движок, ВПН-плечо и сторож живут на нашем прод-боксе.

## Отчёт по форме, которую просила инструкция

- ОС: Ubuntu 24.04 LTS, x86_64, контейнер OpenVZ, 1 vCPU / 1,5 ГБ.
- uid движка: `opencode` = 1001 (отдельный пользователь, не владелец каталога
  деплоя) — он же цель nft-redirect'а.
- Публичный IP бокса не дублирую в письме: у нас правило «инфра-деталь не
  попадает в отслеживаемые файлы» (recon-поверхность). `HOST_IP` прописан
  только в юните на боксе, значение при необходимости отдам отдельным каналом.
- `servers=N`: пока **неизвестно** — ссылки подписки NextGenVPN у нас нет
  (в комнате КАРМАНа её тоже нет: проверил 49 имён). Владелец кладёт
  `NEXTGENVPN_SUBSCRIPTION_URL` в комнату, дальше `refresh-subscription.sh` →
  `servers=N` → включение `neural-vpn` + `neural-egress-redirect`.
- Один вызов модели: `deepseek-v4.1-flash-free`, `outcome=succeeded`, **2,7 с**.
- Reset (до/после): **не замерен** — без подписки менять сервер нечего.
  Пункт остаётся открытым, вернусь с числами.

## Три расхождения с инструкцией (проверено живьём 20.10)

1. **«Штатный установщик v2» ставит не v2.** `https://opencode.ai/install`
   отдаёт **1.19.3** — это другая линия (старый CLI), у неё нет `serve` с
   v2-контрактом. v2-бинарь берётся из npm-пакета платформы:
   `@opencode/cli-linux-x64@2.0.32` (tarball с одним бинарём ~211 МБ, npm не
   нужен — распаковал и `install -m755`). Рекомендую вписать это в инструкцию:
   иначе следующий проект повторит наш путь и получит молча другой продукт.
2. **Авторизация — basic-auth, не Bearer.** `Authorization: Bearer
   $OPENCODE_PASSWORD` на `/api/model` даёт `401 Authentication required`;
   `curl -u opencode:$PASSWORD` — `200`. `/` отвечает 200 вообще без
   авторизации (это health, а не «дыра»).
3. **Free-tier с нашего прод-IP сейчас отвечает 200.** Гейт 17–18.10
   (`403 FreeTierError`) не воспроизводится: один вызов и пилот на трёх живых
   постах прошли без ВПН. ВПН ставим не «чтобы пробить», а как страховку и как
   рычаг сброса лимитов.

## Переносимая находка: лимиты, которые молчат

Поставил движку `MemoryHigh=384M` / `MemoryMax=450M` — как в инструкции. Потом
проверил:

```text
systemctl show opencode-web -p MemoryAccounting -p MemoryCurrent
MemoryAccounting=no
MemoryCurrent=[not set]
```

Бокс — контейнер (у нас OpenVZ, P163), systemd внутри поднялся без учёта
памяти: `/sys/fs/cgroup/system.slice/<unit>.service/` нет вовсе, лимиты не
применяются. Конфиг при этом **выглядит** настроенным, юнит стартует, ничего не
ругается — и жертву при нехватке памяти выбирает OOM killer, не обязательно
виновника (у нас 14.10 он убивал движок при 290–620 МБ, но мог взять uvicorn
или celery).

Класс отказа: **настройка ресурса, которая применяется только при выполнении
условия, о котором никто не спрашивает**. Лечится не памятью, а проверкой:
`systemctl show <unit> -p MemoryAccounting` перед тем, как верить лимитам.
У нас теперь userspace-сторож (`opencode-rss-guard.timer`: раз в 2 минуты
смотрит суммарный RSS пользователя движка, при >400 МБ перезапускает юнит;
исходники — `infra/neural/` в нашем репо). Кандидат в GOTCHAS: «cgroup-лимит в
контейнере может быть декоративным — проверяй accounting, а не конфиг».

## Что дальше с нашей стороны

- Ждём подписку → включаем ВПН-плечо, замеряем `servers=N`, egress IP/страну и
  время reset сменой сервера (на эталоне 17,6 с).
- Движок уже работает движком классификатора: до переключения волны шли без
  нейро-фильтра (`http_402` DeepSeek, P177), теперь получают вердикты.
- Вторая половина заказа владельца — формирование постов для постинга — не
  начата, отдельная работа.
