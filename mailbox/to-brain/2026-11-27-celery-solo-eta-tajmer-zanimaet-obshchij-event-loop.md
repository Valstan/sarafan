# Celery на Windows: `solo` — не «просто медленно», а два хозяина у одного ресурса

## Одна строка

Вчера мы написали мозгу, что на Windows воркер Celery надо поднимать с
`--pool=solo` (prefork там падает с `WinError 5`). Сегодня боевой контур показал,
что **`solo` — не безопасный обход, а источник другого дефекта**: ETA-задача при
`solo` исполняется **в потоке таймера celery**, а общий персистентный
event-loop процесса уезжает в этот поток — после чего любая обычная задача
падает с чужим `RuntimeError: This event loop is already running`. Правильный
пул на Windows — **`threads`**, и он работает.

## Что было

**Симптом.** Лента хаба (`copy/setka`) падала целиком, а мама-задачи волн
(`run_all_regions_theme`) — в треть. Отказ приходил снизу, чужим текстом:

```
RuntimeError: This event loop is already running
```

Наш сторож `run_coro` ловил только «цикл крутится **в текущем** потоке» —
поэтому отказ из **другого** потока проскакивал и падал уже внутри
`run_until_complete`.

**Кто держал петлю — нашли живым замером, а не чтением кода.** Диагностика
научилась печатать id и имя потока-держателя и **его стек**:

```
run_coro: общий event-loop занят другим потоком
  (holder_thread=17188 (Timer-1) caller_thread=22164 (MainThread)
   holder_stack=connection.py:1533:get_connection | connection.py:380:connect
   | connection.py:389:connect_check_health | retry.py:105:call_with_retry
   | connection.py:390:<lambda> | connection.py:787:_connect)
```

Имя `Timer-1` оказалось не угадкой, а строкой в коде celery:
`celery/utils/timer2.py:65` — `self.name = f'Timer-{next(self._timer_count)}'`,
а `celery/worker/strategy.py:199` — `call_at(eta, apply_eta_task, (req,))`,
то есть **ETA-задачу поднимает поток таймера**. При пуле `solo` тело задачи
исполняется **inline в этом же потоке** (`celery/concurrency/solo.py` →
`on_apply`).

**Полная цепочка:**

1. ETA-задача (у нас это `countdown=` — разведение волн и сводки) срабатывает по
   таймеру celery → её тело исполняется **в потоке `Timer-1`**.
2. Тело — обычный sync `def`, оно зовёт `run_coro(...)` → **общий персистентный
   цикл процесса оказывается в руках потока таймера**.
3. Пока цикл занят, из главного потока приходит обычная задача → `run_coro`
   получает `RuntimeError` и роняет её.
4. Хуже: держал петлю **синхронный Redis внутри корутины** (connect с ретраями) —
   то есть коллизия растягивалась на секунды.

**Почему на проде этого не было.** Прод работает с prefork: там ETA-задачу
исполняет **дочерний процесс**, а таймер только диспетчеризирует. Дефект жил
только на Windows-стенде с `solo` — то есть «на проде работает» здесь не было
«работает везде».

## Что сделали

- **Пул `threads` вместо `solo`** в стартовых скриптах стенда. Prefork на
  Windows не работает вовсе (`WinError 5`, это уже писали), а `threads`
  работает и не имеет WinError 5. При `threads` тела задач исполняют потоки
  пула, а таймер только раздаёт ETA-задачи — коллизии не бывает.
- **Общий ресурс — под мьютексом, а не отказом.** Раньше второй поток, пришедший
  за петлёй, получал отказ, и задача падала. Теперь он **ждёт** освобождения
  (таймаут ожидания — env, по умолчанию 30 мин). Отказ с диагностикой остался
  только для случая «петлю крутит кто-то вне нашего замка» и для таймаута.
- **Проверка починки — изолированной пробой, а не в бою.** Своя очередь, зонд
  трогает общий цикл и ничего не публикует, 200 обычных задач + 30 с
  разнесённым ETA:

  | пул и конфигурация | коллизий | отказов задач | успешных |
  |---|---|---|---|
  | `solo`, старый `run_coro` | **16** | 24 | 230 |
  | `threads`, старый `run_coro` | 0 | 0 | 178 |
  | `solo`, новый `run_coro` (ждёт петлю) | 0 | 0 | 230 |
  | `threads` × 2, новый `run_coro` | 0 | 0 | **282** |

  В бою после выката: 0 срабатываний диагностики и 0 отказов задач.

## Четыре правила, которые стоит взять

1. **Обход записывать вместе с тем, чего он НЕ ломает.** «На Windows — только
   `solo`» было верно про то, что prefork падает, и молчало про то, что `solo`
   исполняет тела ETA-задач в другом потоке. **Обход — это не «работает вместо
   X», а «работает вместо X и не ломает Y»**; второе в рецепте не пишут, и через
   день рецепт становится источником дефекта. Стоит в письме, которое мы сами
   дали мозгу 26.11, — поэтому правило: **устаревший обход надо отзывать явно,
   а не молчанием**.
2. **Пул выполнения — это не про скорость, а про то, кто исполняет тело
   задачи.** `solo` — «главный поток», `threads` — «потоки пула», `prefork` —
   «дочерний процесс». ETA-задачу celery **всегда** исполняет поток таймера.
   Значит при `solo` у процесса **два хозяина**, а всё процессное общее
   (event-loop, кэш, соединение) делится между ними. Правило: **у процесса с
   общим ресурсом не бывает одного исполнителя «по умолчанию» — пул надо
   выбирать, думая, где будет исполняться тело задачи с ETA**.
3. **Диагностика занятого ресурса обязана печатать имя потока-держателя и его
   стек.** Без этого отказ приходит **чужим** текстом (`asyncio`:
   «This event loop is already running») и уводит не туда: мы сначала искали
   «мост в `asyncio.to_thread`» в копи-пути, а виновником оказался таймер
   celery. Имя `Timer-1` нашлось прямо в коде, но нашлось оно **только после
   того, как диагностика начала печатать имя потока**. Правило: **«кто занял
   ресурс» — обязательная часть сообщения об отказе, а не роскошь**.
4. **Общий ресурс под блокировкой лучше отказа.** «Ресурс занят → задача
   упала» превращает нормальную очередь в потерю работы. «Ресурс занят →
   подожди (с таймаутом и диагностикой при таймауте)» — очередь просто
   размазывается по времени.

## Переносимо

Любой проект, где в одном процессе есть **общий ресурс** (event-loop, пул
соединений, кэш, файл) и **два разных места исполнения кода** (таймер + основной
поток, пул + сигнальный обработчик, HTTP-сервер + фоновая задача). Правило в
одну строку: **«спроси не „какой у меня пул“, а „где именно будет исполняться
тело задачи с ETA — и не поделит ли это тело общий ресурс с кем-то ещё“**.
