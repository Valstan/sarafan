# Две Windows-грабли для конвейеров: воркер, который «жив», и pytest, который «упал»

**Контекст.** Переносили боевой контур на локальную Windows-машину владельца
(промт КАРМАНА #161, проект SARAFAN): Celery worker + beat + PostgreSQL + Redis.
Обе грабли вылезли при подъёме стенда и обе **выглядят не тем, чем являются**,
— поэтому делюсь: обе переносятся на любой проект, который тянет
Python-конвейер на Windows.

## Грабля 1 — prefork Celery на Windows: воркер рапортует «ready» и не работает

**Симптом.** Воркер с пулом по умолчанию (prefork, `billiard`) стартует и
печатает `ready`, как будто всё в порядке. Но его дочерние процессы падают:

```
File "...\billiard\pool.py", line 406, in _ensure_messages_consumed
    if self.on_ready_counter.value >= completed:
PermissionError: [WinError 5] Отказано в доступе
[ERROR/MainProcess] Process 'SpawnPoolWorker-1' pid:880 exited with 'exitcode 1'
```

Главный процесс **продолжает рапортовать `ready`** и бесконечно перезапускает
детей. Ни одна задача не выполняется, но глазом воркер выглядит живым:
процесс есть, статус зелёный, в логе — `ready`.

**Почему это ловушка.** Проверка «воркер запустился» (процесс есть / в логе
`ready`) — **не проверка того, что воркер работает**. Она не может покраснеть:
пока главный процесс жив, `ready` будет печататься. Краснеет только
счётчик обработанных задач, а он — единственное, что отличает «поднялся» от
«обслуживает».

**Обход (работает).** `--pool=solo`. На Linux остаётся prefork — там он штатно.
При `concurrency=1` соло-пул даёт то же самое, что prefork с одним ребёнком,
но без процесса-ребёнка. Практическое следствие: **на Windows поднимай
воркер с `--pool=solo` и `--concurrency=1`**, а очередь разбирай вторым
воркером — два соло-воркера на одной очереди Celery допустимы.

**Что не выяснено.** Корневая причина не изолирована. Тот же
`PermissionError: [WinError 5]` вылезает на финальной уборке временных
каталогов `pytest` (грабля 2) — то есть оба случая могут иметь одну причину
(права на `%TEMP%` на машине). Перенаправленный `TEMP` внутри репозитория
воспроизведения не снял (пул зависал). Соло-пул — рабочий путь независимо от
причины.

**Переносимо.** Любой проект с Celery на Windows. Правило в одну строку:
**«Celery на Windows — только solo; `ready` в логе не доказывает, что воркер
обрабатывает задачи»**. Если в проекте есть проверка «воркер жив» — она должна
смотреть обработанные задачи, а не наличие процесса.

## Грабля 2 — pytest на Windows: 100% зелёных, а прогон «упал»

**Симптом.** Прогон доходит до 100% и падает на финальной уборке:

```
File "...\_pytest\pathlib.py", line 354, in cleanup_dead_symlinks
    if not left_dir.resolve().exists():
PermissionError: [WinError 5] Отказано в доступе:
  'C:\Users\<user>\AppData\Local\Temp\pytest-of-<user>\pytest-current'
```

При этом **итоговая строка с числом проверок не печатается** — прогон выглядит
упавшим, хотя все проверки зелёные. Это не тесты проекта, а pytest на этой
машине.

**Обход (работает).** `--basetemp` внутри репозитория:

```powershell
.\venv\Scripts\python.exe -m pytest tests/ -q --basetemp=temp\pytest_win
```

**Почему в гейт это нельзя засунуть «как есть».** Канон требует сверять не
только «зелёно/красно», но и **число собранных проверок** — «12 passed вместо
~4500» это не зелёный прогон, а другой путь. На Windows из-за этой грабли
число **вообще не печатается**: красный exit code при 100% зелёных проверок
неотличим от настоящего падения, если не знать причины. Отсюда правило:
**«прогон, который упал на уборке, а не на тесте, надо отличать по месту
падения — иначе Windows-гейт читается как красный тест, и его начинают
«чинить», ломая зелёное»**.

**Переносимо.** Любой проект с pytest на Windows-машине. Кандидат в общий
рецепт запуска тестов на Windows: `--basetemp` внутри репозитория +
сверка числа собранных проверок с эталонным прогоном (Linux/CI).

## Почему обе стоят письма

Обе — из одного класса: **симптом противоречит причине**. Воркер «жив», но не
работает; прогон «упал», но зелёный. И обе лечатся не «починкой», а
переключением режима (`solo`, `--basetemp`) — то есть правильный ход здесь
не чинить, а честно обойти и **записать обход**, чтобы следующая сессия не
искала причину заново. Кандидат в GOTCHAS (Windows-раздел).
