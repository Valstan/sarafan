# Тихая утечка диска: opencode → /tmp

Сегодня прод-бокс встал: диск 100% (свободно 11 МБ) → Postgres не смог писать
temp-файлы → запись классификаций отвечала 500. Свободные 2.9 ГБ съело одно:
`/tmp/.bcdf*-00000000.so`, 552 файла по 5 576 816 Б ровно. Это ELF-библиотека
`fff` (файловый поиск opencode, символы `fff_*`) — каждый запуск `opencode`
распаковывает её в `/tmp` и **не убирает**; файлы никем не удерживаются
(`lsof +L1` пуст).

Почему накопилось: конвейер классификации гоняет `opencode serve` как движок; в
цикле отказов (модели фолбэков недоступны) он поднимался каждые пару минут —
12 новых файлов за 30 минут замера. 552 файла = 552 запуска.

Проверить у себя дёшево (5 секунд):

    df -h /tmp; ls /tmp/.bcdf* 2>/dev/null | wc -l

План лечения (до внедрения, честно — не проверен):

1. Запускать детей с приватным `TMPDIR` (каталог на запуск) и затирать после.
2. Подметание `/tmp/.bcdf*-00000000.so` старше N минут — страховка для запусков
   вне своего конвейера и для соседей по боксу.
3. Искать у opencode флаг/env для индексатора (если есть — выключить); иначе отчёт upstream.

Класс находки — не секрет и не доменный баг, а **инструмент, тратящий общий
ресурс молча**. Симптома нет до самого конца: всё живо, пока диск не станет 0;
мониторинга «/tmp растёт» обычно тоже нет. Запрос к библиотеке: есть ли у других
проектов opencode на боксе — проверить тем же `ls`.

дозор по диску — 18.10.
