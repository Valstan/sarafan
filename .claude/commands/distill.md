# /distill — дистилляция Корпуса в правила классификатора (из чата)

Цель: разобрать **Корпус** (накопленные вердикты нейросети + правки оператора в
`content_classifications`) и предложить обобщённые правила для файла-корректировщика.
Заменяет удалённую облачную рутину «Дистиллятор правил Сарафана» (решение владельца
2026-07-14): дистилляцию делает Claude прямо в dev-сессии, по запросу владельца
(обычно раз в неделю; напоминание — шаг 3.2 в `/start`).

**Ручная ветка — единственная, пока `CLASSIFIER_DISTILL_ENABLED` не поднят** (дефолт выкл,
`config/classifier.py`). Еженедельный beat-слот `classifier-distill-weekly` при выключенном
флаге отвечает `skipped:distill-off`. До 04.09 своего флага у него не было — он гейтился
`CLASSIFIER_HEADLESS_ENABLED`, то есть флагом ИИ-фильтра, который на проде поднят: обе ветки
читали одни и те же правки и писали в одну панель, а та за неделю набрала 8 черновиков-пересказов.
Черновики авто-ветки видно по `source='headless'` в `classification_rules`.

Петля (ADR-0005) не меняется: черновики правил → панель «Правила обучения» в
`/classifier` → оператор утверждает/правит/отклоняет → approved попадает в
эффективные `/postulates` следующего прогона рутины-классификатора. ИИ правила
сам не применяет — человек в петле.

**Исключение — прямое слово владельца** (решение 2026-10-19): если он говорит
«вноси правки напрямую, минуя черновики», правки применяются сразу (Шаг 4,
«Прямой путь»), а черновики не создаются. Петля при этом не разрывается: решает
тот же человек, только не через UI, а через свой же код `decide_rule`.

## Шаг 1. Забрать Корпус с прода (read-only)

Скрипт гоняется **на VPS** (ключ не покидает прод; в локальном env его нет).
NB: файл ключа хранит строку `CLASSIFIER_INGEST_KEY=<значение>` (KEY=VALUE, не голый
ключ) — извлекать через `cut`, иначе 401 (проверено live 2026-07-14):

```bash
ssh sarafan 'cd ~/SETKA && CLASSIFIER_INGEST_KEY=$(sudo -n grep -m1 "^CLASSIFIER_INGEST_KEY=" /etc/setka/classifier-routine-key.txt | cut -d= -f2- | tr -d "[:space:]") python3 scripts/classifier_routine.py corrections --limit 200 --days 30 --out /tmp/distill_run'
ssh sarafan "cat /tmp/distill_run/corrections.json"
ssh sarafan "cat /tmp/distill_run/postulates.md"
```

`--days` брать как **дней с прошлой дистилляции минус один**: правки, сделанные в день
самого прогона, им уже переработаны, и окно «ровно N дней» затянет их повторно —
получится ложное «есть material» при нуле новых (напоролись 2026-07-28: 34 коррекции
в окне 8 дней, все от 07-20, при `--days 7` → `count: 0`).

Если `count=0` — честно доложить «коррекций нет, дистиллировать нечего» и завершить
(журнал всё равно обновить, Шаг 5). Порог осмысленности: коррекций ≥ ~10.

## Шаг 2. Анализ (в чате, это и есть работа)

Прочитать корпус коррекций + действующие постулаты. Найти **повторяющиеся паттерны**
(не единичные случаи): что оператор систематически поправляет и как. По каждому
паттерну — одно ОБОБЩЁННОЕ правило в стиле действующих («если …, то action/theme …»).

**Гигиена файла правил (требование владельца — файл не должен разрастаться):**
- не дублировать правила, уже присутствующие в postulates.md;
- не противоречить существующим; если новый паттерн **противоречит старому правилу**
  — предложить не новое правило, а ПРАВКУ/retire старого (оператору в панели:
  «правило N устарело, паттерн сменился на …»);
- заодно просмотреть действующие выученные правила с бейджем «⏱ протухает»
  (без подачи дольше `CLASSIFIER_RULE_STALE_DAYS`) и включить в отчёт кандидатов на 🗑;
- предлагать мало и метко: 2–5 сильных правил за прогон лучше 20 слабых. Нет
  устойчивых паттернов — не предлагать ничего.

## Шаг 3. Показать владельцу ДО отправки

Вывести предлагаемые правила в чат (rule_text + rationale + сколько правок за каждым).
Дождаться «ок» (можно скорректировать формулировки прямо тут). Это дешёвле, чем
гонять черновики через панель туда-сюда.

## Шаг 4. Внести правила в дело

Два пути, выбор — за владельцем. По умолчанию черновики.

### 4а. Черновиками (по умолчанию)

Записать `proposals.json` локально (scratchpad), закинуть на VPS и отправить:

```bash
scp <scratchpad>/proposals.json sarafan:/tmp/distill_run/proposals.json
ssh sarafan 'cd ~/SETKA && CLASSIFIER_INGEST_KEY=$(sudo -n grep -m1 "^CLASSIFIER_INGEST_KEY=" /etc/setka/classifier-routine-key.txt | cut -d= -f2- | tr -d "[:space:]") python3 scripts/classifier_routine.py propose /tmp/distill_run/proposals.json'
```

Формат: `{"proposals": [{"rule_text", "rationale", "evidence": [{"lip", "verdict_type",
"ai_value", "operator_value"}], "region_code": null, "model": "<модель сессии>"}]}`.
Ответ сервера `{recorded, skipped_existing, skipped_invalid}` — в отчёт.

После отправки напомнить владельцу: утвердить черновики в `/classifier` →
панель «Правила обучения».

### 4б. Прямой путь (по слову владельца «вноси напрямую»)

Правила живут в **двух слоях**, и «напрямую» для них означает разное:

1. **Базовый слой** — файл [`config/classification_postulates.md`](../../config/classification_postulates.md)
   (git, hand-authored). Правится обычной веткой → PR → merge → `git pull` на проде.
   Рестарт не нужен: `read_postulates()` читает файл на каждый прогон.
2. **Выученные правила** — строки в БД `classification_rules` (overlay, ADR-0005).
   Панель закрыта сессионной кукой, ключа у агента нет, поэтому прямой путь —
   [`scripts/distill_apply_rules.py`](../../scripts/distill_apply_rules.py) на проде:
   тот же `decide_rule`, что кнопка «утвердить с правкой» (пересчитывает `norm_key`).

Порядок: файл правок вида `{"<id>": "<новый rule_text>"}` → сначала **dry-run**
(печатает было/станет и отказывается писать текст длиннее `_MAX_RULE_LEN`, иначе
он обрезается молча) → показать владельцу → **запись только после явного «да» в
том же ходе** (гейт #025: это DML в прод-БД) →

```bash
scp <scratchpad>/edits.json sarafan:/tmp/distill_edits.json
ssh sarafan "sudo bash -c 'set -a; . /etc/setka/setka.env; set +a; cd ~/SETKA && exec ./venv/bin/python scripts/distill_apply_rules.py /tmp/distill_edits.json --apply'"
```

Проверка — не по «команда прошла», а по предмету: `GET /api/classifier/postulates`
(ключ рутины) должен содержать новые тексты, а размер файла — вырасти. Правка
выученного правила видна сразу, базовая — после `git pull` на проде.

## Шаг 5. Журнал (обязателен, даже при count=0)

Добавить строку **сверху** таблицы [`docs/ops/DISTILL_LOG.md`](../../docs/ops/DISTILL_LOG.md):
дата, коррекций прочитано, черновиков предложено, recorded, заметка. Закоммитить
вместе с тематической работой или отдельным doc-PR (`/close_session` подхватит).
По этому файлу `/start` считает «дней с последней дистилляции» для напоминания.

## Шаг 6. Отчёт

Числа: коррекций прочитано / паттернов найдено / черновиков предложено /
recorded/skipped / кандидатов на retire. Плюс agree-rate из ленты, если под рукой.
