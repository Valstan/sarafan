# AGENTS.md — единые правила для AI-агентов САРАФАН

Этот файл — **единственный канонический вход для любой нейросети**: Claude Code, Codex, Gemini CLI и других агентов. Инструкции конкретного инструмента (`CLAUDE.md`, `GEMINI.md`) могут дополнять его, но **не должны дублировать или переопределять** проектные правила: две копии канона расходятся молча.

Правила ниже сформулированы через **намерение**, а не через механизм конкретного инструмента. Где у Claude Code есть машинное выражение правила (permissions, хуки, slash-команды) — это указано как *способ исполнения*. **Агент без такого механизма соблюдает то же правило вручную:** неприменим инструмент, а не правило.

## Интеграция с brain_matrica

SETKA управляется meta-репо [brain_matrica](../brain_matrica/) (стратегический hub для всех проектов @valstan). Связь — **асимметричная**: каждая сторона пишет **только в свой репо** ([ADR-0001 v3](../brain_matrica/adr/0001-brain-projects-mailboxes.md) от 2026-05-23). **При старте сессии синхронизировать (`fetch`/`pull --ff-only`) можно ТОЛЬКО свой репо SETKA.** Соседние репо, включая `brain_matrica`, — **только чтение, без каких-либо синхронизирующих команд** (`fetch`, `pull`, `checkout` запрещены): проект или Мозг могут одновременно работать в локальной копии, в т.ч. иметь ещё не запушенные письма. Входящий mailbox читается **из двух каналов**: локально + GitHub API (`main` того же проекта) без clone/fetch/pull.

| Направление | Кто пишет | Куда | Кто читает |
|---|---|---|---|
| brain → setka | brain (в своём репо) | `brain_matrica/mailboxes/setka/from-brain/*.md` | setka read-only, **два канала**: локально + GitHub API (`Valstan/brain_matrica` @ GitHub `main`) без fetch/pull |
| setka → brain | **setka (в своём репо)** | **`setka/mailbox/to-brain/*.md`** | brain read-only тем же двухканальным способом |

| Аспект | Где / как |
|---|---|
| Протокол mailbox | [ADR-0001 v3](../brain_matrica/adr/0001-brain-projects-mailboxes.md) (асимметричная схема; `compliance` field: `suggest`/`recommend`/`mandate` = MAY/SHOULD/MUST по RFC 2119) |
| PR-only flow | [ADR-0002](../brain_matrica/adr/0002-pr-only-flow-no-direct-push.md) — direct push в `main` запрещён, кроме hot-fix аварии |
| Постулаты | [POSTULATES.md](../brain_matrica/docs/POSTULATES.md) |
| Запись о setka в brain | [projects/setka.md](../brain_matrica/projects/setka.md) (read-only с моей стороны — пинговать через `mailbox/to-brain/` feedback) |
| Свой mailbox | [`mailbox/to-brain/`](mailbox/) (только этот канал для исходящих в brain) |

**Жизненный цикл письма от brain:**

1. **Шаг 0 любой сессии, независимо от агента:** входящий mailbox сканится **двумя каналами** (без `git pull`/`fetch`/`clone` в `brain_matrica`):
   - **локально:** `../brain_matrica/mailboxes/setka/from-brain/*.md` (без `DRAFTS/` и `ARCHIVE/`);
   - **GitHub API:** `https://api.github.com/repos/Valstan/brain_matrica/contents/mailboxes/setka/from-brain` — `main` того же репо, запрос на каждый запуск. Читать через `gh api …` (работает и без токена на публичном репо; при 404/лимите — `gh auth status`).
   Набор = **объединение** каналов по каждому письму. Одноимённое письмо различается → свежесть по истории **именно этого пути**: незакоммиченная локальная версия — свежее; иначе последний локальный коммит файла vs последний коммит пути на GitHub; если порядок не определяется — прочитать обе версии, явно отметить конфликт, **не перезаписывать**. Доклад в формате `[urgency COMPLIANCE]`.
2. Пользователь решает обработать → применяем директиву согласно compliance.
3. **Ответ** (acknowledgement / feedback / report) — в **свой репо** `setka/mailbox/to-brain/YYYY-MM-DD-<slug>.md`, коммит в setka через PR.
4. **Архивацию исходных писем делает brain у себя** — не моя зона.

**Проактивный шеринг находок (рефлекс #009):** значимые **переносимые** находки (скилл / фича / паттерн / решённая нетривиальная боль) сам отправляю в мозг через `mailbox/to-brain/` — не дожидаясь просьбы. Условный шаг + анти-спам-фильтр (значимо ∧ переносимо ∧ неочевидно) — шаг 5.5 процедуры закрытия сессии ([`.claude/commands/close_session.md`](.claude/commands/close_session.md), pool [#009](../brain_matrica/cross-project-ideas/ideas/009-share-findings-reflex.md)). По умолчанию — молчим.

**Консультация с библиотекой Мозга (рефлекс #014):** read-сторона того же шкафа, что и #009 (тот пишет, этот читает). **Не** безусловный шаг старта сессии (token economy, [ADR-0003](../brain_matrica/adr/0003-token-economy-principles.md)) — а **условный триггер**, срабатывает ровно в двух случаях:

1. **Перед вводом нового/нетривиального** (паттерн, инструмент, инфра-подход, миграция данных, кросс-cutting рефактор) — *до* проектирования спросить библиотеку: нет ли готового опыта.
2. **При незнакомой грабле инструмента/инфры/деплоя** (не доменный баг, а «почему CI / Payload / git / VK так себя ведёт») — *до* долгого дебага спросить её же по симптому.

**Как спрашивать — одной командой** ([ADR-0013](../brain_matrica/adr/0013-memory-layout-index-plus-chunk-files.md) мозга, мандат D-097 от 2026-09-18):

```bash
python ../brain_matrica/.claude/scripts/brain_find.py "слова симптома или темы"
```

Печатает лучшие строки **всех** индексов мозга (грабли, идеи включая архив, справка, постулаты, решения, ADR) и путь к файлу, который стоит прочитать. Чистый stdlib, без демона и подключений; `brain_matrica` при этом **не синхронизируется** — читается локальная рабочая копия (см. «Что нельзя» ниже).

**Правило чтения — индекс грепается, кусок читается целиком, реестр целиком не читается никогда.** С 2026-09-18 `GOTCHAS.md` и `REFERENCE.md` у мозга — только индексы; тела лежат в `cross-project-ideas/gotchas/G<N>.md` и `cross-project-ideas/reference/R<N>.md` по 2–5 КБ. Прежний рецепт «грепнуть `## G24` → `Read` с offset» **больше не работает**. Якоря вида `GOTCHAS.md#g<N>` в наших файлах остаются валидными адресами записи; новые ссылки ведём на файл.

`brain_find.py` не нашёл нужное с первого запроса → это **письмо мозгу**, а не молчание: так у него решается, строить ли резидентного библиотекаря.

Нашёл релевантное → переиспользуй (и при желании отпишись в `mailbox/to-brain/`, что применил). Не нашёл → продолжай как обычно. Чтение мозга на старте уже делается двухканально (Шаг 0), повторно не платим. **Тишина = норма** (триггер не сработал → 0 лишних чтений). Pool [#014](../brain_matrica/cross-project-ideas/ideas/014-consult-library-reflex.md).

**Одна память на экосистему (мандат D-097, 2026-09-18).** Долговременное и **переносимое** знание живёт только у мозга. У нас локально остаётся *оперативное* (handoff, PENDING, карта кода, профиль машины) и *специфичное для нашего стека и домена* (VK API, Celery-конвейер, районные пулы — непереносимое по построению).

- Нашли переносимое → письмо в мозг (рефлекс #009), **у себя — одна строка-указатель** на `G<N>`/`#NNN`, не копия текста. Копия расходится молча ([#087](../brain_matrica/cross-project-ideas/ideas/087-fix-in-one-copy-is-divergence-not-fix.md)): исправят одну, вторая продолжит врать, и узнать об этом неоткуда.
- **Писать в память мозга нельзя** — только письмом; раскладывает и нумерует он.
- **Свой реестр, переросший ~50 КБ, переходит на ту же раскладку** — индекс + файл на запись, потолок в гейте. У нас так разложен `PENDING_FOLLOWUPS.md`: живой индекс — сам файл, история — [`docs/pending/CLOSED.md`](docs/pending/CLOSED.md), тела — `docs/pending/P<NNN>-<slug>.md`, сторож — [`scripts/pending_gate.py`](scripts/pending_gate.py) в pre-commit. Номера `P<NNN>` не переиспользуются: закрытая запись остаётся адресом.
- **Чистка** — раз в месяц вместе с ротацией PENDING: два места с одним и тем же содержимым или старое, противоречащее новому, сливаются в одну запись.

**Тактика напрямую (ADR-0007 мозга, 2026-07-05):** любой sibling-репо (`../<project>/`) можно читать **read-only** напрямую, без письма в мозг: API-контракты, docs, handoff соседа, его `mailbox/to-brain/`. Синхронизирующих команд (`fetch`/`pull`/`checkout`) при этом **не выполнять** — читается локальная рабочая копия (свежесть последнего локального коммита) или GitHub API показывать избыточно; коммитить никогда. Эвристика: «нужно ЗНАТЬ про соседа → читай сам; нужно, чтобы сосед/экосистема что-то СДЕЛАЛИ или ЗАПОМНИЛИ → письмо в мозг». Начал **зависеть** от чужого API/формата (интеграция, не разовое чтение) → сообщить мозгу письмом (прочитанное — не контракт).

**Что нельзя:**

- ❌ Синхронизировать чужие репо **в любой форме** — `fetch`, `pull`, `checkout`, `reset` в `brain_matrica` или любом sibling-репо запрещены (canon 2026-08-04).
- ❌ Писать в `brain_matrica/` (ни в `mailboxes/setka/to-brain/`, ни в `.last-seen`, ни в `ARCHIVE/`, ни куда-либо ещё). Доступ — только чтение.
- ❌ Клонировать `brain_matrica` для записи; ходить в чужие mailbox'ы; удалять архивные письма у brain'а.
- ❌ Исполнять что-либо на чужом боксе. Соседний репо читаем — соседний сервер трогаем только через его опубликованный HTTP-интерфейс.

## Жизненный цикл задачи

1. **Старт сессии** — стартовая процедура ([`.claude/commands/start.md`](.claude/commands/start.md)). Результат обязателен независимо от агента: сводка mailbox от brain_matrica, что нового на `main`, какие хвосты, состояние прода.
2. **Feature-ветка** — `git checkout -b <type>/<slug>` (`feat/`, `fix/`, `chore/`, `docs/`, `refactor/`). Direct push в `main` запрещён ([ADR-0002](../brain_matrica/adr/0002-pr-only-flow-no-direct-push.md)).
3. **Работа над фичей** — обычные правки кода. После них:
   - `pytest tests/ -q` — все тесты зелёные. **Сверяй и количество собранных** (порядок — в §«Состояние проекта»): «12 passed» вместо ~2000 — это не зелёный прогон, а не тот путь или сломанный сбор.
   - `pre-commit run --all-files` — black/isort/flake8.
4. **PR** — `gh pr create` с Summary + Test plan. **Описательное тело PR заменяет старую DEV_HISTORY** ([ADR-0001](docs/adr/0001-archive-dev-history.md)) — что меняли, почему, какие тесты, какое применение на проде. **Авто-мерж под гейтами** ([#027](#автономия-под-гейтами-027)): зелёные `pre-commit` + `pytest` + CI → `gh pr merge --squash --delete-branch` без ручного «окей» (черта — destructive прод-операции с данными, см. ниже).

   **Обязательная проверка защиты `main`** (директива brain 2026-08-17, сверено с сервером 2026-08-20): влить PR нельзя, пока не позеленела проверка с именем ровно **`test (3.12)`**. Это не «светится красным в интерфейсе» — **merge отклоняет сервер**, и правило действует на владельца тоже (`enforce_admins: true`). Отсюда три следствия для любого агента:
   - ждать надо **именно обязательную** проверку (`gh pr checks <N> --required --watch`), а не «все чеки»;
   - **`--admin` не помогает** — при `enforce_admins: true` он отклоняется и у владельца. Красный CI значит «чинить», а не «обойти»;
   - **`--auto` недоступен** — в настройках репозитория `allow_auto_merge: false`, поэтому «сервер сам вольёт по позеленению» не работает; ждать и мержить приходится самому.

   Красная обязательная проверка — это гейт, работающий как задумано. Если она красна не из-за твоих правок (например, гейт нашёл живой секрет в истории), merge блокируется **всей** работе до устранения причины — так и должно быть, это не повод обходить.
5. **Релиз на прод** — релизная процедура ([`.claude/commands/reliz.md`](.claude/commands/reliz.md)), обязательная последовательность для любого агента: обновление `PENDING_FOLLOWUPS.md` (если есть новые техдолги) → commit с описательным сообщением → push на feature-ветку → `gh pr create` с полным описанием → review → merge → SSH `git pull` → миграции (если есть) → `systemctl restart` → curl health. Один шаг = один диалог.
6. **Закрытие сессии** — процедура закрытия ([`.claude/commands/close_session.md`](.claude/commands/close_session.md)), **единственный** признанный способ закрыть сессию. Коммитит и пушит **всю** работу (код + доки) на GitHub через PR, обновляет `SESSION_HANDOFF.md` + `PENDING_FOLLOWUPS.md`, проверяет sync-гейт (`scripts/git_sync_check.sh --gate`) — сессия не считается закрытой, пока всё не на `origin`. Деплой — отдельно, релизной процедурой.

## Автономия под гейтами (#027)

Brain-мандат [#027](../brain_matrica/cross-project-ideas/ideas/027-gate-replaced-autonomy.md) (2026-06-06): **человеческий «окей на дифф/мерж/деплой» заменён автоматическими гейтами.** Не «убрать проверку», а «заменить ритуал на машинную проверку»: автономия безопасна ⟺ гейты сильны.

**Ярусы риска — проектное правило, а не настройка инструмента.** Claude Code выражает их машинно в коммитимом [`.claude/settings.json`](.claude/settings.json) (`defaultMode: auto` + ярусные `permissions.allow`/`deny`). **Агент без такого механизма соблюдает те же ярусы вручную:** автономен там, где ярус говорит «авто», и останавливается за подтверждением там, где ярус этого требует. Отсутствие машинного выражения не отменяет ни одного яруса.

| Операция | Режим | Гейт = подтверждение |
|---|---|---|
| Правки файлов, ветки, коммиты | **авто** | — |
| Push feature-ветки, `gh pr create`, **`gh pr merge --squash`** | **авто** | `pre-commit run --all-files` (black/isort/flake8) + `pytest tests/ -q` + CI зелёные |
| Деплой не-схемных правок (`git pull` + `systemctl restart` + health-curl) | **авто под гейтом** | smoke-прогон пайплайна (`scripts/smoke_test.py --region <r> --theme <t>`, dry-run поверх `parse_and_publish_theme`; подробности — Шаг 8.5 памятки [`reliz`](.claude/commands/reliz.md)) + health 200; деплои **сериализованы** (не внахлёст) |
| **Миграции на проде с данными, `ALTER`/`DROP`/`DELETE`/`UPDATE`, ротация токенов, необратимые trigger'ы** | **подтверждать в том же ходе** | **эту черту не пересекаем — гейт остаётся человеческим** ([#025](../brain_matrica/cross-project-ideas/ideas/025-destructive-prod-confirm-same-turn.md)): спросить пользователя и дождаться явного «да» **до** операции, в том же ходе |

**Запрещено безусловно** (Claude Code выражает это машинно через `permissions.deny`, который побеждает всё; агент без такого механизма держит тот же запрет поведенчески — сила запрета одинакова): `git push --force`, `git push origin main/master` (только через PR, [ADR-0002](../brain_matrica/adr/0002-pr-only-flow-no-direct-push.md)), `git reset --hard`, `rm -rf`.

**Почему человеческий гейт не выражается конфигом.** У Claude Code разрешительные правила сопоставляются по префиксу команды; у других агентов фильтр устроен иначе, а часто его нет вовсе. Общее одно: **destructive-дискриминатор сидит внутри кавычек** — префикс не отличает read-only `ssh sarafan "..."` от `ssh sarafan "...psql DROP..."`. Поэтому черту держит **поведение агента, а не конфиг**, и нарушать её нельзя. Памятка [`sql`](.claude/commands/sql.md) гейтит DML, релизная процедура ведёт миграции под подтверждением.

**Не полагайся на то, что фильтр инструмента остановит тебя перед продом** — у разных агентов фильтры разные или их нет вовсе. Ответственность за подтверждение прод-операций лежит на агенте, а не на конфиге.

> NB ([#018](../brain_matrica/cross-project-ideas/ideas/018-liveness-watchdog-durable-heartbeat.md)): раз мерж/деплой идут автономнее, «приём/публикация молча встала» дороже — держать heartbeat-watchdog и его вывод в дашборд живым.

## Три правила из пула (D-096, решение владельца 2026-09-18)

Приняты как часть канона по мандату мозга ([D-096](../brain_matrica/mailboxes/setka/from-brain/2026-09-18-d096-ten-pool-ideas-go-to-work-your-slice-and-three-dates.md)).
Каждое — про класс отказа, у которого **нет симптома**: всё зелёное, все спокойны, а работа не сделана.

### #166 — фича с новой границей получает сквозное ревью ветки, а не только по-задачное

Фичу режут на PR'ы, и это правильно. Но **дыра живёт не в задаче, а между задачами**: ревьюер PR №2 держит в голове его диff и его инвариант, а путь «данные из №1 читаются кодом из №3 через механизм, тронутый в №4» не входит в область внимания ни одного из ревью — не по невнимательности, а потому что у него нет предмета.

**Правило:** если фича вводит новую границу изоляции (роль/роль, арендатор/арендатор, демо/прод, публичное/приватное, гость/владелец) и режется на **3+ PR** — до включения обязательно **финальное ревью всей ветки целиком**, а не сумма по-задачных.

**Как ловить заранее:** считай не задачи, а **границы**. Число мест, где граница обязана держать, равно числу путей чтения и записи, а те распределены по PR'ам произвольно. Второй признак — **зеркальность**: границу почти всегда проверяют с одной стороны («демо не видит живое») и почти никогда со второй. Односторонняя формулировка в описании задачи = незакрытая половина.

### #125 — гейты гоняет CI, а не память; зелёный один не говорит ничего про красный соседний

Гейт, покрывающий **те же файлы**, но проверяющий **другое**, читается человеком как подтверждение по всем осям: смотрят на последний запущенный, а не на все. Новый гейт не добавляется к старому в голове — он его **вытесняет**.

**Правило:** каждый гейт вызывается **своим шагом CI**, а не через агрегирующий скрипт, который останавливается на первой ошибке. В ручном прогоне список гейтов берётся из конфигурации CI, а не из привычки.

**У нас это так** — [`.github/workflows/ci.yml`](.github/workflows/ci.yml) держит отдельными шагами: secret scan (gitleaks) · pre-commit (black/isort/flake8) · pytest. **Честная оговорка:** прод-smoke (`scripts/smoke_test.py`) в CI не переносится — он про живой бокс, и остаётся шагом релизной процедуры под гейтом #027. Это не исключение из правила, а его граница: в CI живёт всё, что можно проверить без прода.

### #152 — дата, названная вне будильника, — не дата

Назвал дату в письме мозгу, в теле PR или в абзаце `PENDING_FOLLOWUPS.md` — обещание **выглядит** выполненным (дата произнесена, обе стороны спокойны), а сработать не может: читать её автоматически неоткуда. У нас это уже случилось — «G307, срок 19.09, не начат» три сессии ехал в `SESSION_HANDOFF` и двигался только тем, что человек перечитывал handoff глазами.

**Правило:** единственная дверь для дат — [`docs/TICKLER.md`](docs/TICKLER.md). Назвал дату — **в тот же ход** впиши её туда; письмо, отчёт и абзац PENDING производны и дату не запускают. Будильник печатает SessionStart-хук ([`scripts/tickler.py`](scripts/tickler.py)): просроченное и ближайшие 7 дней, об остальном молчит.

**Проверка на замыкание:** пообещал дату — сгрепай её обратно, `python scripts/tickler.py --check YYYY-MM-DD`. Не нашёл — обещания не было. Закрыл пункт — ставь ✅ с датой, строку не удаляй (история не переписывается).

## Git и совместная работа нескольких агентов

Владелец открывает репо разными нейросетями. Правила ниже — чтобы агенты не затаптывали друг друга ([ADR-0011](../brain_matrica/adr/0011-vendor-neutral-agent-contract.md) §Decision п.4):

- `main` защищён логически: ветка → коммит → push → PR → squash merge. Прямой push в `main`, force-push и `reset --hard` запрещены.
- Один агент — одна задача, отдельная ветка и, при одновременной работе, отдельный `git worktree`. **Не запускай двух пишущих агентов в одном рабочем дереве.**
- Каталог worktree должен быть вне индекса. Текущая конвенция — `.claude/worktrees/<имя>` (уже покрыта `.gitignore`); любой другой игнорируемый каталог тоже годится, но добавь его в `.gitignore` тем же PR.
- Перед правкой проверяй `git status`. **Незнакомые изменения считай чужими:** не удаляй, не форматируй попутно, не включай в свой коммит и не прячь в stash.
- Не переключай ветку в рабочем дереве, которое может использовать другой агент.
- Объявляй границы файлов/задачи в описании PR. Если границы пересекаются — второй агент ждёт merge первого и ребейзит свою ветку до начала правок.
- Один PR решает одну задачу. Коммиты — Conventional Commits.
- После обрыва сначала восстанавливай фактическое состояние из Git/PR и `SESSION_HANDOFF`, не повторяй действия по памяти (отдельной команды для этого нет — решение владельца D-066, 2026-09-02).

**Межмодельная память — только артефакты** ([ADR-0011](../brain_matrica/adr/0011-vendor-neutral-agent-contract.md) §Decision п.5): Git/PR, [`docs/SESSION_HANDOFF.md`](docs/SESSION_HANDOFF.md), `mailbox/`, ADR. **Чат одной модели не является источником истины для другой** — что обсуждалось в другой сессии, существует ровно настолько, насколько записано в файл. Долговечные решения живут в документации/ADR, состояние незавершённой работы — в `SESSION_HANDOFF`, история — в коммитах и PR.

Отдельных vendor-копий памяток нет: рваное зеркало хуже отсутствующего, источник один — этот каталог.

**Как читать памятку, если ты не Claude Code.** Она написана на языке этого инструмента — это способ исполнения, а не условие применимости:

Это важнее прочего: все `AskUserQuestion` в памятках — гейты на destructive-операциях (`sql`, `reliz`, `close_session`), а не украшение. Прочитать «инструмента нет → гейта нет» — самая дорогая ошибка чтения этих файлов.

## Какие AI-файлы хранить в Git

**Коммитить:**
- `AGENTS.md` — этот файл, единственный источник истины по правилам;
- `CLAUDE.md`, `GEMINI.md` — короткие адаптеры к `AGENTS.md`;
- `.claude/commands/`, `.claude/agents/`, `.claude/settings.json` — общие памятки и командная политика разрешений;
- `.codex/hooks.json` — общий SessionStart-хук git-sync для Codex (тот же `scripts/git_sync_check.sh`, что у Claude Code в `settings.json`);
- `docs/`, `mailbox/`, `docs/SESSION_HANDOFF.md`.

**Не коммитить:**
- локальные разрешения и персональные настройки (`.claude/settings.local.json`);
- кэши, сессии и планы конкретного инструмента (`.claude/*` кроме перечисленного выше, `.codex/*` кроме `hooks.json`, `.gemini/`);
- worktrees, `.env*`, ключи, токены, логи, временные файлы.

Список выше — **по именам файлов**, вторая линия обороны. Первая — правило по содержимому, ниже.

**Секреты не должны жить в репозитории даже под защитой `.gitignore`.** Их место — env-файл приложения на прод-боксе (см. ниже).

### Что не публикуется: секреты и инфра-детали

**Публичный репозиторий — recon-поверхность.** Репозиторий открыт с 2026-08-17: любой
отслеживаемый git-ом файл читает посторонний. Поэтому рядом с классом «секреты» действует
второй, самостоятельный класс — **инфра-детали**.

**Инфра-деталь — это то, что помогает постороннему найти бокс, попасть на него или понять его
устройство.** Класс определяется свойством, а не списком файлов:

- имена хостов и технические домены (в т.ч. FQDN, выданный хостером), IP-адреса, внешние порты;
- имя хостера и модель периметра (где терминируется TLS, что стоит на edge, что на боксе);
- абсолютные пути на сервере, имя системного пользователя, раскладка каталогов, пути к
  env-файлам и файлам ключей, имена файлов секретов;
- имена и расположение SSH-ключей, `HostName`/`Port` из `~/.ssh/config`;
- состав жильцов бокса: соседние проекты, их каталоги, посторонние сервисы;
- внутренние URL и адреса машинных дверей (шлюзы, ingest, дашборды, витрины мониторинга);
- профиль машины (ядра, RAM, диск) и модель привилегий («sudo без пароля», кто что видит).

**Запрет — про носитель, а не про канал.** Правило не «не писать в чат» и не «не отдавать
наружу»: инфра-деталь не попадает **ни в один отслеживаемый файл** — ни в код, ни в конфиг, ни
в доку, ни в памятку, ни в тест, ни в сообщение коммита, ни в тело PR/issue, ни в лог, который
может уехать в GitHub Actions. `.gitignore` защитой не считается: файл может стать отслеживаемым,
а репозиторий — публичным (и стал). **Формулировка через канал перестаёт защищать при смене
канала, не выглядя нарушенной** — именно так это правило и сломалось у соседей ([#189]).

**Вместо значения — роль.** В коде и скриптах — переменная окружения **без дефолта**: не задана
→ внятная ошибка или штатная деградация, а не подставленный адрес. В nginx-конфигах —
плейсхолдер, подставляемый `sed`-ом в шаге установки. В доках и памятках — роль словами:
«прод-бокс», «корень деплоя», «env-файл на проде».

**Исключение — канал доступа.** Раздел [«Прод-доступ — только SSH»](#прод-доступ--только-ssh)
называет SSH-алиас (`sarafan`) намеренно: алиас — локальное имя из приватного `~/.ssh/config`,
снаружи он ничего не резолвит, и он несёт allowlist разрешений инструмента. Всё остальное в том
разделе — путь, пользователь, хост — под общим правилом.

**Границы правила — честно.**

- **Вычистка ничего не отзывает.** Литерал остаётся в git-истории, в форках и в кэше GitHub.
  Настоящая митигация для уже опубликованного — сменить сам факт: переехать, отозвать ключ,
  ротировать секрет, закрыть дверь. Правка репозитория — гигиена на будущее, не инцидент-ответ.
- **Исторические записи не переписываем.** `docs/SESSION_HANDOFF.md`, `mailbox/to-brain/*`,
  `docs/adr/*`, `docs/ops/*LOG*.md` и закрытые (✅ / ~~зачёркнутые~~) пункты
  `docs/PENDING_FOLLOWUPS.md` — записи о том, что было: их находят и помечают, но не правят.
  Живые части тех же файлов (открытые и `parked` пункты, инструктивные разделы) — под общим
  правилом.
- **Зелёный `gitleaks` этого класса не ловит.** Правила сканера — регулярки по форме секрета; у
  хостнейма, пути и алиаса формы нет. «Secret scan passed» ≠ «recon-деталей нет». Класс держится
  обзором перед коммитом, а не гейтом.
- ⚠️ **Коллизия с правилом «GitHub — источник истины между машинами», найдена при первом же
  применении 2026-08-25.** Стандартный рецепт «вынести значение в приватную памятку» здесь не
  работает: приватная памятка по определению не коммитится, а владелец работает с нескольких
  машин, где единственный общий носитель — `origin`. Не-синхронизируемый файл с прод-путями
  создаёт разъезд машин ровно того класса, против которого написан
  [раздел про GitHub](#github--источник-истины-между-машинами) — то есть лечит recon-гигиену
  ценой более дорогой болезни.
  **Поэтому объём вычистки ограничен тем, что не требует приватного носителя:** абсолютные пути
  заменены на `~`-относительные (работают в удалённом шелле идентично, но не раскрывают ни
  системного пользователя, ни раскладки), устаревшие алиасы поправлены. **Путь к env-файлу
  остаётся literal'ом сознательно** — без него команды перестают копироваться, а вынести его
  некуда. Настоящее решение — третий носитель, доступный со всех машин (комната КАРМАНа), и это
  отдельная работа, а не побочный эффект вычистки. Пока её нет, **не делай вид, что класс
  закрыт**: он сужен.

**Проверка перед коммитом одна:** «поможет ли эта строка постороннему добраться до бокса или
понять его устройство?» Если да — заменить на роль.

## Правила, которые НЕ менять

### GitHub — источник истины между машинами
- Пользователь работает на **разных компьютерах** (днём один, вечером другой). GitHub (`origin`) — единственный общий источник истины. Версии разъезжаются, если работа осталась незапушенной на одной машине.
- **Никогда не оставляй сессию с несинхронизированной работой.** Закрытие сессии = всё закоммичено и **запушено** на `origin`. Гейт — `scripts/git_sync_check.sh --gate` (exit 1, пока дерево не чистое и не запушено); его обязан прогнать любой агент перед объявлением сессии закрытой. Процедура-носитель — [`close_session`](.claude/commands/close_session.md).
- **Нитка сессии фиксируется двумя механизмами.** Курируемый `docs/SESSION_HANDOFF.md`
  пишет агент по `/close_session` — это «почему» и «что дальше». Машинное состояние
  пишет хук без участия модели (`scripts/session_autosave.py`) — это «что происходило»:
  локально полную выжимку в `.claude/session-state/` после каждого хода, а после
  каждого мержа/пуша — версию без дословных реплик владельца в ветку `session-state`
  и снимок рабочего дерева в `wip/<машина>` на GitHub. Ветки строятся `commit-tree`
  мимо рабочего дерева и не трогают `main`. Правило: после мержа сессию можно закрыть
  молча, ничего не потеряв; курируемую нитку по-прежнему пишет только `/close_session`.
- **При входе в сессию должен отработать `scripts/git_sync_check.sh --warn`** — он предупреждает, если на этой машине осталась несинхронизированная работа или `origin` ушёл вперёд (другая машина запушила → нужен `git pull`). Скрипт vendor-neutral, способ его запуска инструмент-специфичен: Claude Code — SessionStart-хук в `.claude/settings.json`, Codex — `.codex/hooks.json`. **Агент без механизма хуков запускает скрипт первой командой сессии вручную** — требование не отменяется отсутствием хуков.
- **Естественная фраза** «закрой сессию», «закрой сессию разработки», «заверши сессию», «закрываемся» → выполнять процедуру закрытия сессии.

Точный путь остаётся в отслеживаемых памятках сознательно — см. оговорку про коллизию в [«Что не публикуется»](#что-не-публикуется-секреты-и-инфра-детали).

### Ссылки на сообщества — числом внутрь, именем наружу

Закон владельца 2026-09-06. У каждого сообщества ВК два адреса: числовой
(`vk.com/club158787639`) и короткий (`vk.com/malmyzh_info43`). У них разные свойства,
и путать их нельзя.

- **Внутри системы — только числовой `owner_id`.** Парсинг, публикация, статистика,
  дедуп, привязки — всё адресуется числом. Число не меняется никогда; короткий адрес
  владелец волен переименовать в любой момент, и код, завязанный на него, сломается молча.
- **Наружу — короткий адрес.** Посты, сообщения, лендинги, письма, визитки, списки сети:
  всё, что читает человек, показывает `vk.com/<screen_name>`. Единственная точка сборки —
  `modules/region_links.community_url(vk_group_id, screen_name)`; она же держит фолбэк на
  `club<id>`, если короткий адрес неизвестен. **Не собирать такие ссылки строкой на месте.**
- **Ссылка на пост — исключение:** `vk.com/wall<owner_id>_<post_id>` работает только с
  числом, короткого адреса в ней не бывает. Это не нарушение закона, а другая сущность.
- Короткий адрес кэширует ночная таска `collect_member_snapshots` в
  `Region.config['screen_name']`, поэтому переименование группы самолечится за сутки и
  ручной синхронизации не требует.

**Шаблон короткого адреса** — `<латиницей город>_info<код региона по РФ>`: Кировская
область — `43`, Татарстан — `16`. Код выводится из области (`regions.parent_region_id`),
а не зашивается в текст.

⚠️ **Переименование группы — необратимое действие.** Старый короткий адрес
**освобождается** и может быть занят кем угодно, а все ранее опубликованные ссылки на него
умирают. Числовая ссылка при этом продолжает работать. Отдельно: короткий адрес может
входить в привязку ключа шлюза (`gateway_keys.allowed_screen_names`) — например,
`VMALMYZHE` привязан к `malmig_info`. Переименование без правки привязки тем же действием
даёт потребителю `403`.

### Описание сообщества — половина человеку, половина поиску

Закон владельца 2026-09-06. Описание группы ВК — **это то, по чему её находят во внутреннем
поиске**, а не только текст «о нас». Поэтому у каждой нашей группы описание состоит из двух
частей, и обе обязательны:

1. **Для человека** — что это за лента, как прислать новость, ссылка на витрину сети.
2. **Поисковый индекс** — строка тем (`<Город> — новости, происшествия, афиша, объявления,
   работа, расписание автобусов, подслушано.`) плюс строка мест: у района — сёла и посёлки,
   у области — районы. Не больше восьми: длинный список читается как спам.

**Это правило распространяется на новые группы с момента создания** — не «потом допишем».
Генератор один: `modules.promotion.copy.render_group_description` (`render_search_tail`).
Руками описания не сочинять — иначе части сети снова разъедутся.

**Места ранжируются, а не берутся по алфавиту.** Данных о населении у проекта нет и выдумывать
их нельзя. Ранг считает `scripts/setup_groups.py --rank-localities` и кладёт в
`Region.config['localities_top']`: для района — по частоте упоминаний села в собранных постах
(`collected_post_audit`), для области — по числу подписчиков районной группы. Частота
упоминаний для поискового индекса даже лучше населения: она говорит, о чём люди пишут, то есть
что они и ищут. Алфавитный список остаётся запасным вариантом, если ранга ещё нет.

⚠️ **Унификация не должна отбирать функцию.** Правило родилось из ошибки: 06.09 описания
приводили «к единому виду» и на первой же группе чуть не стёрли авторский хвост поисковых фраз,
который выглядел просто длинным текстом, а работал индексом. **Прежде чем заменить авторский
артефакт шаблонным — спроси, что этот артефакт делал.** Форма унифицируется, функция — нет.

### Локальная разработка
- ОС: Windows 11; основная оболочка — PowerShell 5.1, POSIX-скрипты гоняются через Git Bash. Это две разные среды (пути, кавычки, `NUL` vs `/dev/null`) — если у агента отдельные инструменты под каждую, не смешивай синтаксис.
- **Не сочиняй текст внутри командной строки — вообще** (заказ владельца 2026-08-25, письмо
  [`2026-08-25-never-author-text-inside-a-command-string.md`](mailbox/to-brain/2026-08-25-never-author-text-inside-a-command-string.md)).
  Ни heredoc (`cat <<'EOF'`), ни `git commit -m` с переносами, ни `psql -c "…"`, ни
  `--body "…"`, ни PowerShell `@'…'@`. **Пиши содержимое в файл, а команде отдавай путь:**
  `git commit -F msg.txt`, `gh pr create --body-file body.md`, `psql -f q.sql`,
  `curl --data-binary @body.json`, на прод — `scp` (или `base64 -w0 f | ssh sarafan 'base64 -d > /path'`).
  **Почему:** текст в команде проходит через кавычки аргумента инструмента → парсер
  локального шелла (а их здесь два, с несовместимым синтаксисом многострочных строк) →
  для `ssh` ещё и парсер удалённого шелла → кодовую страницу консоли. Число слоёв на месте
  вызова не видно, и backtick, `$`, кавычка или кириллица ломаются на любом из них — а
  выглядит это как ошибка в самом коде. Путь к файлу — один ASCII-токен, он переживает все
  слои, и содержимое не встречает парсер ни разу. **Триггер:** увидел в своей команде
  перенос строки, backtick, `$`, кавычку или не-ASCII — переписывай через файл, а не
  доэкранируй (типовые отказы этого класса — G190, G235 в GOTCHAS мозга).
- Worktree: `.claude/worktrees/<имя>` на отдельной ветке (см. [«Git и совместная работа нескольких агентов»](#git-и-совместная-работа-нескольких-агентов)).
- Python: `py -3.11` локально для тестов (preferred), `py -3.12` тоже OK (=прод). `scripts/setup-dev.ps1` сам выбирает 3.11 → 3.12 → дефолтный `py`. venv в корне worktree.
- Запуск тестов: `.\venv\Scripts\python.exe -m pytest tests/ -q` (или через активированный venv).
- **`main.py` локально** — логи идут в stderr через `logging.basicConfig` (LOG_LEVEL env, дефолт `INFO`). На проде systemd редиректит stdout/stderr в `~/SETKA/logs/uvicorn_production.log`. Полный запуск всё равно требует Postgres + Redis локально; обычно достаточно тестов.

## Стиль коммитов и веток

Conventional commits + соответствующий префикс ветки:
- `feat(scope):` / `feat/<slug>` — новая фича
- `fix(scope):` / `fix/<slug>` — баг-фикс
- `refactor(scope):` / `refactor/<slug>` — рефакторинг без смены поведения
- `docs:` / `docs/<slug>` — только документация
- `chore:` / `chore/<slug>` — обслуживание (deps, configs)
- `test:` / `test/<slug>` — только тесты

Slug — kebab-case, описательный. Ветка удаляется после merge (`gh pr merge --delete-branch`). Force-push в feature-ветку разрешён, в `main` — никогда.

Тело коммита — что и почему. В конце — трейлер с **именем и версией агента, которым велась работа**: каждый агент подписывается собой, трейлер фиксирует, кто реально писал.

```
Co-Authored-By: <агент и версия> <noreply@...>
```

Например: `Co-Authored-By: <Имя модели и версия> <noreply@anthropic.com>`.

## Когда что-то идёт не так

- **Прод 502 / health не отвечает** → `ssh sarafan "journalctl -u setka -n 100 --no-pager"`. Чаще всего — `setka.service` упал, нужен `systemctl restart`.
- **Сводки не выходят** → проверить по памятке [`celery`](.claude/commands/celery.md): жив ли beat, нет ли регионов на cooldown, нет ли ошибок в `celery-worker.log`.
- **`pytest` падает локально** → проверить, что worktree свежий (`git pull origin <ветка>`), venv обновлён (`pip install -r requirements.txt`), есть `pytest pytest-asyncio`.
- **Миграция не применилась** → SQL-файлы в `database/migrations/*.sql`, применяются вручную через `ssh sarafan 'sudo -u postgres psql -d setka -f ~/SETKA/database/migrations/NNN_*.sql'`. Памятка [`sql`](.claude/commands/sql.md) это умеет.
